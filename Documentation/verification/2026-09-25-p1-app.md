## 実装と確認点

- 検証 reader を、`O_NOFOLLOW` で開いた通常ファイルの記述子と結び付けた。同一性は fstat とパスの両方で検査し、公開直前にも再検査する。ZIP 出力は eager な検証・計画照合に加えて `ArchiveUpdater.probe` と件数照合を通す。
- 公開名・inode・size・mtime・記述子・兄弟巻・パスワード・形式が一致すれば `reopen()` で解析を引き継ぎ、eager な local header cache を手放す。不一致なら、検証 output を解放してから URL から開く。
- S0 の追加要件: fallback の open と 7z の暗号化 header の再判定は、既存の `VolumePublishUncancelled` を使い、Task のない別 thread で行う。新しく作った reader は Mutex から一度だけ `sending` で取り出す。session の reader や sink を別 thread と共有せず、actor の公開・再読込の間に await は挟まない。新たな `@unchecked Sendable`、`nonisolated(unsafe)` はない。
- 保存計画は基底の key と占有を一度作り、改名先の key を pass 間で再利用する。init の初回 `validate` だけは局所的な `baseKeys` を渡す（子の多い削除で key を再計算しないため）。その配列は保持せず、その後の `validate` は変更分だけを検査する。stamp・参照・最終形と途中の衝突検査を残す。
- 表現可能性の全件 probe は残す。hard link の参照の付け替えが不要な場合だけ、entry の再構築を省く。旧実装をテスト target の `ReferenceArchiveSaveReplayPlan` に保持して比較する。
- 保存後は一覧・filter・基底の読み出しを先に用意し、編集準備を `loadingTask` に渡す。controller の `display` が token を消していたため、明示的に渡された token を維持する引数も追加した。前の準備の取消し・世代・revision・editor・準備 ID を照合し、別名で保存の二度目の reset からの古い失敗は提示しない。
- 自前で検証して採用した単一 ZIP の世代だけ、背景準備・最初の予約の G4 を省略する。次の保存の G4 は必ず実行する。

意図した代償: KaitoKit の eager な検証と終端 probe の両方を通る G4 固有の欠陥は、保存後の最初の予約ではなく、次の保存で拒否される。その間の予約は別名で保存できる。`DeferredPostSaveTests` は第二候補（ditto 製 ZIP の data descriptor の CRC を 1 bit 変更）でこの差を固定する。第一候補の CD 末尾への 4 byte の追加と CD size +4 は、この KaitoKit では `ZIP central-directory count does not match its data` で拒否された。第二候補は `descriptor-probe.log` でも eager open・tail probe が 3 件を返し、G4 が `invalidArchive` になることを確認した。

仕様 D3 の「ZIP 以外でも updater_preparation」という記述は、変更しない `prepareDeferredEditing` の `format == .zip` guard と両立しない。非 ZIP は背景の `baseValidation` と token の寿命を検査し、G4 の段を人工的には追加していない。

### 原因と修正

split の保存でも `savePendingDocument` は、`savePendingSplit` の reload が終わった後に
`disposePending()` と `displayAfterMutation()` を通る。後者は一覧と読み出し用 snapshot を先に用意し、
`loadingTask` の中で `prepareDeferredEditing` → `editor.install` → `editor.prepare` を行う。
一覧までで保存の completion が返るため、その直後には editor の base がまだ空の場合がある。
採用 reader が無い split でもこの準備は実行され、世代の不一致や準備の欠落ではなかった。

- `DeferredSplitSaveFixture.save()` は、completion の後に
  `waitForDeferredPreparationForTesting()` を待ってから既存の base / generation の assertion を行う。
- `testSplitSaveInstallsReloadedBaseAndQueuedEditWaitsForPreparation` は ZIP / 7z / tar.gz の split set で
  `.baseValidation` を止める。保存 completion と一覧表示は済み、base はまだ未設定であること、
  その間に開始した編集が待つこと、解除後に編集が成功して base 全体と baseGeneration が reload の
  snapshot と一致することを検査する。さらに次の保存で queued のフォルダも実際に書き込む。
- `testSplitSaveHelperWaitsForPreparationWithoutWindow` は、window の無い共通 helper の構成でも、
  ZIP / tar / tar.gz / tar.bz2 / tar.xz / 7z / LHA の保存と、続く変更なしの保存の両方で
  base 全体と baseGeneration の一致を確認する。
- 上の新規 split 試験だけは既存の `operations.coordinate` hook から callback を返す。
  実際の分割・公開・再読込は行うが、Foundation の file coordination 自体の試験ではない。
  これにより直接 runner でも背景準備を独立して確認できた。共通 fixture の coordination は変更していない。

indicator も同じ境界の違いだった。即時モードでは一覧表示の完了時、保存時モードでは背景準備の
`defer` で token が終了する。stage A の一覧が先に見える時点だけでは、保存時モードの準備は未完了。
`ImmediateOpeningTests.testExternalChangeRevertKeepsPreviousRowsUntilNewTreeInBothModes` は、
新しい行の表示を従来どおり確かめ、その後に準備を待って token が nil、indicator が非表示、
保存時モードの base / generation が新しい snapshot と一致することを検査する。

`testPublishedDisplayFinishesLoadingTokenInBothModesAndReloadPaths` では、即時 / 保存時の各モードで
採用 / 強制 fallback を走らせ、木の準備を止めて indicator を実際に表示する。
解除後、取得した token が無効になり、現在の token が nil、indicator が非表示になることを確認した。
既存の deferred post-save / revert / reload と準備失敗の試験も再実行した。
準備や token を終える production code の追加修正は必要なかった。
