## 実装と不変条件

- `ArchiveNameIndex` は名前が clean なときだけ作る。改名欄・予約の clean 判定を一か所に揃えた。
  hard link も占有表に含め、多重度を失わない。表現可能性の証明は別のフラグとした。
- session は `Mutex` に世代・形式を伴う索引を保持する。古い世代や、同じ世代の弱い証明で上書きしない。
  即時モードの改名欄の背景準備も同じ値を共有する。削除だけの計画は索引を新規作成しない。
- 即時の編集計画と mutate 内の検査に overlay を渡す。衝突解決の候補が占有されていなければ、
  `existingGroups` の全件走査を省く。既存の独立した GK の検査と P0 の公開前照合は残した。
- 公開後は旧 reader の生存 entry と新 reader を位置ごとに照合する。未変更名は UTF-8 byte と kind、
  改名・追加は clean 判定・key・kind を照合し、変更 entry を一件ずつ probe する。
  占有表には削除・最終改名・追加だけを適用する。照合不一致、rewrite、変更情報のない reload は索引を破棄する。
  追加順は即時の `plan.items`、保存の additions → folders のまま。
- S21 の内部 LHA / tar fallback を含む実際の公開 mode を `ArchiveVerifiedOutputSink.publishedMode` で渡す。
  分割保存は producer の `Result.mode` を pipeline の結果に引き継ぐ。
  ZIP の nonRelocatableEntry による rewrite も索引を破棄する。
- 保存時 install は世代・形式・件数・証明・hard link 不在を満たす索引を共有する。
  全件検査に戻った場合も、その成功した占有表を session に渡す。document の7か所を接続した。
- 保存前は同じ条件を満たすときだけ変更 entry を projection の順に検査する。
  位置は削除 index の二分探索と追加 offset で求め、全件の positions 辞書を作らない。
  clean でない基底、未証明、hard link、形式不一致は従来の全件検査。
- replay は既存の占有表を受け取り、使う index だけの key を memo にする。
  循環改名をほどく場合の全件走査と、Save As の全件検査は残した。
- 保存 probe は形式に依らず differential / install を要求し、plan_keys を禁止する。
  実際に rewriter を使った行だけ、保存後の全件検査を要求する。LHA・7z・ZIP password・分割の保存にも同じ helper を使う。

新しい設定・文言・永続形式・GK/KK API・concurrency の opt-out はない。
公開済みの `Documentation/releases/` は変更していない。

## S33 correction 1

2026-09-26。調査時の canonical HEAD は `ce96ec57c8be7876cbe9f308b6b8687ef9bae28d`。
上記の未 commit の S33 実装を保持したまま調査した。

利用者からのオーケストレータ実行報告（今回こちらで実行した結果ではない）:
固定 GK `6e7cd9b` / KK `0cbd809` の隔離配置・通常 Xcode test host・画面ロック解除で
build-for-testing 成功、focused 12 classes / 201 tests / 0 failures。
全件は 1,562 tests / 29 skipped / 3 failures（1 unexpected）。
`ImmediateOpeningTests` 単独11件でも
`testPostEditKeepsPreviousRowsThenDisplaysBeforeNewIndex` の `indexGate.isEntered` 待機が時間切れになった。

通常経路の原因は報告の解析と一致する。初回表示が作った索引を即時改名後の
`reloadAfterMutation(advancing:)` が次世代へ進め、`prepareRenameIndex` から呼ぶ
`prepareNameIndex(generation:)` はその値を返す。`.renameIndex` / `.renameIndexBuilt` のある
`buildNameIndex` に入らないため、元の試験の「編集後も必ず再構築する」という前提は AA3 と合わない。

最初に指定された再構築試験の作り方には相違があった。
`ArchiveSession.prepareNameIndex(generation:)` は DEBUG の
`nameIndexDisabledForTesting.get() == true` で直ちに `nil` を返す。
これは仕様 A2 の「立てると常に nil」と一致する。
`ArchiveWindowController.prepareRenameIndex` の即時モードの枝には、戻り値が nil の場合に
`EntryNode.buildRenameOccupancy` を呼ぶ fallback はない。
controller が prepared occupancy を得られない場合、`renameOccupancy` は `root.editOccupancy` を参照し、
それも nil なら `ArchiveRenameValidation.plan(for:)` の `ArchiveEditPlan.build` が全件を走査する。
この即時表示の木は `indexingEdits: false` なので、無効化フラグでは背景再構築ではなく全件走査の経路になる。
従って true が伝播すれば索引を作らず、伝播しなければ advance 済みの索引を返すので、
どちらでも要求された再構築の gate には入らない。
この相違を TaskLocal の伝播不良とみなして DEBUG hook を追加することはしなかった。

初回調査では製品・試験を変更する前に停止して報告した。
その後、同日の利用者の承認により、既存の `nameIndexChangeForTesting` で
`change.renamed = [:]` を注入し、公開後の位置照合で索引を破棄させる代案を適用した。
製品コード・DEBUG hook は追加変更していない。

変更した試験（`KaitoFinderTests/ImmediateOpeningTests.swift` のみ）:

- `testPostEditKeepsPreviousRowsThenDisplaysBeforeNewIndex` は元の二つの gate と順序を保持した。
  最初の表示と索引の準備後に改名差分を落とし、背景での木の構築中は旧行を保持して loading を表示する。
  その時点で注入された改名の index/name を確認し、旧世代・新世代の session 索引がともに nil、
  `name_index_build` が未記録であることを検査する。
  新しい行の表示後も索引の gate を解除するまで ready は false、占有表は nil。
  解除後は session と controller の占有表が `renamed.txt` に衝突し、`a.txt` には衝突しない。
  初回表示を除く改名操作の観測範囲で `name_index_build` が新世代について一回、
  `.renameIndex` / `.renameIndexBuilt` も各一回・off-main、表示が構築開始より先であることを検査する。
  差分注入・診断 observer は改名 Task 内の TaskLocal に束縛し、window controller の背景 Task まで
  observer が届いたことを gate と event/stage の件数で検査する。
