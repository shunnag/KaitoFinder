## 変更と不変条件

- D1: `begin` で `allowsStampRecheck && fileSystem == "apfs" && hazard == nil` を確定し、publication の `let` から transaction に渡す。
  `allowsStampRecheck` は既定 true、`didRecheckStamps` とも DEBUG に限らない注入点。
  transaction の既定は false。journal に保存せず、回復はこの近道を使わない。
- `validateNew` の最初の全文 hash は毎回残す。修正1では全巻の dev・ino・size・mtime（秒と ns）を hash 前にも採取し、
  hash 後の別の stat で記録した `newProof` と一致する場合だけ、reader 成功後の stamp の近道を使う。
  hash の最終 path 検査から証拠の stat までの間に stamp を変えた書き込みも、全文 hash に戻して照合する。
  通常ファイル・長さ・stamp・配置時 inode のいずれかが違えば、全巻の `validateHashes` に戻る。
  HFS+・FAT/exFAT・non-local・file-provider は全文 hash のまま。
  xattr の書き込みが変える ctime は比較しない。同じ inode・size への書き込みは mtime を更新する場合に検出する。
  writeback 前の `MAP_SHARED` store など mtime を更新しない書き込みと、mtime を ns まで意図して戻す書き込みは検出しない。
  独立した反証レビューの報告では、この機械の APFS で `msync` なしの store により `read()` の byte が変わり、
  `munmap`・close の2秒後も inode・size・mtime（ns）は同一だった。`pwrite` と `F_PUNCHHOLE` は stamp を更新した。
  これは既存の `newMatches` / `oldProof` および APFS の旧巻の照合と同じ信頼の範囲。
- D2: W の開き直しだけを除いた。`didProduceWork` は `produce` の直後に残す。
  W と同じ byte と証明された巻の reader に対し、S4 の既存 closure が同じ計画を照合する。
  不一致の拒否は S5 の前。失うのは切り出し前に止まる早さだけで、不正な W を切り出す書き込みと hash の費用が増えうる。
  計画との不一致の文言は維持する。W の reader open で発生した KaitoKit error の文言だけは、
  S4 の `stagedReaderFailed` を通じて汎用の「アーカイブの原本を確認できません。…」になる。新しい UI 文言はない。
- D3: `prepareDraft` は旧属性・旧世代・世代上限の拒否を切り出し前に行う。
  `finish` は切り出し後・`writeNative` 前に巻別 digest から metadata を完成させる。
  `split_metadata_digest` は `finish` 内の導出だけを計測する。metadata が journal に載る境界は `.prepared` のまま。
- D4: `ArchiveVolumeInput.copy` の SHA-256 の開始・更新・finalize は `usesHashes` のときだけ。
  fd・path・stamp の前後の照合と `verify` は維持。DEBUG の task-local `ArchiveTestCounters.splitInputHashes` で開始回数を数える。
- probe は `split_work_validation` を禁止し、その他の必須段・mode・TSV・fixture を維持。
  前段の diagnostics 試験には `allowsStampRecheck = false` を渡して全文 hash の経路を引き続き検査し、metadata の期待値を巻別 digest に更新した。

## 永続データの互換性

`totalSHA256` は巻の index 順に各 `sha256`（64桁の小文字16進）を32 byteへ戻して連結し、その SHA-256 を同じ書式で記録する。
不正な16進は `VolumePublishError.validationFailed`。W 全体を読む処理はない。

変わるのは意味だけ（旧版: W 全体の SHA-256、新版: 巻別 digest の列の SHA-256）。
JSON の key・型・桁数・文字の範囲を変えず、journal・Marker・Publication・Layout の schema を維持した。
`Publication.validate` は書式だけを検査し、`inspect` の mixed 判定が比べるのは setUUID・generation・count・index。
値そのものは内容の検証に使わない。新版が書いたセット・journal・store を旧版が受理でき、その逆も受理できる。
`NewVolume.sha256` は従来どおり必須で、内容の証明を担う。

## 修正1（独立した反証レビュー後）

オーケストレータからの報告では、修正前のP12-1はhostのbuildが成功し、SplitSavePassTestsを含む
指定16クラスの251件が失敗0・skip 0で完了した（hostではhdiutilも動作）。独立した反証レビューにblockerはなかった。
これは上のsandbox実行と区別し、この修正後のhost再検証の代わりにはしない。

修正内容:

- stampが証明できる範囲を訂正した。検出できるのはstampを変える書き込み。
  同じinode・sizeでmtimeを更新しないwriteback前のMAP_SHARED store、またはmtimeを意図して戻す書き込みは検出しない。
  レビューで報告された「msyncなしのstoreがread()のbyteを変え、munmap・closeの2秒後もstampが同じ」というAPFSの観測を明記した。
  pwrite / F_PUNCHHOLEがstampを変えたという観測と区別し、oldProof / newMatches / APFS旧巻の照合と同じ信頼の範囲とした。
  mmap / F_PUNCHHOLEの実験は今回Codexでは再実行していない。
- 別名保存の入力連結ではSHA-256を計算しない説明に訂正。計算するのはusesHashesが真の置換だけ。
- 公開済み0.3.0のrelease notesはオーケストレータによる復元を維持し、文面を本記録の「release notes に書くこと」へ移した。
