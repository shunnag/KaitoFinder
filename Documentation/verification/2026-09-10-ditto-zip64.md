# 検証: ditto は 4 GiB 超の ZIP を ZIP64 なしで壊す(2026-09-10)

## 背景

書庫内編集(削除・改名・追加)では、生き残る entry の local record を
そのままバイト列で運ぶ。bit 3 が立っている entry では payload の後ろに
data descriptor が続くので、その終端を

```
descriptor 位置 = localHeaderOffset + 30 + nameLen + extraLen + CD.compressedSize
```

と算術で求めることになる。ここで `CD.compressedSize` が真値でないと、
この式は deflate stream の**途中**を指す。編集のたびに静かに壊れる。

macOS の Finder「圧縮」は `ditto -c -k` であり、deflate entry すべてに bit 3 を
立てる。4 GiB を超える entry でこの式が成り立つかを実測した。

## 方法

非圧縮の 5 GiB(`/dev/urandom` 由来、5,369,757,696 bytes)を `ditto -c -k` し、
EOCD・ZIP64 EOCD・central directory・data descriptor を直接読んだ。
環境は macOS 27.0 (26A5425a) / Apple Silicon。

## 結果: ZIP64 が一切書かれず、3 つの値がすべて mod 2^32 で切られる

```
file size               : 5,371,395,834
ZIP64 EOCD locator      : ABSENT          <-- ZIP64 構造が無い
EOCD entries            : 1
EOCD.cdOffset           : 1,076,428,455
真の central directory  : 5,371,395,751
                          5,371,395,751 mod 2^32 = 1,076,428,455  ← 一致
```

central directory record も同じく切られている。

```
flags                   : 0x0008  (bit 3 data descriptor = true, bit 11 UTF-8 = false)
method                  : 8 (deflate)
uncompressed size (32)  : 1,074,790,400
  真値 5,369,757,696 mod 2^32 = 1,074,790,400  ← 一致
compressed size (32)    : 1,076,428,390
  真値 5,371,395,686 mod 2^32 = 1,076,428,390  ← 一致
```

data descriptor も **16 byte の非 ZIP64 形式**で、中身も切られている。

```
504b0708 edbbf4bf 66fe2840 00001040
signature crc      csize     usize
                   =1,076,428,390  =1,074,790,400
```

つまり **uncompressed size、compressed size、EOCD の central directory offset の
3 つすべてが mod 2^32 で切られ、ZIP64 は一切書かれない**。

## 結果: 算術による descriptor 探索は本当に壊れる

```
naive な descriptor 位置 = 49 + 1,076,428,390 = 1,076,428,439
  そこにある byte : de802428c7608379   ← deflate stream の途中
実際の descriptor 位置   = 49 + 5,371,395,686 = 5,371,395,735
  そこにある byte : 504b0708...        ← 正しい signature
```

危惧は現実だった。この書庫を素朴な式で編集すると必ず壊れる。

## 結果: 読み手の反応はばらばら

| 読み手 | 挙動 |
|---|---|
| `unzip -l` | 切られた 1,074,790,400 をそのまま表示。警告なし |
| KaitoKit | 同上。切られた値をそのまま返す |
| `7zz l` | 真の compressed size 5,371,395,686 を復元するが Warnings 1 / Errors 1 |
| `ditto -x` | 自分が書いたものは正しく展開できる(byte 一致を確認) |

`ditto` はサイズを見ずに deflate stream を最後まで流しているので往復する。
サイズを信じる実装だけが壊れる。

## 門番: EOCD.cdOffset が本物の signature を指すか

切られた書庫は、EOCD が申告する central directory offset が
`PK\x01\x02` を指さない。これが安く確実な判定になる。

```
big.zip     : EOCD.cdOffset=1,076,428,455  そこの byte=8397bb05  valid=False
withdirs.zip: EOCD.cdOffset=415            そこの byte=504b0102  valid=True
```

## 設計への反映

- **編集の門番を 3 つにする。** SFX prefix 付き ZIP、EOCD の後ろに trailing data の
  ある ZIP に加えて、**EOCD.cdOffset が `PK\x01\x02` を指さない ZIP** も編集しない。
  読み取りは従来どおり行い、UI では read-only である理由を言う
  (「この ZIP は 4 GiB 超の項目を ZIP64 なしで格納しており、安全に変更できません」)。
- 逃げ道は §7.4 と同じ**変換**。中身を取り出して ZIP64 付きで書き直せば編集できる。
- KaitoFinder 自身の writer は、4 GiB を跨ぐ値に必ず ZIP64 を書く。
- 進捗表示と buffer 事前確保は、申告サイズが 4 GiB の倍数だけ間違いうる前提で組む。

> **Verification: ditto writes a broken ZIP above 4 GiB (2026-09-10)**
>
> In-archive editing copies each surviving entry's local record verbatim, and for
> an entry with general-purpose bit 3 set, the trailing data descriptor is located
> arithmetically as `localHeaderOffset + 30 + nameLen + extraLen +
> CD.compressedSize`. macOS Finder's Compress is `ditto -c -k`, which sets bit 3
> on every deflated entry, so this was measured on a 5 GiB incompressible file.
>
> **ditto writes no ZIP64 structure at all**, and truncates three values mod 2^32:
> the uncompressed size (5,369,757,696 → 1,074,790,400), the compressed size
> (5,371,395,686 → 1,076,428,390) and the EOCD's central-directory offset
> (5,371,395,751 → 1,076,428,455). The data descriptor is the 16-byte non-ZIP64
> form and carries the truncated values too.
>
> The danger is real, not theoretical: the naive arithmetic lands at offset
> 1,076,428,439, in the middle of the deflate stream, where the real descriptor is
> at 5,371,395,735. Editing such an archive would silently corrupt it.
>
> Readers disagree. `unzip -l` and KaitoKit report the truncated size with no
> warning; `7zz l` reconstructs the true compressed size but reports one warning
> and one error; `ditto -x` round-trips its own output byte-for-byte because it
> streams the deflate rather than trusting the sizes.
>
> **The guard is cheap**: in a truncated archive the EOCD's declared
> central-directory offset does not point at a `PK\x01\x02` signature — measured
> `8397bb05` for the 5 GiB archive against a correct `504b0102` for a normal one.
> KaitoFinder therefore refuses to edit such archives (alongside SFX-prefixed ZIPs
> and ZIPs with trailing data after the EOCD), keeps reading them as before, says
> why in the UI, and offers conversion as the escape hatch. Its own writer always
> emits ZIP64 once a value crosses 4 GiB, and its progress and buffer sizing
> assume a declared size may be wrong by a multiple of 4 GiB.
