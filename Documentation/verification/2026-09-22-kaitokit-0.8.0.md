# KaitoKit 0.8.0 への追従 — 2026-09-22

## 対象と変更

KaitoFinder `release/0.2.0` を 0.2.0 / build 3 へ更新した。参照先は兄弟 checkout の
KaitoKit `release/0.8.1`（0.8.0 + レビュー修正 R1〜R14）と GyoshukuKit `release/0.4.2`。
兄弟 checkout は読み取りのみ。commit / push、LaunchServices 登録、UI 結合テストは行っていない。

- `ArchiveFormat` の追加 12 case を表示名・文書型・展開サービスへ接続した。
- 初回対応では文書型は 33 件、識別子の集合は 37 件（末尾の ARJ / MSI 追補で 39 件へ更新）。新規自前 import は依頼の列挙に従い **8 件**
  （UDF、WIM、MSI、CHM、ARJ、lzip、Brotli、pbzx）。「6 つ」という表題ではなく列挙された全識別子を採用した。
- DMG と旧 Mac 3 形式は CoreTypes の識別子を参照し、import を追加しない。
  Office / Outlook の拡張子、追加の `.bin` import、拡張子のない Payload の関連付けは追加しない。
  `tlz` は既存の LZMA import に残す。
- 表示名の `lzip` は依頼された小文字表記を採用した。参照 checkout の compat 実装は
  `KaitoArchive.swift:509` で `Lzip` を返すため、この一語は指定値を優先している。
- 展開サービスは文書型の全識別子と一致。一括展開パネルは
  `ArchiveBatchExtractionController.swift:21–35`、ようこそのドロップは
  `WelcomeDropZoneView.swift:30,235` で既に同じ宣言を参照しており、別一覧の修正は不要だった。
- ZIP の Shrink / Reduce 1〜4 / Implode、7z の Zstandard をプレビュー・オープンの許可方式へ追加した。
  ZIP method 7 は引き続き拒否する。
- `.tar.lz` / `.tar.br` は展開できるが編集できない。`ArchiveCapabilities` の拒否名を外側の形式に合わせた。
- README、設計 §5.5、圧縮形式ロードマップ、更新配信の 0.2.0 用の例、リリースノートを更新した。

## AppleDouble の一覧と編集 index

`ReaderOptions.kaitoFinder(password:)` は `appleDoublePolicy: .expose` を使う。
`.merge` は sidecar を除去し resource fork を擬似 entry にして index を詰め直すため、
GyoshukuKit の `.expose` の一覧との間で削除 index と entry 数が一致しなくなる。
全アプリの `ArchiveReader.open` がこの factory を使うことも検索で確認した。
GyoshukuKit の根拠は `ArchiveUpdater.swift:79,182`、`ArchiveRewriter.swift:85`。

`appledouble/finder.zip.b64` は 12 entry。`folder/plain.txt` は原本の index 10 で、
sidecar の後にある。追加したテストではアプリと KaitoKit `.expose` の全 entry を比較し、
`__MACOSX/folder/._rsrc.txt` の存在、`..namedfork` の不在、`mode == .inPlace` と refusal nil を検査する。
その後 `folder/plain.txt` だけを削除・保存し、独立した `.expose` reader で残る 11 entry の順序と
全ファイルの内容が一致することを検査する。**このアプリ経由の XCTest は下記の sandbox 制約により未実行**。

fixture の原本 SHA-256 は `0a7dfb5c9865a4d3ec8441bcf974d6c7d9955bdc92cc30b89accc2e6a6e24599`。
`SHA256SUMS` と Python の ZIP 一覧で上記の原本・項目位置を確認した。

- WIM solid / LZMS は `WIM/WIMStructures.swift:118–119` と `WIMReader.swift:42` により一覧前に拒否される。
  `stored.wim` の version / compression flag の変異 2 件で境界を検査する。
- DMG ADC は `DMG/UDIFImage.swift:255–258` で chunk を読む際に拒否される。
  `hfs-adc.dmg.gz` は一覧の解析中に拒否される。個々の file の chunk type は公開 entry にない。
- tar の旧 GNU `S` 型は `Tar/TarReader.swift:185–186`、star sparse は `:192,1090–1096` で

- WIM の chunk size、UDIF の chunk の制限など、entry の公開情報から判断できない条件は読み取り時の報告に委ねる。
- CFB と Mac wrapper に、追加すべき「一覧済みの通常 file の未対応方式」規則はなかった。
  AppleDouble merge の reopen 制限は `.expose` では通らない。

7z の追加許可値の根拠は `SevenZip/SevenZipFolderPipeline.swift:638` の `Zstandard`。
ZIP の旧 method 名は `ZIP/ZipReader.swift:2293–2308`。

## export 後の ARJ / MSI 型不一致への追補（2026-09-22）

オーケストレータの報告では、`3500ca7` の変更を含む export した 0.2.0 の app を引数付きで起動すると、
`.arj` / `.msi` だけが開けず、ようこそウインドウと `NSDocumentController` の型不一致アラートが出た。
`.chm` / `.wim` / `.dmg` / `.lz` / `.zip` は書庫ウインドウが開いた。

同じ Mac で `UTType.types(tag:tagClass:)` の `.filenameExtension` による解決先を確認した結果、
他アプリの exported 型が自前の imported 型より優先され、既存の `LSItemContentTypes` のどれにも一致・準拠していなかった。
既存の `.txz` / `.zipx` / `.deb` と同じ方式で、次の二識別子をそれぞれの `LSItemContentTypes` に追加した。

| 拡張子 | 文書型 | 追加した識別子 |
|---|---|---|
| `arj` | ARJ | `cx.c3.arj-archive` |
| `msi` | Compound File | `com.microsoft.msi-installer` |

自前識別子は残し、追加した二識別子を `UTImportedTypeDeclarations` にも宣言した。
他アプリがない Mac でも意味を持つよう、準拠先は `public.data` / `public.archive`、
拡張子は表のとおり、説明は文書型と同じ ARJ / Compound File とした。
展開サービスの `NSSendFileTypes` も全文書型の識別子の集合へ揃えた。
`DocumentTypesTests` の識別子・import 拡張子の期待値と、文書型ごとの別識別子の検査を更新し、
`documents.count == expected.count` の検査は維持した。設計 §5.5 と README の記述も揃えた。
同じ Mac で動的な型に解決される `udf` / `wim` / `swm` / `chm` / `lz` / `br` / `tbr` / `pbzx` は変更していない。

今回の実行結果:

- `plutil -lint KaitoFinder/Info.plist`: **OK**。
