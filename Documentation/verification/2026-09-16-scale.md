# 大規模アーカイブの実測 — 2026-09-16

## 結果

オーケストレータが 2026-09-16 に開発用 Mac(Apple Silicon)の Release ビルドで測定した。
KaitoKit PR #28(`fix/zip-first-candidate-budget`)を反映した状態で、10 万件は約 1.3 s / 232 MB、
50 万件は約 4.2 s / 924 MB で文書ウインドウが現れた(時間はウインドウ出現まで、メモリは dirty footprint)。
100 万件は KaitoKit の保持メタデータの合計上限 `maxTotalMetadataSize`(256 MiB)で拒否された。

解析中もメインスレッドは応答していた。メモリは件数にほぼ比例し、1 件あたり約 1.85 KB。
今回は実測の記録であり、メモリの最適化や表示の改善は行っていない。

## 方法

- Python の `zipfile` で ZIP64 を作成した。パスは `dNNN/sN/tN/fNNNNNNN.txt` のように短く、
  本文は 1 byte、圧縮方式は stored。10 万件のアーカイブだけは 3 行の本文を deflate で圧縮した。
- 中央ディレクトリのサイズは、10 万件が 6.9 MiB、50 万件が 31.9 MiB、100 万件が 65.8 MiB。
- 各測定前に `osascript` で KaitoFinder を正常終了させてから、
  `open -a KaitoFinder.app <zip>` で対象を開いた。`<zip>` は測定するアーカイブのパス。
  **以前の文書のウインドウ復元が混ざった先行測定が一度あったため、正常終了を挟み、
  復元による影響が混ざらない条件で測定した。**
- ウインドウの出現は `CGWindowListCopyWindowInfo` のウインドウ数で確認し、
  メモリは `ps` の RSS と `footprint`、ヒープの内訳は `heap -s` で測った。
- メインスレッドの応答性は、解析中に Apple Event
  (`tell application "KaitoFinder" to get name`)を送り、返答までの時間で確認した。

## 所見

### メモリ

メモリは 1 件あたり約 1.85 KB でほぼ線形に増える。10 万件での `heap -s` の主な内訳は次のとおり。
ヒープ全体は約 184 MB だった。

| 保持しているもの | サイズ | 1 件あたり |
|---|---|---|
| 各 entry の `formatSpecific` 辞書(`[String: String]`) | 38.4 MB | 384 B |
| `[ArchiveEntry]` のストレージ | 34.4 MB | 344 B |
| `EntryNode` | 25.9 MB | 256 B |
| ZipReader のレコード | 14.7 MB | — |
| 文字列 | 12.8 MB | — |

最大の単一項目は entry ごとの `formatSpecific` 辞書だった。内訳を記録した段階で、最適化は未実施。

### 解析中の応答性

50 万件を開いて CPU が約 100 % の間に、次の Apple Event 応答時間を測定した。

| 開き始めてからの送信時刻 | 返答まで |
|---|---|
| 1.0 s | 0.09 s |
| 2.1 s | 0.14 s |
| 3.2 s | 0.05 s |

メインスレッドは解析中も応答する。文書ウインドウは解析終了時に現れ、
それまでは仮のウインドウや進捗ウインドウは出ない。

### KaitoKit の上限と PR #28

PR #28(`fix/zip-first-candidate-budget`)の前は、50 万件のアーカイブが
「読み込みの上限を超えました: ZIP end-record candidate metadata work」で拒否された。
EOCD の候補再試行予算は `2 × maxMetadataSize` = 32 MiB で、最初の候補にも
16 MiB の ZIP64 locator 探索を含めて計上していた。さらに中央ディレクトリ自体にも
`maxMetadataSize`(16 MiB)を上限として適用しており、`maxEntryCount = 1,000,000` と矛盾していた。

PR #28 は中央ディレクトリの上限を `maxTotalMetadataSize`(256 MiB)にし、
最初の候補を再試行予算から除外した。悪意のある入力に対する上限は維持している。
約 25 万件を超えるアーカイブの読み込みはこの修正に依存する。
オーケストレータによる KaitoKit の `swift test` は 1,142 件、スキップ 45 件、失敗 0 件。
`kaito list` は 10 万件で 1.3 s、50 万件で 6.1 s だった。

100 万件では保持メタデータが 1 件 268 B、合計 268 MB となり、
`maxTotalMetadataSize`(256 MiB)によって拒否された。
既定の制限での実用上限は、短い名前の entry で約 95 万件。

## 未対応

- entry ごとの辞書や配列、ツリーなどのメモリ削減は行っていない。
- 約 20 万件を超えるアーカイブでは、解析が終わるまでの仮のウインドウや進捗表示を
  後から追加すると待機中の状態が分かりやすくなる。現状は解析終了後に文書ウインドウが出る。
- エラー表示は当時「読み込みの上限を超えました: ZIP end-record candidate metadata work」のように、
  日本語の文の中へ KaitoKit 内部の英語の理由文字列をそのまま埋め込んでいた。同日、
  「アーカイブが大きすぎるか複雑すぎるため、読み込みの上限を超えました(ZIP end-record candidate metadata work)」
  に改め、原因を先に述べて識別子は診断用に括弧で残す形にした(26 言語)。
