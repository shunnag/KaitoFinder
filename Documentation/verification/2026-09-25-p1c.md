# P1c: 暗号化 entry の並列検証

2026-09-25 / `feature/2026-09-24-review`。KaitoFinder のみ変更。両 sibling の編集・コミットは行っていない。

## 実装

- `ArchiveSession.verify` の CRC / HMAC まで読む処理を `ArchivePasswordVerification` に移した。
  元の actor を保持した同期処理のまま、連続する書庫順の batch を GCD worker に配る。
  各 worker は事前に直列で作った専用の `reader.reopen()` と 128 KiB buffer を所有する。
  reader は `Mutex` 内に閉じ込め、`@unchecked Sendable` は追加していない。
- W は `writerOptions(...).compressionThreads` を優先する。未指定時は現行 writer と同じ
  CPU 数・8・物理メモリ GiB の最小値、最低 1。実際の worker 数は entry 数以下。
  現行の通常環境では `min(activeProcessorCount, 8)`。P9 が writerOptions に設定を渡せば検証にも反映される。
- **件数 < 64 かつ合計本文 < 8 MiB** は直列。どちらかの閾値を満たせば並列候補になる。
  本文サイズだけで直列に戻すと、対象の 100k / 500k 個の 1-byte AES が並列にならないため。
  鍵が未入力、不明サイズ、solid group を含む入力も直列に保つ。reopen 失敗時は元 reader の直列検証に戻す。
- worker ごとの entry の結果を保存し、batch と entry の書庫順に集約する。
  wrongPassword は従来どおり最後にまとめて、部分成功があれば既存の「異なるパスワード」拒否、
  成功がなければ `KaitoError.wrongPassword`。それ以外のエラーは直列処理で最初に出るものを返す。
  失敗・取消しでは session の検証済み集合を更新しない。
- 並列化には reader の既知の password が必要で、各 worker でも assert する。
  パスワード入力・再入力は従来の session / MainActor 経路で直列に行い、候補を受け取ってから並列検証する。
- Task の取消しを待機側から最大 10 ms 間隔で worker に伝える。
  Progress は entry 開始前・各 128 KiB 読み取り境界で確認する。全 worker の終了後に戻る。
  即時編集、保存待ちの編集、保存、展開、promise、保留中 entry の読み出し、変換、パスワード編集前の
  呼び出し元にある Progress を検証へ渡す。
- DEBUG の `password_verification` span は従来の編集前検証全体を囲んだまま。
  `passwordVerificationBytes` は各 worker が実際に受け取った byte 数を最後に Mutex で加算する。
  失敗・取消しで既に他 worker が読んだ byte も含むため、その場合の値は直列と同じとは限らない。
  payload 用 buffer は W × 128 KiB。entry ごとの outcome と返却用集合は O(entry 数) のメタデータ。

DEBUG の比較スイッチは TaskLocal の
`ArchivePasswordVerification.execution.withValue(.serial)` / `.withValue(.parallel)`。
既定は `.automatic`。`.parallel` は小入力の閾値を外すが、既知の鍵・サイズ・solid の条件と W は維持する。
`observer` も TaskLocal で、テストが worker 数・読み取り・取消しの境界を観測する。Release には含まれない。

## 検証結果

アプリ全 Swift source とテスト全 Swift source を Swift 6 / DEBUG / MainActor default isolation で
直接コンパイルして成功。アプリの Release 全 source の型検査も成功。
テストの型検査には既存の 2 件の警告がある。最終テスト bundle の全モジュールコンパイルでは、
未変更の `ArchiveImportSafetyTests.swift:64` にも Sendable 関連の警告が 2 件出る。P1c の追加・変更箇所に警告はない。
依存は既存の `build/P1BVerification` の実ライブラリ（KaitoKit `ba42ed8`、GyoshukuKit `e907e1d`）。
兄弟リポジトリが並行作業中のため、この固定済みビルドを使い、依存を書き換えずに検証した。
アプリホストを使う通常の XCTest 実行ではなく、Xcode 付属の `xctest` から直接実行した。

| 対象 | 成功 | 失敗 | 範囲 |

| ArchivePasswordVerificationTests | 11 | 0 | 新規全件 |
| ArchivePasswordTests | 16 | 0 | session / 読み出し等の選択実行 |

| ArchiveBatchExtractionTests | 30 | 0 | 全件 |

新規試験で確認した内容:

- AES / ZipCrypto の直列・強制並列・自動実行の集合、成功時の byte 数、既知の鍵で provider が呼ばれないこと。
- 混在パスワードを両方の鍵で検証、全件誤り、中央 entry の HMAC / CRC 破損。
- 先行する wrongPassword と後方の異なる未対応方式 2 件があっても、書庫順で最初の typed error を返すこと。
- 63 / 64 件、8 MiB、W の下限、未入力の鍵の直列経路。
- Progress と Task の途中取消し、編集・展開前の取消しによる原本・出力先の不変。
- 既存の部分検証集合の維持、成功後の再検証省略、writer 指定の W=3、stage の完了通知。
- 必須入力 → 誤った候補 → 正しい候補の順に prompt が直列で呼ばれ、候補は W=4 で検証されること。

最初の新規試験実行では Task 取消しの試験用 semaphore を chunk ごとに待ってしまい、
試験自身の 3 秒の待機で時間検査が失敗した。最初の chunk だけを止めるよう直し、新規全 11 件が通過した。

クラス全体の実行も試みたが、ArchivePasswordTests は
`testCancelHeaderPromptKeepsCleanLockedDocumentAndUnlockButtonCanRetry` で HIServices の接続エラー後に signal 5、
ArchivePasswordEditingTests は `testMenuPlacementAndValidationForPlainKnownUnknownLockedTarAndRAR` で
`freed pointer was not the last allocation` により signal 6 で停止した。
既存の P1B 実行記録にも同じ停止がある。選択実行の一覧と未完了ケースは下記 JSON に残した。
