# 暗号化書庫の実測(2026-09-10)

M4 の第一段。設計の前提を実装前に確かめ、実装が主張する安全性の性質を
実装後に確かめた。

## 1. 入力を求める瞬間は二つある(実装前に確認)

KaitoKit を直接叩いて 4 形式の挙動を測った。

| 書庫 | 無パスワード open | 無パスワード read | 正パスワード | 誤パスワード |
|---|---|---|---|---|
| ZIP 従来型 PKWARE | 2 項目(一覧可) | `passwordRequired` | 復号成功 | `wrongPassword` |
| ZIP WinZip AES-256 | 2 項目(一覧可) | `passwordRequired` | 復号成功 | `wrongPassword` |
| 7z 本体のみ暗号化 | 2 項目(一覧可) | `passwordRequired` | 復号成功 | `wrongPassword` |
| 7z `-mhe=on` | **open 自体が失敗** | — | 復号成功 | `wrongPassword` |

上三つは一覧できて初回読み取り時に要求する。`-mhe=on` だけは開く時点で
要求する。しかもその open は `ArchiveDocument.read(from:ofType:)` の中で、
`nonisolated` かつ AppKit の並行読み込み経路なので **UI を出せない**。
`.locked(URL)` 状態を経由する設計はこのために要る。ここが違っていれば
設計ごと不要だった。

`passwordRequired` と `wrongPassword` が明確に分かれることも確認した。
「入力を求める」と「誤りを伝えて再入力させる」を出し分けられる。

## 2. ZipCrypto の照合値だけでは誤った鍵を弾けない(実装後に確認)

実装のコメントが

> ZipCrypto の短い照合値だけでは誤った鍵を除外できない。CRC / HMAC まで読む。

と主張している。安全性に直結するので実測した。誤ったパスワードを 4000 個
試し、`stream()` が開けるか(照合値の通過)と、`readAll()` まで到達するか
(CRC の通過)を分けて数えた。

```
試行 4000
  照合値の段階で落ちた             : 3985
  照合値を通過した(stream が開けた) : 15  例: ["wrong-57", "wrong-431", "wrong-650", ...]
  最後まで読めた(=誤受理)           : 0
```

**15/4000 ≒ 1/267** が照合値を通過する。ZipCrypto の照合値は 1 byte なので
理論値 1/256 とほぼ一致する。`stream()` が開けたことをもって「パスワードが
正しい」と判定する実装は、**約 0.4% の確率で誤ったパスワードを受け入れる**。

CRC まで読めば 15 個すべて落ち、誤受理は 0 だった。実装の対処は必要かつ十分。

## 3. 設計上そうした点

`PasswordProvider` は使わない。KaitoKit の同期 `Sendable` コールバックで、
復号中の任意スレッドから呼ばれる。ここで入力を求めると背景スレッドを
メインのモーダルで塞ぐことになり、取り消しもできず「キャンセル」と
「拒否」の区別もつかない。`ReaderOptions.password` だけを使い、再試行は
操作の境界に置く。UI はメイン、復号は背景、塞ぐ橋を作らない。

`reopen()` は `reopenedOptions.password = password` で options と
パスワードを自前で引き継ぐことを確認済み。展開経路の再配管は要らない。
一方 `reloadAfterMutation` は URL から開き直すので、ここには明示的に渡す
必要がある。書き換えは毎回 inode を差し替えるため、渡さないと
「追加した後に暗号化項目を展開できない」が静かに壊れる。
