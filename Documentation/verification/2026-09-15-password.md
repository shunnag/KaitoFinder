# パスワード保護 UI 検証 — 2026-09-15

## 結果

Wave C の保存時の暗号化、開いたアーカイブのパスワード設定・変更・削除、既知の鍵を使う編集を実装した。
暗号化関連の **46 テストは成功**。保存アクセサリと三シートの **10 言語・190 描画ではみ出し 0 件**を確認した。
ユーザーのシェルでは build が成功し、全件実行の順序依存の失敗もテスト用ウインドウの
アニメーションを起動時に無効化することで **563 件・失敗 0** になった（追補前のユーザー検証、詳細は後述）。
このエージェントの標準の `xcodebuild build` / `test` は sandbox で依存解決が拒否され、完走していない。
補助実行した既存 Undo テストには、変更前の HEAD でも再現する失敗が 3 件ある。全件成功とは扱わない。

KaitoKit / GyoshukuKit は変更していない。追補の Xcode プロジェクト変更はテストターゲットの
Debug / Release に principal class を指定する 2 行のみ。既存の未コミット変更を保持し、コミットも行っていない。

## 実装

- 新規作成、Finder の圧縮サービス、ドロップ変換、別名で保存の共通保存パネルに暗号化行を追加。
  ZIP は AES-256 / ZipCrypto、7z はファイル名の暗号化を選べる。
  tar / tar.gz / LHA は無効表示と理由を出し、形式変更でも入力値を保持する。
  空欄・不一致は `NSOpenSavePanelDelegate.panel(_:validate:)` で拒否する。
- 設定・変更シートは解除シートとレイアウト規則を共有し、空欄・不一致を欄下に表示する。
  確定ボタンは一致するまで無効。変更では古いパスワードを再入力させない。
  削除は対象名と非暗号化で書き直す説明を出す。
- 三操作は `ArchiveDocument.updatePassword` から既存の公開境界へ入り、
  `.rewrite(format)` と空の mutate クロージャで全項目を再出力する。
  入力の鍵と出力の鍵を分離し、公開成功後に session の鍵・一覧・capabilities を更新する。
  取消し、identity 照合、quarantine / xattr の保持、進捗、Undo の退避は既存の経路を共用する。
- 通常編集では設定スナップショットに session の鍵を重ねる。
  ZIP は既存 record をそのまま保持し、追加項目を同じ鍵で暗号化する。
  既存の暗号化項目がすべて ZipCrypto なら追加も ZipCrypto、それ以外は AES-256。
  7z は鍵とファイル名の保護を維持して全体を書き直す。
  不明な鍵は新しい拒否文言で止め、既知の候補も編集前に CRC / HMAC まで検証する。
- Undo スロットには原本に対応する暗号化設定をメモリ内で保持し、Undo / Redo で byte と鍵を一緒に戻す。
  設定・変更・削除は専用の取り消し名を使う。古い記憶済みの鍵を次の open に使い続けない。
- 暗号化された別名保存・変換は、現在の鍵を両欄に入れて暗号化を初期選択する。
  出力の鍵で新しい backing session を開く。暗号化を解除したコピーも選べる。
- カタログの新規 27 キーを含む全 284 キーに、en / ja / de / fr / es / it / pt-BR /
  zh-Hans / zh-Hant / ko の翻訳を用意した。古い編集拒否文言は 10 言語すべて廃止した。

## 追補：テストプロセスのウインドウアニメーション

ユーザーのシェルでの初回検証は build 成功、全 562 件中 1 件失敗。
`ScenarioNestedTests.testOpenInnerArchiveShowsTemporaryCopyRefusalAndOuterCloseRemovesIt` は単独では成功した。
`sample` / lldb によるユーザーの調査で、表示されないテスト用ウインドウのシート表示
（`ExtractionProgressSheet.begin`、アラート）と文書の close が開始する `_NSWindowTransformAnimation` の
`-[NSAnimation _runBlocking]` が終了せず、GCD ワーカーを占有し続けることが判明した。
`task_threads` は 9 → 96、うち 80 スレッドがその待機だった。ワーカープールの枯渇により
`NSDocumentController Coordination` の `NSOperationQueue` は ready のまま実行を開始できず、
内包書庫を開く `openDocument(withContentsOf:)` がタイムアウトした。

ユーザーがテスト起動時に `NSAutomaticWindowAnimationsEnabled = false` を揮発性の登録ドメインへ
登録すると、スレッド数は 23 以下に収まり、全件実行は **563 件・失敗 0** になった。
Wave C の追加テストが既存のテスト基盤のリークを閾値まで進めたもので、今回の追補でこの対策を恒久化した。
`Support/TestProcessSetup.swift` の `NSObject` サブクラスを、生成するテスト用 Info.plist の
`NSPrincipalClass = KaitoFinderTests.TestProcessSetup` に指定する。XCTest がテスト開始前に生成し、
`override init()` が `UserDefaults.standard.register(defaults:)` を呼ぶ。アプリの保存済み設定は変更しない。
原因を日本語コメントにも残した。

`Support/ZZProcessHealthTests.swift` は標準の名前順で最後に実行される。登録ドメインと有効値を確認し、
`task_threads` を一度だけ取得して **48 を超えたら失敗**させる。失敗文には `TestProcessSetup.swift` の
コメントへの案内を入れ、取得した各 Mach ポートの送信権と配列は `defer` で解放する。

追補を含む全 XCTest ソースの補助コンパイルは成功した。一時 framework で暗号化編集 11 件の後に
回帰検査を実行し、**12 件・失敗 0**。さらに、本番のテストターゲットから生成設定を取り出し、
追加した Support 2 ファイルだけの一時 Xcode プロジェクトを `/private/tmp` に作成した。
Debug / Release とも `build-for-testing`、生成 Info.plist の principal class 値、生成バンドルでの回帰検査が成功した。
この検査は principal class の自動生成・初期化の確認であり、アプリの全件実行の代わりとはしていない。
追補後の標準 `xcodebuild test` は依存解決時に終了コード 74 となり、上記と同じ sandbox の制約で完走しなかった。
この制約を回避するためのリポジトリ内のプロジェクト設定変更は行っていない。


## 描画と保存パネルの制約

保存パネル本体は XPC の `ClientCallsAuxiliary` / `HostCallsAuxiliary` 接続が拒否され、
補助ホストが終了コード 69 で終了した。保存パネルを生成して delegate を直接呼ぶ 2 テストと、
保存パネルを経由する Save As の統合テストは追加・型検査済みだが、この環境では実行確認できていない。
保存パネルを使わない作成・変換・backing session 切り替えは上記の実テストで確認した。

描画監査は本番の `makeAccessoryView` を直接構築して実行した。
保存アクセサリは 10 言語 × 5 形式 = 50 枚、設定・変更・削除シートは 140 枚、合計 **190 枚**。
長い ZipCrypto 表記を選択し、空欄・不一致・一致、長い対象名を描画した。
初回の監査で検出した NSTextField の alignment rect による左右 2 pt のはみ出しを修正し、
再実行では `UISnapshot.overflowViolations` の違反は 0 件。形式切替時の高さと入力値の保持も確認した。
日本語の保存アクセサリ、ドイツ語の保存・変更シート、フランス語の削除シートは PNG を目視確認した。

PNG は `/private/tmp/kf-password-snapshots` に保存した。補助ホストでは LaunchServices の
`kLSDataUnavailableErr` により XCTest 添付のエンコードに警告が出るが、PNG の書き出し・描画監査は成功している。
実際の保存パネル内での配置、Finder サービス、アーカイブユーティリティとの互換性は
[手動確認 §3](../manual-verification.md#3-暗号化書庫) に手順を追加した。
