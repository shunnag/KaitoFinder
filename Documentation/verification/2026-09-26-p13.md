## 実装と範囲

- `ExtractionPath.NameSyntax` は KaitoKit の `.tar`、GyoshukuKit の tar 系だけを `.posix` にする。
  圧縮された tar も reader の format が `.tar` なので同じ規則を使う。
  ZIP・cpio・ar・xar・ISO などは `.portable` のまま。リスク項目1には広げていない。
- NUL → 先頭 `/` の除去 → portable の drive 除去 → 構文別の分割 → `..` の拒否 →
  posix の backslash 片の `..` 拒否 → `.` の除去、の順。
  backslash の片は UTF-8 byte で比較し、出力先の検査でも同じ述語を使う。
- 通常の展開、promise の親、並列 worker の3か所だけで `ExtractionDestination` に構文を渡す。
  既定は `.portable`。`components(_:syntax:)` は既定値のない関数一つだけ。
  `ArchivePendingReadSnapshot` の二つの initializer も `nameSyntax:` は必須。
  snapshot がすぐ索引を作る経路と、Undo 後に遅延して作る経路の両方に保持する。
- selection、hard link の照合、並列処理の衝突判定、promise、Quick Look、コピー、読み取り可否は同じ構文を使う。
  重複名の鍵は `components.joined(separator: "/").precomposedStringWithCanonicalMapping` のまま
  （`ExtractionService.swift:264`）。`a\b` と `a/b` は別、NFC/NFD は最初の entry が優先される。
- `ArchiveIncomingFiles.restoredLeaf` は形式未定 (`nil`) のとき `.tar` のパス検査と一成分の照合だけを行う。
  `receive` の既定は `.zip` を維持し、`startConversion` だけが `nil` を渡す。
  `startImport`、file URL、元の名前のない promise、受信 cache の規則は維持した。
  最終形式の検査は `ArchiveCreationTransaction.run` の既存の `ArchiveImportPlan.build` に残る
  （:27–32、作業領域の作成は :53 以降）。新しい UI 文言・設定・Mode・公開経路はない。
- 必須引数の追加に伴い、仕様の一覧以外では `ArchiveImportTransaction` の選択索引、
  `DeferredSaveExtractionTests`・`ArchiveEntryControlsTests` の resolve、`M6bReviewTests` の snapshot 呼出しだけを更新した。
  いずれも既存の成分 closure・assertion・期待値は維持した。
- `Documentation/design.md` §9、review-plan の旧説明、0.3.0 の release notes を更新した。

## Path traversal が起きないことの証明（P13 A-4）

1. 展開のすべての書き込みは `ExtractionDestination` を通る。各成分は directory の記述子に相対な一回の系呼出しで開く
   （中間: `mkdirat` と `openat(…, O_DIRECTORY | O_NOFOLLOW)`、`ExtractionDestination.swift:115–118`、flags は :21。
   葉: `openat(parent, leaf, O_CREAT | O_EXCL | O_NOFOLLOW)`、:161・:237。
   link: `symlinkat` :210、`linkat` :286）。並列 worker も同じ出力先を使う（`ParallelExtraction.swift:55`）。
2. macOS の VFS は、名前の探索で `/`（0x2F）だけを区切りにする。
   `openat(dirfd, "a\\..\\x")` はその directory の直下の一つの名前だけを指す。
   成分が `/`・NUL・空・`.`・`..` を含まないことは `validate`（`ExtractionDestination.swift:61–65`）が保証する（変えない）。
   ここで空・`.`・`..` は成分全体の一致を指し、通常の拡張子の `.` は許す。
3. `\` を置けない、または特別に扱うファイルシステム（msdos・exfat・smbfs など）でも、A-1 の6と A-2 により
   `\` で分けた片に `..` は無い（`ExtractionPath.swift:25–34`、`ExtractionDestination.swift:64`）。
   `\` が区切りと解釈されても、出力 root の下の名前にしか届かない。
   実際の動作（拒否か置換か）は下記の FAT32/exFAT 試験で出力する。今回の sandbox で未実測の場合はそのまま未確認として記録する。
4. 解決後の実パスの照合（`isInside`、`ExtractionDestination.swift:70–83` と `ExtractionPath.swift:37`）と、
   symlink の target の検査（`ExtractionDestination.swift:195–208`。target は `/` だけで分けて解決する）は変えない。
5. 以上により、`posix` で新たに許すのは「出力 root の中の一つの名前に `\` の byte が入ること」だけになる。

上記は仕様の論証を現行の行番号に対応させたもの。NAME_MAX / PATH_MAX、fd 相対の書込み、quarantine、mode、
`O_EXCL`、`O_NOFOLLOW`、既存の traversal 拒否文言は変更していない。

`dir\sub/file.txt` など）が拒否も失敗もなく展開され、展開先の directory 列挙でも名前の UTF-8 が `\`（0x5C）と `:`（0x3A）を含む元の
byte のまま返った（macOS の msdos / exfat driver が、FAT で使えない文字を内部で対応付けて往復させる）。出力 root の外は変わらない。
したがって FAT32 / exFAT でも、P13 の後の展開は `back\slash.txt` を一つのファイルとして作る（P13 の前は `back/slash.txt`）。
