# 総合レビューと高速化の計画（2026-09-24）

0.3.0 (4) 公開直後の main から、KaitoFinder / GyoshukuKit / KaitoKit の三つを
`feature/2026-09-24-review` で見直す。依頼の重点は次の四つ。

1. 圧縮まわりの処理を限界まで速くする。
2. 保存時にまとめて書き込むモードの応答時間と、処理中シートを出すかどうかの快適さ。
3. 巨大なアーカイブを開いたときの分かりやすさと、読み込み中の表示。
4. 一覧の表示項目を Finder のように切り替えられるか。

加えて、分かりにくい箇所・非効率な箇所・不具合を客観的に探し、必要なら直す。

## 手順

1. 計測を先に行う（推測で最適化しない）。
2. 計測結果を添えて観点別のレビューを並列に行い、指摘は反証役で確かめる（完了: 47 エージェント、検証済み 39 件）。
3. 修正は里程標ごとに仕様を書いて実装し、ビルドの鮮度確認・全件テスト・反証レビューを経てローカルにコミットする。
4. 各里程標の前後の数値を `Documentation/verification/2026-09-24-*.md` に記録する。

## 完了の基準

- 四つの重点それぞれについて、計測値に基づく判断と、直したものは前後の数値がある。
- 直さないと決めたものは理由と次の手を記す（この文書の「見送り」）。
- 三つのリポジトリの全件テストが通り、UI の変更は GUI で確認済み（画面ロック中の失敗は環境要因として分類）。
- 新しい UI 文言は 26 言語、新しい autosave の状態はテストの退避・復元の対象に含まれている。
- 計測の道具は残す（書き込み速度のベンチマークと、環境変数で有効にする計測テスト）。
- push・merge・リリースは行わない（利用者の判断を待つ）。

## 計測の要点（R0、M4 Max 12P+4E / 128 GB）

書き込み（GyoshukuKit、単一スレッド、秒）と参照ツール:

| 入力 | zip | tar.gz | tar.bz2 | tar.xz | 7z | 参照 |
|---|---|---|---|---|---|---|
| text 256 MiB | 7.99 | 8.03 | 11.84 | 119.5 | 106.6 | zip-6 8.81 / xz -T1 122.5 / **xz -T0 17.8** / 7zz mmt1 206 |
| random 256 MiB | 3.74 | 3.75 | 17.5 | 50.7 | 40.8 | xz -T0 5.8 / 7zz mmt 14.4 |
| SDK headers 9.5k 件 64 MB | 1.89 | 1.80 | 5.47 | 17.1 | 9.67 | 7zz-zip mt 0.62 / xz -T0 4.45 |
| 小ファイル 5 万件 100 MB | 4.49 | 5.82 | 7.64 | 46.9 | 13.2 | zip 3.11 / 7zz-zip mt 1.56 |

- Apple の LZMA は `xz -6 -T1` と速度・出力サイズがほぼ一致（82,640,244 B 対 82,641,312 B）。codec 自体の改良余地はなく、並列化が唯一の大きな手段。
- ピーク RSS が入力サイズに比例（256 MiB 入力で 265 MiB、5 万件で 602 MiB）。`FileHandle.read(upToCount:)` の autorelease の滞留と確認（autoreleasepool で 262 → 6 MiB）。
- 展開（KaitoKit）は参照と同等。zstd だけ 1.97 s 対 zstd 0.27 s（約 7 倍遅い）。

アプリ（`-O` の Debug 構成・テスト有効、ミリ秒）:

| 件数 | 開く read | 保存時: 改名 | 保存時: 削除 | 保存時: 改名欄 1 打鍵 | 即時: 改名 | 即時: 削除 |
|---|---|---|---|---|---|---|
| 1 万 | 28 | 134 | 94 | 18 | 264 | 185 |
| 10 万 | 226 | 1,329 | 702 | 179 | 2,038 | 1,828 |
| 50 万 | 1,104 | 6,770 | 3,714 | 896 | 10,033 | 9,000 |

- 保存時モードの予約は 100% MainActor（sample: 検査 `validateRepresentability` 2.3 s、`ArchiveEditPlan.build` 1.2 s、投影 0.7 s / 50 万件）。改名を重ねても伸びない（2 回目以降 4.2 s）。
- 即時モードは MainActor 外。ZIP の再解析（DOS 日時変換が約 3 割）と全ローカルヘッダの検査、検証用の再 open、再読み込みで全件解析が 3〜4 回。
- 文書を開く処理はメインスレッドを全時間止める（`DispatchQueue.main.sync` の待ちが 10 万件 281/284 ms、50 万件 1,129/1,132 ms）。圧縮 tar は一覧の前に全体を展開する（text.tbz 256 MiB で 5.6 s）。

## 見送り（理由と次の手）

- 並列数をアプリの設定で選べるようにすること: 既定の自動値で十分な間は出さない。
- `formatSpecific` 辞書のメモリ（1 件 384 B）: KaitoKit の公開 API と GyoshukuKit の依存に及ぶ。
- 現在のフォルダへの移動（Finder の「フォルダに入る」）、⌘J の表示オプションのパネル: 設計の追加が必要。列の切替は M5 でヘッダのメニューと表示メニューから行う。
- 分割巻の性能の指摘（再ハッシュ等）: 4 回の反証レビューを経た部分で、変更の危険が利得を上回る。
