# P14（GyoshukuKit）: tar.xz の区切りの上限を二つに分ける。小さな member は 4 MiB まで詰め、大きな本文は 16 MiB の片のまま（反証レビュー後 2026-09-26）

計画の P14 行（「tar.xz の block の大きさ（P3 の区切りの配置と合わせて実測で決める）」）の仕様。段は **P14-G**（GyoshukuKit）の一つだけ。
KaitoKit と KaitoFinder の code・文言は変えない。KaitoFinder で変えるのは release notes だけ（§0.5）。
段の番号は ORDER-P6-P13 が与える（§0.4-A1）。本書では「P14-G」と呼ぶ。

## この版で決めたこと

1. **S を一つの定数にせず、二つの上限に分ける。**
   - **詰める上限 `ParallelXZCompressor.memberPackingSize` = 4 MiB（新設）。** 長さ（header 群 + 本文 + 詰め物）が 4 MiB 以下の member は、今と同じ規則で一つの区切りに詰める。区切りは 4 MiB まで。
   - **片の上限 `ParallelXZCompressor.defaultBlockSize` = 16 MiB（名前も値も今のまま）。** 4 MiB を越える member は、header 群と本文を別の区切りにする。本文（と 4 MiB を越える header 群）は 16 MiB ごとに切る。
     - 今は、この分け方を 16 MiB を越える member にだけ当てている。P14 は同じ分け方を 4 MiB を越える member から当てる。
   - **hint の無い入力（`!layout.hasHints`）の上限は 16 MiB（固定幅）のまま。** 詰める上限は hint のある入力にだけ当てる。
     - 当てると、組立が 4 MiB に達した所で `nextCount` が 0 を返し続け、`write` が進まない（TarCompressor.swift:53 の上限と ParallelXZCompressor.swift:50 の固定幅 16 MiB が食い違う）。hint の無い経路は `CompressedTarTestSupport.compress(aligned: false)`（Support/CompressedTarTestSupport.swift:43-45、:70）と `testUnhintedOutputMatchesOriginalFixedWidthFraming`（TarChunkLayoutTests.swift:258-279）が使う。
   - 根拠は §0.1。編集の時間を決めるのは「変更を含む区切り」の大きさだけで、大きな本文の片の大きさは効かない。
     - text256 の改名は S = 2・4・8・16 のどれでも 25–31 ms。
     - 4 MiB のファイルの改名は、S ≤ 4 なら 21–22 ms。
     - 一方、本文を 4 MiB に切ると text は 11.0 % 大きくなり、それで速くなる編集は無い。
2. **期待出力は byte 単位で決まっている（§0.1-5）。** S = 4 と S = 16 の出力の block を継いで作った file と、P14-G の出力が一致することを受入条件にする（AC-3）。
   - text と random は今の出力と同一。
   - small・headers・payload は S = 4 の出力と同一。
   - mixed は 156,255,864 byte（今より 3.43 % 大きい）。
   - レビューの試作（§0.1-8）の出力も、6 つとも合成と `cmp` で一致した。
3. **header 群だけの軽い区切りに、圧縮の並列の枠を使わせない（§D4）。** 入力が 64 KiB（`ParallelXZCompressor.lightChunkLimit`）以下の区切りは、`OrderedChunkPipeline` の枠の `threads` に数えない。
   - item の総数は 2 × threads + 1 までに抑える。
   - 詰める上限を越えるファイルが続くと、header だけの区切りと本文の区切りが交互になる。今の枠では、その半分を header の区切りが占め、8 threads でも本文が 4 本しか並ばない（S = 4 の payload で CPU/壁 3.96、作成は S = 16 より 17 % 遅い）。
     - 試作（§0.1-8）では、この規則で payload の作成が 10.66 s（B 15.35 s）、CPU/壁 7.40。規則を外すと 18.02 s、3.98。
   - **writer（`ParallelXZCompressor`）と updater（`CompressedTarSpliceWriter` の preflight と書出しの二つの枠）の両方に当てる。**
     - updater が全体を作り直す編集（fullEncode）と長い橋も、同じ区切りの規則（§D2）で切るので、header と本文が交互になる。
     - 全ての区切りに header がある今の書庫のフォルダ改名、CRC64 の xz（xz-utils の既定。`framingReason` で fullEncode）、運べる区切りの無い計画がこれに当たる。
     - updater に当てないと、今より遅くなる（試作: 今の書庫の payload のフォルダ改名 15.5 → 18.6 s、mid 13.6 → 24.2 s）。当てると 11.1 s・13.9 s（§0.1-8）。
   - **threads == 1 では `lightWeightLimit` を 0 にする。** 同時に動く符号化を 1 本に保ち、設定の「1」の意味を変えない。
   - この仕組みは P6-G が足す予定の `submit(…, weight:)` と同じ引数で入れる（重み = 入力の byte）。P6-G はそれを使い、別の引数を足さない。
   - `lightWeightLimit` の既定は 0。0 なら全ての item が今と同じく枠に数えられる。tar.xz 以外の圧縮の動作は変わらない。
4. **上限の使い分けは呼出し元ごとに決める（§D5）。** 詰める上限を使うのは次の二つだけ。
   - 区切りの切り方（hint のある入力と updater の橋）
   - 吸収のしきい値（`packing / 16` = 256 KiB）
   - それ以外は片の上限 16 MiB（今の値）を使い、動作を変えない。encode の cache、`nextEditReencodesEverything`、7z の片、P6-G の上界、hint の無い入力の固定幅がこれに当たる。
5. **KaitoKit・KaitoFinder の code と文言は変えない。**
   - KaitoKit は S に依らない（区切りの地図を読む。上限は `tooManyChunks` の 1,048,576 区切りだけ）。
   - P9 の記憶の見積り `30 + 135 × t` MiB（26 言語の「7z・tar.xz の圧縮では、最大で約 %@ …」）は、**上界ではなく text256 の実測に合わせた見積り**。
     - 今でも B の mixed（8 threads）は 1,140–1,153 MiB で、見積り 1,110 MiB を 3–4 % 越える。
     - P14 は peak RSS を corpus によって変える（試作、8 threads。§0.1-8）: mixed +3–4 %（1,177–1,189 MiB）、mid +12 %（999–1,004 MiB）、small・payload 約 −46 %、text・random は同じ。
     - 最大は mixed の 1,189 MiB で、見積りの +7 %。文言の「約」の範囲として式と文言は変えない。
     - P8-P9-P10 §0.3(e) に実測を足し（§0.4-B6）、係数を改めるか（KaitoFinder の別の段）を利用者に諮る（諮る点 6）。
6. **置き場所**（§0.3）: GyoshukuKit の列の S24 の commit の後、S38 の前に置く。
   - 専用の worktree `GyoshukuKit-p14` で行う。
   - AC-1–AC-12（KaitoFinder の全件と P0b を含む）を branch の commit で満たしてから merge する。merge は S25 の受入計測の後、S38 の開始前に行う。
   - 既存の文書へ入れる文は二つに分ける（§0.4）。
     - **A（P14-G の起動前）**: 段の番号・門・並行・B-P14・受入計測のまとめ。
     - **B（merge の時）**: P6-G の上界の式・接点・SCOPE、B-P6G、S43 の中身、計画書、P9 の注記。
     - 後置になったら B を入れない（S38 が存在しない API を前提にしないため）。
   - S38 の開始までに merge できなければ、S40 の後へ送る（§0.3 の後置の形）。
7. **出力の byte が変わるのは tar.xz だけ。** 既存の tar.xz も今と同じく編集できる（updater は元の書庫の区切りの地図を読み、変更を含む区間だけを新しい規則で切る）。
   - 16 MiB の区切りの書庫でも、最初の編集はその区間を 4 MiB の区切りに分けて並列に符号化する。今の 3.7–3.9 s が 1.05–1.16 s になる（§0.1-4、§0.1-8）。
   - 全ての区切りに header がある今の書庫のフォルダ改名は、最初の一回は今と同じく全体の作り直し（fullEncode）になる。§D4 の updater の枠で、今より遅くしない（試作で payload 0.71 倍、mid 1.01–1.02 倍）。
   - 逆向きも成り立つ。P14 の書庫は、今の KaitoKit で開け、今の GyoshukuKit でも編集できる。
     - KaitoKit の読取と K5 は区切りの大きさに依らない。
     - 今の updater は地図を読み、作り直す区間を 16 MiB の規則で切るだけ。
   - release notes に書く（§0.5）。
8. **採らなかった案**（数値は §0.1）
   - **単一の S = 4 MiB**:
     - 編集の速さは本案と同じ。
     - text が 11.0 %、mixed が 9.6 % 大きくなる。
     - 得るのは、作成が 31 % 速くなること（text、8 threads）と、thread あたりの記憶が 64 MiB になることだけ。これは圧縮率と速さの取引で、P14 の目的（編集）とは別。
     - 本案を利用者が採らないときの代案として残す（リスクと未決の「利用者に諮る点」1）。
   - **S = 8 MiB**（単一でも詰める上限としてでも）:
     - small の 1 件の削除が 1,954 ms かかる。
     - 4 MiB のファイルは header と本文が同じ区切りに入り、改名に 1,025 ms かかる。
     - payload のフォルダ改名は全体の再符号化になる（11.6 s）。
   - **S = 2 MiB**: small・mixed で tar.xz が tar.bz2 より大きくなる（small 50.46 MB 対 48.60 MB、mixed 175.12 MB 対 174.06 MB）。xz を選ぶ意味が無くなる。
   - **`WriterOptions` の値にする**:
     - KaitoFinder に UI が無い。設定を足すなら 26 言語の文言が要る。
     - 本案で費用は「小さなファイルが詰まった区間」に限られ、書庫ごとに選ぶ理由が計測に無い。
     - reader は S に依らないので、後から options にしても書式の互換は保てる。
   - **writer は 16 MiB のまま、updater だけ 4 MiB で切り直す**:
     - 各区間の最初の編集が 1 s を越える（§0.1-4 の 1,053 ms）。
     - payload のフォルダ改名は、全ての区切りに header があるので全体の再符号化のまま。
   - **軽い区切りを呼出側で同期に符号化する**: 枠から外すだけの方が経路が一つで済み、P6-G の重みと一つにできる。
   - **大きな member の header 群を前の区切りの末尾に付ける**:
     - その member の改名・削除が、前の区切り（≤ 4 MiB）の再符号化になる（今の 20 ms が約 0.7 s になる）。
     - 大きな member が続くと、結局 header だけの区切りが残る。
   - **組立の予約（`input.reserveCapacity(chunkSize)`）を次の区切りの大きさにする**: 試作で mid の peak RSS は −50 MiB だが、mixed は +30 MiB（1,218–1,222 MiB）。corpus で効果が逆になるので採らない。
   - **byte の枠（待ちの重みの和で並列を抑える）**: 1 MiB 前後の尾の片も軽く扱えるが、同時に動く重い符号化が threads を越える。17 MiB のファイルの列の CPU/壁 3.85 は今（3.06）より良く、退行ではない（§0.1-8）。

## OBJECTIVE

tar.xz の書庫で、1 件の追加・削除・改名・置換が再符号化する量を「変更を含む ≤ 4 MiB の区切り」に抑える。

- 4 MiB を越える member の改名・削除・フォルダ改名では、header 群だけの区切りの再符号化にする。
- 大きなファイルの本文の圧縮率・作成の時間は今と同じにする。記憶は §AC-8 の範囲に収める。
- updater が全体を作り直す編集（fullEncode）を今より遅くしない。

手段は二つ。

- 区切りの上限を「詰める 4 MiB」と「片の 16 MiB」に分ける（§D2）。hint の無い入力は 16 MiB の固定幅のまま。
- header 群だけの区切りが圧縮の並列の枠を使わないようにする（§D4。writer と updater、threads > 1）。

tar.gz・tar.bz2・7z・ZIP・LHA の出力の byte と、KaitoKit・KaitoFinder の code は変えない。

## DESIGN

### D1 定数

| 名前 | 値 | 意味 |
|---|---|---|
| `ParallelXZCompressor.memberPackingSize`（新） | 4 MiB | 小さな member を詰める区切りの上限。これを越える member は header 群と本文を分ける |
| `ParallelXZCompressor.defaultBlockSize`（今のまま） | 16 MiB | 最大の block。本文と大きな header 群の片。hint の無い入力の固定幅 |
| `ParallelXZCompressor.lightChunkLimit`（新） | 64 KiB | 並列の枠に数えない区切りの入力の上限（header 群だけの区切りと終端など） |
| `LZMA2ChunkPipeline.chunkSize`（今のまま） | 16 MiB | 7z の片、LZMA2 の入力の上限 |

### D2 区切りの規則（`TarChunkLayout`、P = packing、Q = piece、P ≤ Q）

gzip・bzip2 は P = Q なので、今の規則と同じ動作になる。tar.xz だけが P < Q。

1. `beginMember(headerLength: h, bodyLength: b, bufferedCount: n)`。L = h + b とする（b は詰め物を含む。TarWriter.swift:64）。
   - `cutBeforeInput = n > 0 && L > P − n`（今の `limit` を P にする）。
   - L > P なら、この member を「大きな member」にする。`pendingEnds` に header の終わり（h > 0 のとき）と member の終わり（b > 0 のとき）を積む（今と同じ）。
   - L ≤ P なら、「詰める member」にする。
2. 今の上限 U は次のとおり。
   - hint がまだ無い間（`!hasHints`）: Q。`write` の固定幅（`input.count == chunkSize`）と同じ値にする。P にすると、組立が P に達した所で `nextCount` が 0 を返し続け、`write` の loop が進まない。
   - 大きな member の区間（最後の `pendingEnds` に届くまで）: Q。
   - それ以外（詰める member と、終端の前まで）: P。
3. `nextCount(available:bufferedCount: n)`:
   - `count = min(available, 256 KiB)`。
   - 終端でなければ `min(count, U − n)`。
   - `pendingEnds.first` があれば、そこまでで止める（今と同じ）。
4. `appended(_:bufferedCount: n)`: `pendingEnds` の先頭に届いたとき、または n == U（届く前の U）のとき区切る。最後の `pendingEnds` に届いたら、大きな member の区間を出る。hint が無ければ今と同じく区切らない（固定幅は `write` が切る）。
5. 終端（`beginEndOfArchive`）は今と同じ。組立中があれば前で区切り、上限なしの一つの区切りにする。
6. 結果:
   - 4 MiB 以下の member が続く区間は、今の S = 4 の出力と同じ区切りになる（small・headers と同一。§0.1-5）。
   - 16 MiB を越える member は今の出力と同じ区切りになる（text・random と同一）。
   - 4 MiB を越え 16 MiB 以下の member は、header 群の区切りと、本文一つの区切りになる（mid。今は header と本文が一つの区切り）。
   - 本文の最後の片は詰め物を含む（16 MiB + 129 byte の本文は 512 byte・16 MiB・512 byte）。
7. `CompressedTarSplicePlan.cuts` は同じ `TarChunkLayout(limits:)` を byte 数だけで進める。
   - 橋の先頭が member の途中なら、残りの長さで 1 の判定をする（今と同じ形）。
   - したがって、member の境界から始まる橋は新しく書いた書庫と同じ区切りになる。今の書庫の本文の途中から始まる橋は、そうとは限らない（今と同じ性質）。

### D3 writer

- `ParallelXZCompressor` は `TarChunkLimits(packing: min(packingSize ?? memberPackingSize, chunkSize), piece: chunkSize)` を使う。
- 試験は internal の `ArchiveWriter.create(…, lzmaChunkSize: 65_536)` で呼ぶ。
  - 今の試験は P = Q = 65,536 のまま、今の期待で通る。
  - 新しい試験は `lzmaChunkSize: 262_144, xzPackingSize: 65_536` で二つの上限を試す。
- 出力はどの threads でも byte 一致（区切りの規則は入力の byte 数だけで決まり、符号化は決定的）。

### D4 軽い区切りと並列の枠（`OrderedChunkPipeline`）

- 各 item は `weight`（入力の byte。既定 0）を持つ。
- item を「軽い」とするのは `lightWeightLimit > 0 && 0 < weight ≤ lightWeightLimit` のとき。それ以外は「重い」。
- `waitForCapacity(emit:)`（`submit` の中からも呼ばれる）は、次のどちらかの間、先頭の item を書き出す。
  - 重い item の数が `threads` 以上。
  - 全 item の数が `2 × threads + 1` 以上。
  - 次に入れる item の重みは見ない。重い item が threads 本のときは、軽い item の投入も先頭の書出しを待つ（試作はこの形で CPU/壁 7.40）。
- 書出しの順（投入の順）と、失敗・取消し・`abandon` の扱いは変えない。
- `lightWeightLimit == 0` なら全て重いので、今の `items.count == threads` と同じになる。
  - 使うのは gzip・bzip2・ZIP・LHA・7z・自己照合・ZIP の再暗号化と、tar.gz・tar.bz2 の updater。
  - この経路は既定のままにする。
- `lightWeightLimit` を使う呼出し（どちらも tar.xz で threads > 1 のときだけ）:
  - writer: `ParallelXZCompressor`。
  - updater: `CompressedTarSpliceWriter.commit` の preflight と書出しの二つの枠。符号化する part の重みは `part.image.spliceLength`、入力の無い item（運ぶ part と cache 済みの part）は重み 0（今と同じく重い。すぐ終わるので枠を待たせない。試作は 1 で入れたが、§0.1-8 の結果は変わらない）。
    - updater も §D2 の規則で橋を切るので、4 MiB を越えるファイルが続く区間を作り直すと header と本文が交互になる。fullEncode（全ての区切りに header がある今の書庫のフォルダ改名、CRC64 の xz、運べる区切りの無い計画）で効く（§0.1-8）。
  - threads == 1 は 0（同時に動く符号化を 1 本に保つ）。
- 同時に動く符号化:
  - 重い item は `threads` 本まで。
  - 軽い item（64 KiB 以下）は、全体の上限の中でそれに加わりうる（最大 threads + 1 本）。
  - 記憶は区切りの大きさの混在と軽い item の同時の符号化で変わる。試作の peak RSS は mixed +3–4 %（§D4 を外しても同じ）、mid +12 %、他は同じか少ない（§0.1-8）。AC-8 の閾値はこの実測から決める。
- 待ちの入力の上界（P6-G の `maximumPendingInputBytes(for: .tarXZ)`）:
  - 重い item は threads × Q、軽い item は (threads + 1) × 64 KiB まで。これに組立中の Q を足す。
  - 合計は `(threads + 1) × (Q + lightChunkLimit)`。threads == 1 は (threads + 1) × Q で足りるが、式は上界のまま使う。§0.4-B2・§0.4-B3 で P6-G の式をこれに改める。
- 自己照合（`CompressedTarSelfCheck` の並列の復号）は変えない。fullEncode では区切りが増えた分だけ遅くなる（試作で 410–450 ms、B の mid は 213 ms）。

## リスクと未決

1. **小さなファイルの多い tar.xz が大きくなる**:
   - small +11.8 %、headers +5.5 %、payload（4 MiB の text のファイル）+4.6 %。
   - 大きなファイルだけの書庫は変わらない。
   - xz は small でも tar.bz2 より 2.5 % 小さいまま（47.38 MB 対 48.60 MB）。
   - 詰める上限を 8 MiB にすれば +4.7 % で済むが、1 件の編集が 2 s に戻る（§0.1-7）。
2. **読取が遅くなる**:
   - KaitoKit は xz を 1 本で復号するので、区切りの多い書庫の open は small・payload で約 +15 % になる（§0.1-3・§0.1-8）。K5 も、大きな区間を作り直す編集で同じ比だけ遅くなる（AC-9）。
   - KaitoKit に xz の block の並列の復号（P3-K の K4 の xz 版）を足せば、区切りが多いほど速くなり、この費用は逆になる（`xz -T0` は mixed で 0.26 s、KaitoKit は 3.1 s）。
   - 別の段として利用者に諮る。
3. **進捗の間隔**（P6）: 本文の片は 16 MiB のままなので、大きな text のファイルでは finishAdditions の間隔（約 4–7 s）が残る（P6-P7 のリスク 2）。詰めた区間は約 1 s になる。
4. **記憶**（§0.1-8）:
   - peak RSS は corpus によって変わる。mixed +3–4 %（§D4 の有無に依らない。区切りの大きさの混在による）、mid +11–12 %（軽い item の同時の符号化による）、small・payload 約 −46 %。
   - P9 の見積り（8 threads で 1,110 MiB）に対して、試作の最大は mixed の 1,189 MiB（+7 %）。B でも mixed は +3–4 % 越えている。
   - AC-8 の上限（B × 1.05・1.15、見積り × 1.10）を越えたら、軽い item の同時の数を 1 本にする形（呼出側の順に一つずつ）を試し、両方の RSS と時間を報告する。
5. **tar.gz・tar.bz2 の header だけの区切り**:
   - 1 MiB を越える member の header の区切りも、今は枠を使っている。
   - P14 は `lightWeightLimit` を tar.xz にだけ当てる。gzip・bzip2 へ広げるのは、計測してから別に判断する（出力の byte は変わらない）。
6. **今の書庫の編集**:
   - 編集しない区間は 16 MiB の区切りのまま残る（方針 1・2。運ぶ区間は byte のまま）。
   - 編集した区間だけが 4 MiB の区切りに切り直される。
   - 全ての区切りに header がある書庫（4 MiB 前後のファイルが並ぶ今の書庫）のフォルダ改名と CRC64 の xz は、最初の一回が fullEncode になる。§D4 の updater の枠で今より遅くしない（試作 0.71–1.02 倍）。枠が無いと 1.2–1.8 倍遅い。
   - 書庫全体を新しい規則に揃えたいときは、書き直しの経路（`ArchiveRewriter`）で作り直す。
7. **4–16 MiB の単一 block の他ツールの書庫**:
   - CRC32 なら `nextEditReencodesEverything` は今と同じく偽なので、KF は注意書きを出さない。最初の編集は ≤ 16 MiB を 4 MiB の区切りに分けて並列に符号化する（1 s 未満の見込み）。
   - CRC64（xz-utils の既定）は今と同じく注意書きが出て、fullEncode になる（6 と同じ）。
8. **期待出力の合成は corpus に依る**:
   - headers は SDK の版で変わる。
   - AC-3 は、R4 と B の出力から付録 A でその場で合成して比べる。§0.1-5 の SHA-256 は同じ corpus のときだけ使う。
   - G1 の `p3gA_review/g1-layout-reference.json`（scratchpad）の tar.xz の行は P14 で使わない。tar.gz・tar.bz2 の行は AC-4 の一致でそのまま成り立つ。
9. **S24 との重なり**:
   - P5-G が `LZMA2ChunkPipeline` を変えていれば（7z の header の 1 MiB の片など。P5.md:592）、P14-G の引数の足し方を合わせる（CONSTRAINTS）。
   - S24 の修正の commit が P14-G の実行中・後に入ったら、§0.3 のとおり rebase し、AC-1・AC-3・AC-4・AC-11 を採り直す。
10. **後置の形**（§0.3）: S38 が先に `weight:` を足していれば、P14-G は `lightWeightLimit` と枠の規則だけを足し、P6-G の上界の式と AC-G4 の試験を自分で改める。
11. **1 MiB 前後の尾の片**（§0.1-8 の 17 MiB のファイル）: 16 MiB を少し越えるファイルが並ぶと、尾の片が重い item に数えられ、CPU/壁は 3.85 に留まる（今は 3.06。出力は同じ）。退行ではないので P14 では変えない。

### 利用者に諮る点（ORDER-P6-P13 §6 に足す）

1. **二つの上限（本案）を採るか**。これは計画の P14 行（「block の大きさ」）を越える、区切りの規則の変更になる。
   - 採らなければ、単一の定数 S = 4 MiB で同じ仕様を実装する（§D2 の P = Q = 4 MiB、§D4 は同じ、§D5 の cache と `nextEditReencodesEverything` も 4 MiB 基準）。
   - その場合、P9 の記憶の見積りは 7z の分として残る。text +11.0 %、mixed +9.6 % を release notes に書く。
2. **小さなファイルの多い tar.xz のサイズの増加**（+5–12 %）を、編集の速さ（約 5 倍）と引き換えにしてよいか。
3. **置き場所**: P14-G を S38 の前に入れ、merge の時に P6-G の上界の式と接点を改めてよいか（§0.4-B）。
4. **版**: GyoshukuKit 0.11.0 に P6-G と一緒に入れるか、P14 だけで先に出すか（§0.3）。
5. **後続**: KaitoKit の xz の block の並列の復号（リスク 2）を別の段にするか。
6. **P9 の記憶の注記**: 「最大で約 %@」の見積り `30 + 135 × t` は、P14 の後 mixed の tar.xz（8 threads）で実測より 7 % 小さい（今も 3–4 % 小さい）。係数を改める KaitoFinder の段（26 言語の文言は変えず、式だけ）を足すか。足さなければ P8-P9-P10 §0.3(e) の注記（§0.4-B6）だけにする。

## 付録 A: `p14-compose.py`（期待出力の合成）

```python
#!/usr/bin/env python3
# P14 の期待出力: 詰める上限 PACK の build（S_PACK）と本文の片 PIECE の build（S_PIECE）の tar.xz から block を継ぐ。
# usage: p14-compose.py <S_PACK.tar.xz> <S_PIECE.tar.xz> <out.tar.xz> [PACK_MiB PIECE_MiB]
import subprocess, sys, struct, zlib, tarfile, io
pack_in, piece_in, out = sys.argv[1:4]
PACK = int(sys.argv[4] if len(sys.argv) > 4 else 4) << 20
PIECE = int(sys.argv[5] if len(sys.argv) > 5 else 16) << 20
def blocks(path):
    rows = subprocess.run(["xz", "--robot", "--list", "-vv", path], capture_output=True, text=True, check=True).stdout
    return [dict(coff=int(f[4]), uoff=int(f[5]), total=int(f[6]), usize=int(f[7]), hdr=int(f[11]), csize=int(f[13]))
            for f in (l.split("\t") for l in rows.splitlines()) if f[0] == "block"]
def members(path):
    image = subprocess.run(["xz", "-T0", "-dc", path], capture_output=True, check=True).stdout
    with tarfile.open(fileobj=io.BytesIO(image), mode="r:") as t:
        return [(m.offset, m.offset_data, m.offset_data + (m.size + 511) // 512 * 512 if m.isreg() else m.offset_data)
                for m in t.getmembers()], len(image)
ms, length = members(piece_in)
ranges = []  # (lo, hi, source)
for start, data, end in ms:
    size = end - start
    if size > PIECE: src = piece_in
    elif size > PACK and (end - data > PACK or data - start > PACK):
        sys.exit(f"not composable: member at {start} header {data - start} body {end - data}")
    else: src = pack_in
    if ranges and ranges[-1][2] == src and ranges[-1][1] == start: ranges[-1] = (ranges[-1][0], end, src)
    else: ranges.append((start, end, src))
if ranges[-1][2] == pack_in: ranges[-1] = (ranges[-1][0], length, pack_in)
else: ranges.append((ranges[-1][1], length, pack_in))
def vli(n):
    b = bytearray()
    while n >= 0x80: b.append((n & 0x7f) | 0x80); n >>= 7
    return bytes(b + bytes([n]))
cache = {p: (open(p, "rb").read(), blocks(p)) for p in (pack_in, piece_in)}
body = bytearray(cache[pack_in][0][:12]); records = []
for lo, hi, src in ranges:
    raw, bl = cache[src]
    sel = [b for b in bl if lo <= b["uoff"] < hi]
    if not sel or sel[0]["uoff"] != lo or sel[-1]["uoff"] + sel[-1]["usize"] != hi: sys.exit(f"blocks do not align at {lo}..{hi} in {src}")
    for b in sel:
        body += raw[b["coff"]:b["coff"] + b["total"]]; records.append((b["hdr"] + b["csize"] + 4, b["usize"]))
index = bytearray(b"\x00") + vli(len(records))
for unpadded, size in records: index += vli(unpadded) + vli(size)
index += bytes(-len(index) % 4); index += struct.pack("<I", zlib.crc32(index))
footer = struct.pack("<I", len(index) // 4 - 1) + bytes(body[6:8])
body += index + struct.pack("<I", zlib.crc32(footer)) + footer + b"YZ"
open(out, "wb").write(body)
print(f"{out}\tbytes={len(body)}\tblocks={len(records)}\tranges={len(ranges)}")
```

- この script は、次の場合に止まる。
  - 長さが 4 MiB を越え 16 MiB 以下の member で、本文か header 群が 4 MiB を越える（どちらの出力にも同じ block が無い）
  - block の境界が区間の境界と揃わない
- 2026-09-26 に §0.1-5 の 6 つで実行した（`SP/p14/hybrid/` の前の版。付録 A の版でも 6 つとも同じ file になることを確かめた）。
  - text・random は S = 16 と、small・headers・payload は S = 4 と `cmp` で一致した。
  - mixed は 3 区間を継いだ。
  - mixed と payload は `xz -t` と復号した tar の SHA-256 を確かめた。
  - レビューの試作の出力（§0.1-8）とも 6 つとも一致した。
