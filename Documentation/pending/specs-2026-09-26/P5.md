# P5（KaitoKit + GyoshukuKit + KaitoFinder）: 7z の header だけの改名、追記だけの追加、詰めるだけの削除（solid の一部削除はその folder だけ再圧縮）、AES の掛け直しを再圧縮なしで（最終版）

## この版での調停（2026-09-25）

反証レビュー反映版（指摘 F1–F20 を反映済み）を、P4 と共通の設計（`specs/final-p2p3/ORDER-P2-P3.md` の §1–§2。以下「ORDER」）と `specs/final-p45/ORDER-P4-P5.md`（以下「ORDER45」）に合わせて、次のとおり改めた。

1. **出力の部品**: `SplicedArchiveOutput` は ORDER45 §1.1 の最終の形を P2-G（S11）が作る。7z が要る `generated`・`finalPatch`・一時ファイル（`makeScratch`）・`CommitProgressMeter` もそこに含まれるので、P5-G は共有のファイルを変えない（旧版の「2 点を加法的に足す」をやめた）。
2. **solid の作り直しは一時ファイルを経る**（§G5）: 部品は「どの長さも計画の時点で決まる」形を保つ。作り直す folder は、先に `makeScratch` の一時ファイルへ符号化して長さを確定し、`generated` で出力へ写す。旧版の「長さが書き終えて決まる segment」は、後ろの位置・clone の飛ばし・再配置の判断を実行中に変える必要があった。さらに clone mode で、作り直した folder が大きくなると、add の時に書いた追加 block を上書きしていた。
   - 費用は、作り直した folder の圧縮後の byte を一度余分に書いて読むこと（AC-G15 で分けて報告する）。
   - header の byte と開始 header は、segment を書く前に確定する（`terminal` と `finalPatch`）。
3. **`ZipUpdateSource(duplicating:)`** は P4-G-b（S20）が作る。P5 は使うだけ。
4. **進捗**: total は作り直しの符号化を含む上界。`CommitProgressMeter.finish()` が残りを完了として数え、total は変えない（P1-G の `ZipCommitMeter.finish` の「total を縮める」形は使わない）。
5. **KF の枝**: P4-A と同じ形（ORDER45 §3.2）。`rewriteBranch(format:)` は `willOpenUpdater` を呼ばない（ORDER45 §1.2）。圧縮 tar の枝と注意書きの三形式への限定は、ORDER45 §1.3 か P4-A（S21）で済んでいる。P5-A は確かめるだけ。
6. **probe**: 7z のパスワードの probe を受ける形への改めを SCOPE に明記した（`ProbeArchiveEncryption` と fixture の `precondition` は ZIP 専用）。パスワードの操作の基準は、同じ build の従来の設定（`KAITOFINDER_PROBE_ADDITION_PLACEMENT=beginning`）で採る。direct の 7z を SevenZipUpdater で測る。
7. **段と版**: S23（P5-K）→ S24（P5-G）→ S25（P5-A）→ S26（KaitoKit 0.14.0 / GyoshukuKit 0.10.0）。B-P5 は S21 の計測（KK: S19、GK: S20、KF: S21）と兼ねる。
8. **行番号の基準**: KaitoKit は 24311ac（7z の parser のファイルは ba42ed8 と同一）、GyoshukuKit は e907e1d（S7 の後は関数名）にそろえた。
9. **書く量**: clone mode の改名は、先頭の 32 byte の 0 と開始 header の両方を書くので「header + header の pack + 64 B」にした（AC-G5）。

反証レビューで直した点（本文に反映済み）:

- currentPassword の folder ごとの確認（password の違う folder を持つ `mix.7z`）。
- 0 件の header の形 `01 05 00 00 00`。
- `.unchanged` の条件。
- KF の進捗の二重の数え。

- AppleDouble の条件の削除、見込みの数値、記録の memory、version `00 04`、encoded header の表現、SFX、header の暗号化を外す安全網、16 MiB を越える header、writer の寿命、入力の password の意味。

### 0.1 この仕様で決めたこと（要約）

| # | 論点 | 決定 |
|---|---|---|
| 1 | 経路 | 新しい `GyoshukuKit.SevenZipUpdater: ArchiveReencrypting`（`ArchiveEditing` を含む）。`open(url:password:output:options:)` で開く（P2 の TarUpdater と同じ形）。原本の**記述子**から P1-G の `ArchiveSourceSnapshot` で snapshot を clone し、KaitoKit はその snapshot を解析する。編集の計画に使う構造と、運ぶ byte は、同じ不変の inode から来る |
| 2 | 出力の組み立て | 呼出側の作業ファイル（output）1 つへ書く。output の作成・segment の実行・ftruncate・fsync・finalPatch・V5・進捗の計量・cleanup・再配置・一時ファイルは、P2-G の `SplicedArchiveOutput`（ORDER45 §1.1）で行い、変えない。clone mode では output を snapshot の clone から始め、出力位置が原本と同じ運ぶ pack は書かない。それ以外の pack・header・開始 header だけを、snapshot か一時ファイルから読むか、書きながら作って書く（その場ではずらさない）。clone できない volume（ENOTSUP / EXDEV）では output を先頭から一度ずつ書く。どの segment の長さも、segment を書く前に決まる |
| 3 | 改名 | header と開始 header だけを書く。pack は一 byte も書かない |
| 4 | 追加 | P2 §G7 と同じ: 最初の add で `SplicedArchiveOutput.beginAppend(at: P_add, prefix:)` が output を作り、その時点の計画の pack の終わり P_add から、返る dup 済みの FileHandle に GK の 7z writer（1 file = 1 folder、LZMA2、options.password があれば AES。`SevenZipWriter(startPosition: P_add)`）で直接書く。commit の最終計画で位置が違えば `SplicedArchiveOutput` の再配置（`.relocatedAppend`）。新しい file は一覧の最後（呼出し順） |
| 5 | 削除 | stream の無い entry（directory・空ファイル・anti）は header だけ。全 file を失う folder はその pack を落とし、後ろの pack を詰める（復号しない）。末尾の folder だけなら header を書いて切り詰める。file が 0 件になれば header は `01 05 00 00 00` |
| 6 | solid の一部削除 | 一部の file を失う folder（substream が 2 以上）だけを KaitoKit で復号し、生存 file を元の順で**一つの solid な LZMA2 folder** に作り直して、同じ folder の位置に置く（7zz の `d` と同じ）。元の folder が AES なら AES も掛ける。作り直した folder は、先に一時ファイル（`makeScratch`）へ符号化して長さを確定し、`generated` で出力へ写す。大きさが変わるので後ろの pack は動く。新しいファイルへ書くので、その場の重なりは起きない |
| 7 | 運ぶ folder | coder・props（LZMA2 の辞書、AES の IV）・bind・packed stream・unpack size・CRC・pack の byte が同一。BCJ / BCJ2 / PPMd / AES も不透明なまま運ぶ |
| 8 | 運ぶ file | 名前の UTF-16LE の byte、ctime / atime / mtime の FILETIME の生値、属性の生値、emptyStream / emptyFile / anti、StartPos が同一。stream の無い entry を先頭へ寄せない（元の位置のまま） |

## P5-K（KaitoKit、S23）

### OBJECTIVE

1. 7z の編集に要る「生の header 値」を、SPI の option を立てたときだけ open の中で記録し、`sevenZipEditingSnapshot()` で返す（§0.2）。GK がこれで header を損失なく作り直せること（folder・coder・props・bind・packed stream・unpack size・CRC・substream・file の生の名前・FILETIME・属性・フラグ・property の順・kDummy・header の符号化の形・packPos・SFX の base）。

3. 変えないもの: 公開 API の宣言・値・検査・エラー、option が false のときの動作・費用・読み取り量、`reopen()` の共有と記述子の数。

### DESIGN

#### K0 公開値の golden（Sources を変える前に採る）

P3-K の K0 と同じ手順。Step 0 の fixture 全部について、`ArchiveReader.open(url:options:)`（password は fixture の README のもの）の `entries` の全公開値（name・rawName・kind・sizes・dates・permissions・isEncrypted・solidGroup・crc32・methodDescription・formatSpecific の全 key）と、各 entry の `read` の SHA-256、失敗する fixture では error の値を `public-values.json` に採る。変更後、option の off と on の両方で一致すること。

#### K1 option と記録

- option が false のときは何も記録しない（配列も確保しない）。true のときだけ、次を内部の `SevenZipEditState` に採る:
  - 開始 header の version の 2 byte と `nextHeaderRange`（`readNextHeader` :247-283 の値）。
  - header の形: 平文（:301-303）か、kEncodedHeader のときの streams の全 folder と全 pack の範囲（`decodeNextHeader` :308-316 の `streams` と `SevenZipFolderLayout.ranges`。1 つに限らない）。`plainHeaderLength` は復号した header の byte 数。
  - main の streams: packPos、pack の範囲と digest（`SevenZipFolderLayout.ranges` :71-111 の値と同じ）、folder（coder の methodID・入出力数・**生の flags**・props、bind、packed index、unpack size、folder CRC、finalOutput）、substream（folder・offset・size・CRC）。
  - FilesInfo: 各 file の生の名前（今も保持 :4）、`hasStream`・`isEmptyFile`・`isAnti`、**FILETIME の生値**（`parseTimes` が `Date` に変える前の UInt64。:362）、属性、StartPos、property ID の出現順（kDummy を含む。重複可の ID も出た回数だけ）。
  - `unrepresentedReason`: kArchiveProperties（:56-61）・kAdditionalStreamsInfo（:63-73）が現れた、`valueCursor` の external = 1（:417）か UnpackInfo の external = 1、0x0E–0x15・0x18・0x19 以外の property ID（:242-245 で飛ばすもの。kComment 0x16 を含む）。最初に見つけた一つ。
  - `baseOffset`: `sfxRebasedSource`（:736-763）が `RebasedByteSource` を返したらその baseOffset、そうでなければ 0。
- `files` の数と順は `entries` と一致する（`makeEntries` :540-652 の index）。`substreamIndex` は `makeEntries` の `streamIndex` と同じ規則。
- 生の値は、公開値の元になる値と同じ解析の結果から採る（別の走査を作らない）。記録の費用は O(件数) のメモリ。Optional の UInt64 ×4（ctime・atime・mtime・StartPos、stride 16）、UInt32?、Int?、flag で 1 件あたり ≈ 90–110 B（名前は既存の配列を共有）。上限は 1 件あたり 128 B（定義されない値を持たない表現にしてよい）。KF は全ての 7z の open でこの option を立てるので、この量は全 session に乗る。
- 記録は検査を増やさず減らさない。今 `malformed` になる header は、option に依らず同じ error になる。

#### K2 snapshot の意味

- `sevenZipEditingSnapshot()` が nil になるのは: option が false、`format != .sevenZip`、`volumeSet != nil` か source が `ConcatenatedByteSource`。7z の reader は AppleDouble で包まれない（KK ArchiveReader.swift:157-170。包むのは tar :147 と zip :153）ので、AppleDouble の条件は置かない。
- snapshot は reader から独立した値（Sendable）で、source を持たない。
- 座標: pack・`nextHeaderRange`・header の pack・`mainPackEnd` は、7z の署名を 0 とする座標（`SevenZipPackRange.offset` と同じ。SFX でも署名が 0）。
- `SevenZipEditHeader.isCompressed` は AES と Copy（`00`）以外の coder があるとき true。

#### K3 reopen

- `SevenZipReader.reopened(options:)`（:150-155）は `SevenZipEditState` も渡す。新しい reader の snapshot は元と等しい。source を読まず、記述子を増やさない（`ReopenSharingTests` をそのまま通す）。
- option の値も今どおり `reopen()` の options に引き継ぐ。

#### K4 AES が直接読む packed stream の復号

- `sevenZipDecryptedPackedStream(folder:packedInput:)`: `folders[folder].packedInputs[packedInput]` を入力に持つ coder が AES（1 入力 1 出力）であること。そうでなければ `KaitoError.malformed("7z packed input is not read by AES")`。範囲外は `KaitoError.notFound("7z folder \(folder)")` / `notFound("7z packed input \(packedInput)")`。
- 鍵は `ArchiveReader.password` から、既存の `SevenZipAESKeyCache`（SevenZipAES.swift:49-100）と `maxSevenZipAESCyclesPower`（既定 24）で導く。password が nil なら `passwordRequired`（provider は呼ばない）。`ArchiveReader.stream` と同じく、呼ぶ前に format reader の password を `ArchiveReader.password` にそろえる（`setPassword`。password が変われば鍵 cache と coordinator を捨てる今の規則のまま）。
- stream の長さは AES の output の unpack size。pack を AES-256-CBC で復号し、その長さに切る。展開も CRC の照合もしない（`EntryStream(… expectedCRC32: nil …)`）。PackInfo の digest があれば、既存の `SevenZipPackedStreamVerifier` が読む前に照合する（今の復号の経路と同じ）。
- 実装は既存の AES の復号器（`SevenZipFolderDecoderFactory` の `.aes` の経路）を、packed stream の `bytes` 入力に直接つないで作る。新しい暗号の実装を作らない。
- option に依らず使える（snapshot を要しない）。

#### K5 端の場合

- folder が 0 個・file が 0 個の書庫（`01 00` と `01 05 00 00 00`）: snapshot は空の配列で返す（`filePropertyOrder` も空）。7zz の全件削除の出力（32 byte、next header の長さ 0）を KaitoKit が拒否するのは今と同じ（本仕様では変えない。リスク 11）。
- substream が 0 個で unpack size が 0 の folder（今も受理する）: `substreamIndices` は空。
- PackInfo の digest の一部だけがある書庫: 各 pack の `crc32` はその値か nil。
- header の暗号化の書庫: snapshot を採れるのは open が成功した後だけ（header の復号には password が要る）。

### DESIGN

#### G1 寿命・出力・状態

**open(url:password:output:options:)** の順序（どこで失敗しても、原本は無傷で、output も一時ファイルも残らない）:

1. `options.validate(for: .sevenZip)`（WriterOptions.swift:99-116。`preserveOwnerIDs` は :106-108 で拒否）。
2. R0: `options.additionPlacement == .beginning` なら `requiresRewrite("additionPlacement")`。
3. S1: `ArchiveVolumeSet.parse(fileName: url.lastPathComponent) != nil` なら `requiresRewrite("split volume name")`。
4. output の検査（P1-G D7: `ArchiveSourceSnapshot.validateOutput`）。満たさなければ `WriterError.invalidPath`。
5. `ArchiveSourceSnapshot(url:directory: output の親, pathExtension: "7z")`: 原本を O_RDONLY | O_NOFOLLOW で開き、flags（UF/SF の IMMUTABLE・APPEND）を拒否し、記述子から `fclonefileat` で `.gyoshuku-source-<UUID>.7z` を作る（**clone mode**）。ENOTSUP / EXDEV なら原本を直接読む（**sequential mode**）。`testingDisablesClone` なら sequential。
6. KaitoKit: `ArchiveReader.open(source: snapshot か原本の ZipUpdateSource, sourceURL: url, options:)`。options は `ReaderOptions(limits: ReadLimits(maxEntrySize: .max, maxTotalUncompressedSize: .max), password: password, appleDoublePolicy: .expose)` に `recordsSevenZipEditLayout = true`。KaitoError はそのまま投げる。`reader.format != .sevenZip` なら `UpdaterError.invalidArchive("7z ではありません")`（P2 の TarUpdater と同じ。KF の inspect が 7z と判定した書庫では起きない）。
7. `ArchiveRewriter.validateRepresentability(entries:format: .sevenZip, reader:)`（P2 で internal）で `names` を得る。`RewriterError.unrepresentable` はそのまま投げる（アプリの門番と同じ集合）。
8. snapshot の検査（§G2 の S2–S6）。当たれば snapshot を消してから `requiresRewrite(reason:)`。
9. `checkUnchanged`（原本と snapshot）。

**状態**: `adding → committing → committed | failed`（ArchiveRewriter と同じ `perform`）。commit の progress の callback から他の API を呼ぶと `invalidState` で failed。失敗後は `invalidState`、成功後の commit は no-op。index の範囲外は `invalidEntryIndex`。

**output の作成**（最初の add（`beginAppend`）か commit。変更の無い commit でも作る）: `SplicedArchiveOutput` が P2 §G3 の 1–5 のとおりに作る（checkUnchanged → clone mode は snapshot の記述子から `fclonefileat`、chmod 0600、flags を 0、sequential mode は `O_RDWR | O_CREAT | O_EXCL | O_CLOEXEC`・0600 → checkUnchanged → fstat と lstat の (dev, ino) の一致を記録）。

**後始末**（失敗・取消し・破棄・deinit）: `SplicedArchiveOutput.discard()`（自分が作った output と一時ファイル（再配置の spool、作り直しの一時ファイル）を、lstat の (dev, ino) が記録と一致するときだけ消す）と、snapshot の cleanup（P1-G）。追加の writer があれば、その dup した記述子を閉じる。commit が成功したら output を close して残し、snapshot と一時ファイルを消す。原本は byte も inode も無傷。

#### G2 open の検査と rewriter へ戻す条件

snapshot（`reader.sevenZipEditingSnapshot()`）に対して、次の順に判定する。どれも構造だけで決まり、操作に依らない。

| # | 条件 | reason |
|---|---|---|
| S0 | `additionPlacement == .beginning`（G1-2） | `additionPlacement` |
| S1 | 分割巻の名前（G1-3） | `split volume name` |
| S2 | snapshot が nil（起きないはず。option を立てて単一ファイルを開くので） | `no 7z editing snapshot` |
| S3 | `baseOffset != 0`（SFX。rewriter は今日どおり prefix を落とす） | `sfx prefix` |
| S4 | `unrepresentedReason != nil` | `header: archiveProperties` など case の名前（未知の ID は 16 進） |
| S5 | `packPosition != 0` | `pack position gap` |
| S6 | snapshot と `reader.entries` の不一致: files と entries の数、`files[i].rawName == entries[i].rawName.bytes`、stream を持つ file の substream の size が `entries[i].uncompressedSize`、folder・pack・substream の対応（pack が連続して `mainPackEnd` で終わる、substream の数の和） | `layout mismatch` |

- 変えない（戻さない）もの: header の pack の位置（出力では常に最後の pack の直後に書き直す）、main の最後の pack と next header の間の byte と `nextHeaderRange` の後ろの余分な byte（捨てる。今日の rewriter と同じ）、PackInfo の digest（運ぶ pack では保つ）、anti の entry（そのまま運ぶ）、BCJ2 など複数 packed stream の folder（不透明に運ぶ）、version の byte（出力は常に `00 04`。libarchive は 0.3 を書く）。
- `assess(reader:)` は S2–S6 と同じ判定を KF の reader の snapshot で行う（S6 は reader の entries で）。`reason` は同じ文字列。`canReencrypt` は §G6 の形の判定。

#### G3 model と計画器（純関数）

入力: snapshot から作った元の model、`names`（正規化した名前。衝突の判定用）、削除の集合、改名（index → 正規化した新しい名前）、追加の writer の record と output の中の範囲（§G4）、暗号化の予約（§G6）、header の方針（§G7）。出力: 出力の folder の列、出力の file の列、各 folder の作業、`SplicedCommitPlan`（§G8。作り直す folder の長さは §G5 の一時ファイルで確定した後に入れる）、戦略、作業量。

1. **file の列**: 生存 file を元の index の順（削除した file を除く）→ 追加を呼出し順。
   - 改名しない file は元の生の名前・時刻・属性・フラグ・StartPos のまま。
   - 改名した file の名前は `ArchiveWriter.normalizedPath(path, directory:, format: .sevenZip)`（:563-574。NFC、directory は末尾 `/`）の UTF-16LE。他の値は元のまま。正規化後の名前が元の正規化名と同じ改名は、何もしない（元の生の名前を保つ。P2 の `.unchanged` と同じ扱い）。
   - 追加の file: SevenZipWriter の record から、名前（writer が正規化したもの）、mtime（秒単位の FILETIME、SevenZipRecords.swift:20-27）、属性 `UInt32(mode) << 16 | 0x8000 | (directory ? 0x10 : 0x20)`（:96 と同じ）、emptyStream = size が 0、emptyFile = size が 0 で directory でない、anti = false、ctime / atime / StartPos は未定義。
2. **folder の作業**（元の folder k ごと。k の substream を持つ file の集合を F_k とする）:
   - F_k の全部が生存: `.carry(k)`（暗号化の予約があれば §G6 で `.convert(k, 変換)` に置き換わりうる）。
   - F_k の全部が削除: `.drop(k)`。
   - 一部だけが削除（substream が 2 以上のときだけ起きる）: `.reencode(k, 生存 substream の列, 暗号化)`（§G5）。
   - substream が 0 の folder: `.carry(k)`。
3. **folder の列**: 元の folder の順に `.carry` / `.convert` / `.reencode`（`.drop` は除く）→ 追加の folder（writer の record の順）。file と substream と folder と pack の順が一致すること（7z の暗黙の対応。file の順は生存 file が元の順なので保たれる）。
4. **戦略**（`@_spi(Testing)`）:
   - `.unchanged`: 実際に効く削除・改名・追加・変換が無く、**かつ** §G7 の方針で出る header が元と同じ形と鍵であること（形: 平文 / 圧縮 / AES の有無が同じ。AES なら `options.password` と header の復号に使った password の UTF-16 の列が等しい）。そうでなければ少なくとも `.headerOnly`。
   - それ以外は次の順に最初に当たるもの: sequential mode なら `.sequential`、追加が再配置されたら `.relocatedAppend`（この二つは `SplicedArchiveOutput.commit` の戻り値で決まる）、変換があれば `.reencrypted`、作り直しがあれば `.reencoded`、位置が変わる運ぶ folder（途中の `.drop` より後ろ）があれば `.compacted`、追加の folder だけを書くなら `.appendOnly`、pack を書かないなら `.headerOnly`。
5. **作業量**（進捗の total。計画の後、作り直しの符号化の前に確定し、以後変えない。`CommitProgressMeter(total:progress:)` に渡す）: 作り直しの入力の byte（その folder の unpack size。一時ファイルへの符号化で数える）、作り直した folder の写し（unpack size + unpack size / 32 + 256 で数える。LZMA2 の非圧縮の chunk と AES の padding の分。越えた分は meter が止める）、書く見込みの運ぶ pack の byte（作り直す folder より後ろは、位置が変わるものとして数える。§G8-3）、変換の pack の byte、再配置があればその往復、先頭の 32 byte と開始 header の 32 byte、header の上界 H、照合の読み取り（V1 に H、V2 に動かす運ぶ pack の 2 倍、V3 に復号する folder の unpack size、V3a に変換した pack の byte）。H は、計画の後の model の平文の header の長さを、作り直す folder の、書くまで決まらない数値欄（pack の大きさと、AES のときの LZMA2 の長さ）を number の最大長 9 byte で数え、整列を行う場合は kDummy 1 つにつき最大 17 byte を足して求める（coder と props の長さは決まっている。改名・新しい property を含む上界）。`CommitProgressMeter` は completed を total で止め、`finish()` が見積りより少なく済んだ分を完了として数える（最後に completed == total。total は変えない）。作り直しが無く追加の再配置も無い commit では、total は `units(for:)` と同じ（正確）になる。
   - 追加の byte は add の時に書いたので含めない（P2 §G7。再配置の往復だけを含める）。
6. 計画は I/O をせず、決定的（試験 `SevenZipUpdatePlanTests` で合成の snapshot に対して確かめる）。

#### G4 追加（P2 §G7 と同じ形）

- 最初の add:
  - その時点の予約で G3 を計画し、`P_add` = 追加より前の pack の終わりとする。`SplicedArchiveOutput.beginAppend(at: P_add, prefix:)` が output を作る（G1）。
  - **clone mode** では、`.reencode` の folder はこの時点では元の pack の大きさで数える（commit で大きさが違えば再配置）。beginAppend は何も書かない（clone の byte の上に `P_add` から追記する。`P_add` より前の運ぶ pack は snapshot から読むので、clone の中身を上書きしても害は無い）。
  - **sequential mode** では、beginAppend が prefix（先頭の 32 byte の 0 の `literal` と、`P_add` までの pack の segment）を output の 0 から順に書く（HFS+ / exFAT は疎なファイルを持たないため。P2 §G7）。`.reencode` があれば、その前に §G5 の一時ファイルへ符号化して長さを確定し、`generated` で写す。`P_add` はその長さで決まる。変換（`.convert`）があれば、その前に §G6 の currentPassword の確認を行う。取消しは片ごと。commit の `CommitProgress` には含めない。
- writer:
  - `beginAppend` が返す FileHandle（output の記述子を dup したもの、closeOnDealloc）だけに書く（パスで開き直さない。ArchiveWriter の deinit が close しても、`SplicedArchiveOutput` の記述子は残る）。
  - `SevenZipWriter(…, startPosition: P_add)`（32 byte を予約しない。pack の範囲は output の座標）で `ArchiveWriter` の 7z の追記用の factory を作り、`prepareAppend(at: P_add, existingPaths:)` で、その時点の予約を反映した名前の集合を渡す（ArchiveUpdater と同じ `writerPathsNeedRefresh` の規則で、予約が変わったら `replaceExistingPaths`）。
  - `add(contentsOf:as:)`・`add(data:…)`・`addDirectory(_:)`・`addDirectory(_:modificationDate:ownerIDs:)`・`add(contentsOf:as:ownerIDs:)` は writer の同じ API へ渡す（ownerIDs が nil でなければ `unsupportedOption("ownerIDs")`。P2-G）。ディスクの読み取り・symlink・directory の再帰・読取中の変更の検出は writer のまま。
  - 暗号化は writer の規則のまま（`options.password` があれば size > 0 の entry を AES、SevenZipWriter.swift:54）。
- commit で `endSevenZipEntries()` を呼び、record と output の中の追加の範囲 `[P_add, appendedEnd)` を得て writer を解放する（dup の記述子が閉じる。`finished` なので abort は何もしない）。writer の失敗は今日どおり writer の abort（output を 0 に切り詰める）と updater の failed・cleanup。
- **再配置**: 最終計画の追加の開始 `M'` が `P_add` と違う場合（予約が追加より後に来た、`.reencode` の一時ファイルの長さが元の pack と違った）、または sequential mode で `P_add` より前の segment が最初の add の後に変わった場合は、`SplicedArchiveOutput.commit` が再配置を行う（P2 §G7 の 1–3。`[P_add, appendedEnd)` を一時ファイルへ写す → clone mode は snapshot から clone し直し、sequential mode は 0 に切り詰める → 最終計画を実行し、一時ファイルを `M'` へ写す）。作り直す folder の長さは segment を書く前に一時ファイルで確定しているので、判断は実行の前に決まり、add の時に書いた追加 block を上書きしない。戦略は `.relocatedAppend`。7z の pack は offset を持たないので、追加の pack の byte は位置に依らない。
- KF は予約（削除・改名・暗号化）を追加より先に呼ぶ（§A3）。再配置が起きるのは、`.reencode` の大きさが元と違うときと、ライブラリの呼出し順が逆のときだけ。

#### G5 solid folder の一部削除の作り直し

1. GK の reader（open で開いた snapshot の reader）で、folder k の substream を持つ file を substream の順に、**削除する file も含めて**全部 `reader.stream(entry)` で最後まで読む（KaitoKit が各 substream の CRC を照合する。削除する file の byte は捨てる）。元の coder は KaitoKit が復号できるもの全部（LZMA・LZMA2・PPMd・BCJ・BCJ2・Deflate など。試作は Python の復号器が無く BCJ / BCJ2 の一部削除を試していない）。暗号化された folder では reader の password が要る（無ければ KaitoKit の `passwordRequired` をそのまま投げる。予約の後は currentPassword。§G6）。
2. 生存 file の byte を順に連結した入力を、`SevenZipFolderEncoder` で一つの folder に符号化する:
   - coder は GK の writer と同じ形: `[LZMA2]`、暗号化するなら `[AES, LZMA2]`（bind pair は input 1 ← output 0、SevenZipRecords.swift:57-62 と同じ）。
   - LZMA2 は `LZMA2ChunkPipeline`（16 MiB の片、`options.resolvedCompressionThreads`）。片は file の境界をまたいでよい。片ごとの辞書 reset を保ち、終端の 0 は folder の最後に一度だけ（SevenZipWriter.swift:147-158 の規則）。props は片の最大。
   - 暗号化は、変換の予約があれば §G6 の目標、無ければ元の folder が AES なら `options.password` の AES（password が nil なら `WriterError.invalidOption("password")` を commit で投げる。KF は暗号化された書庫で常に password を渡す）、元が平文なら平文。IV は folder ごとに新しく作る。
   - unpackSizes は `[全体]` か `[LZMA2 の長さ, 全体]`。folder CRC は無し。substream は生存 file の数で、size は元の size、CRC は読みながら求めた CRC-32（元に CRC があればそれと一致する。常に定義する）。
   - 生存 substream の合計が 0 byte（size 0 の stream を持つ file だけが残る）なら、`LZMA2ChunkPipeline` に空の入力を渡さない（`submit` は空を precondition で拒否する。LZMA2ChunkPipeline.swift:21）。LZMA2 の pack は終端の `00` の 1 byte、props は `00`、unpackSizes は `[0]`（AES なら `[1, 0]` で pack は 16 byte）にする（平文の形は 7zz・bsdtar・KaitoKit が受理することを確かめた。`SP/p5review/zero_lzma2.7z`）。
3. 符号化の出力は、`SplicedArchiveOutput.makeScratch(tag: "reencode")` の一時ファイル（output の隣、O_EXCL、0600）へ書く。commit では、全ての segment を書く前に作り直す folder を符号化し（sequential mode で最初の add の時に符号化したものは、入力が同じなら使い直す）、その長さで最終計画の位置・header・開始 header を確定する。出力へは、計画の folder の位置で `generated(length: 一時ファイルの長さ, write: { try $0.copy(0..<長さ, from: 一時ファイル.source()) })` として写す。folder の順と file の順は変わらない。
   - 一時ファイルを経る理由: 部品は「どの長さも segment を書く前に決まる」形で、後ろの位置・clone の飛ばし・再配置の判断を実行の前に決める（ORDER45 §7-1）。長さが書き終えて決まる segment にすると、clone mode で大きくなった folder が、add の時に書いた追加 block を上書きしうる。
   - 費用: 作り直した folder の圧縮後の byte を、一時ファイルへ書いて読み、出力へ書く（書く量が一度分増える）。`lastCommitStatistics` と AC-G15 で、一時ファイルの時間を分けて示す。
   - 一時ファイルは、commit の終わり・失敗・破棄で `SplicedArchiveOutput` が消す。
4. 決定性: 同じ入力と同じ片の大きさなら、thread 数に依らず同じ byte（Apple の LZMA は入力だけで決まる。片の境界は入力の byte だけで決まる）。AES は IV を除いて同じ。

#### G6 暗号化の変換（`reencryptExistingEntries(currentPassword:)`）

意味は P1b の ZIP と同じ。

- 目標: stream を持つ全 folder を、`options.password` が nil なら平文、そうでなければ `options.password` の AES にする。header は `options.encryptsSevenZipHeaders`（§G7）。追加は writer の規則（目標と同じ）。
- 状態: `adding` のときだけ。一度だけ（二度目は `invalidState` で failed）。remove / rename / add との順序は問わない（追加の後に呼ぶと、変換で pack の大きさが変わる場合に再配置になる。§G4）。予約の時点で、全 folder が変換の形（packed stream が 1 本、AES があれば 1 入力 1 出力でその stream を直接読む）であることを確かめ、そうでなければ `UpdaterError.reencryptionFailed(index: その folder の最初の file の index, name: その名前, reason: "7z の folder の形のため暗号化を変更できません")`（KF は `assess` の `canReencrypt` で先に書き直しへ回すので、通常は起きない）。
- 入力の password: header は open の `password` で復号済み。予約の後は、既存の folder の復号（§G5 の作り直しと本節の変換）に `currentPassword` を使う（reader の `password` を currentPassword にする）。予約が無ければ open の `password`。
- folder ごとの変換（`.drop` と `.reencode` の folder は対象外。作り直しは §G5 で直接目標にする）:

| 元 → 目標 | 処理 | pack の大きさ |
|---|---|---|
| 平文 → 平文 | 運ぶ | 同じ |
| AES → AES で、`currentPassword` と `options.password` の UTF-16 の列が等しい（String の `==` は正規化を同一視するので使わない。P1b と同じ） | 運ぶ（IV も同じ） | 同じ |
| AES → AES（違う password） | 掛け直し: KaitoKit の `sevenZipDecryptedPackedStream`（reader の password = currentPassword）の平文を、新しい鍵（`EncryptionPrimitives.sevenZipKey(password: options.password)`、書庫で一度だけ）と新しい IV の `SevenZipAESEncryptor` で暗号化する（最後は 0 で 16 の倍数へ詰める。:192-） | 16 の倍数に切り上げた AES の出力長（通常は同じ） |
| AES → 平文 | 解除: 同じ平文をそのまま pack にし、AES の coder と bind を除き、AES の output の unpack size を除く。LZMA2 などの次の coder が packed stream を直接読む | AES の出力長 |
| 平文 → AES | 付与: 元の pack の byte を snapshot から読んで暗号化し、coder を `[AES] + 元の coder`、AES の output を元の packed input へ bind し、unpackSizes の先頭に元の pack の長さを足す | 16 の倍数に切り上げ |

  - 番号の付け替え（7z の coder の input・output の番号は folder の中で coder の順に通し番号）: 付与では AES を coder 0（input 0・output 0）にし、元の coder の input・output の番号をすべて 1 ずつ後ろへずらし、元の bind pair も同じくずらし、bind pair `(元の packed input + 1, 0)` を足し、packedInputs を `[0]`、finalOutput を元 + 1 にする。解除はその逆（AES の coder と、その output を読む bind pair を除き、番号を詰め、AES の output を読んでいた input を packed input にする）。試作の `sz_edit.recrypt` と同じ規則。
  - props は writer と同じ `53 0F` + 新しい 16 byte の IV（cycles 19、salt 無し）。folder CRC・substream・unpack size の最終出力は変えない。PackInfo の digest は、変換した pack では未定義にする。
  - 変換の平文（掛け直し・解除では KaitoKit の復号、付与では元の pack の byte）の CRC-32 と長さを記録する（V3a で使う）。
- **currentPassword の確認**（7z の AES には認証が無く、誤った password でも復号は成功して無意味な byte になる。V3a は変換の前後の平文を比べるだけなので、誤った鍵の平文を包み直しても通ってしまう）:
  - 7-Zip は、暗号化済みの書庫へ別の password で追加すると、同じ props の形（`53 0F` + IV、salt 無し、cycles 19）で password の違う folder を作る（実測 `SP/p5review/mix.7z`）。鍵の材料（salt・cycles）が同じでも鍵が同じとは限らないので、材料ごとに一つを確かめる方法は使わない。
  - 変換する AES の folder **ごとに**、reader の password を `currentPassword` にして、その folder の substream を持つ entry を substream の順に `reader.stream(entry)` で読む。folder の出力の先頭 64 KiB まで読み、その範囲で終わる entry は最後まで読んで KaitoKit の CRC の照合を通す。64 KiB を越える entry は、その先頭までの復号で KaitoKit の復号器が誤りを出さないことを確かめる（LZMA・LZMA2・PPMd などは誤った鍵で先頭から壊れる）。
  - 失敗は KaitoKit の `wrongPassword`（CRC の不一致を含む。`checksumMismatchIsWrongPassword`）をそのまま投げる（出力は残らない）。復号器の `malformed` / `truncated` も、この確認の中では `wrongPassword` にする（AES の folder の復号器の誤りは鍵の誤りと区別できない。KaitoKit が暗号化 header で同じ写し方をしている。SevenZipReader.swift:98-107）。
  - 限界: AES + Copy（`7zz a -mx0 -p`。実測 `SP/p5review/copyaes.7z`）で 64 KiB を越える entry は、誤った鍵を検出できない。doc に書き、全ての暗号化 entry を currentPassword で検証済みであることは呼出側の責務（KF の `verifyBeforeEditing`、ArchiveSession.swift:665-676。P1b D5 と同じ）とする。
  - 費用: folder 1 つにつき decoder の準備と最大 64 KiB の復号（本文 fixture の 1,064 folder で数十 ms の見込み。AC-G15 で測る）。sequential mode の最初の add で変換を書く場合（§G4）は、その前にこの確認を行う。
- 変換する AES の folder があるのに `currentPassword == nil` なら、変換を始める前に `KaitoError.passwordRequired`。
- 変換の途中の、CancellationError・wrongPassword・passwordRequired 以外のエラー（KaitoKit の `malformed` など）は `reencryptionFailed(index:name:reason:)` に包む（P1b と同じ。reason に password を含めない）。

#### G7 header の直列化と符号化

**直列化**（`SevenZipHeaderSerializer`。7-Zip の書き方と GK の書き方の両方を byte で再現する）:

- `kHeader` → `kMainStreamsInfo`（pack か folder があるとき）→ `kFilesInfo`（file があるとき）→ `kEnd`。archiveProperties と additionalStreams は書かない（S4 で除いてある）。
- 出力の file が 0 件なら、header は `01 05 00 00 00`（kHeader・kFilesInfo・0 件・kEnd・kEnd）にする。`01 00`（GK の writer の 0 件の形）は bsdtar が拒否し、7zz の 32 byte の形（next header の長さ 0）は KaitoKit が拒否する。この 5 byte は 7zz・bsdtar・KaitoKit が受理する（`SP/p5review/empty_fi0.7z`）。元が `01 00` の書庫を変えない commit（`.unchanged`）では元の byte のまま。
- 数は最小の長さの 7z の number（SevenZipRecords.swift:130-145 と同じ）。
- PackInfo: packPos、pack の数、kSize、digest（どれか定義されていれば kCRC。全部なら allDefined = 1、そうでなければ bit の列）、kEnd。
- UnpackInfo: kFolder、数、external = 0、各 folder（coder の flags = methodID の長さ | complex なら 0x10 | props があれば 0x20。complex なら入出力数、props があれば長さと値。bind pair、packed input が 2 以上なら packed index）、kCodersUnpackSize、folder CRC（どれか定義されていれば kCRC）、kEnd。coder の isComplex と props の有無は元の値を保つ（新しい coder は complex = 入出力数が 1 でない、props は LZMA2 と AES なら有り）。
- SubStreamsInfo（folder があるとき）: どれかの folder の substream の数が 1 でなければ kNumUnpackStream、substream が 2 以上の folder があれば kSize（各 folder の最後を除く）、digest は「substream が 1 で folder CRC がある folder」を除いた substream の列で、どれか定義されていれば kCRC、kEnd。
- FilesInfo: file の数、property を順に、kEnd。
  - 順: 元の `filePropertyOrder` に出た property の順を保つ（kDummy は除いて作り直す）。元に無かった property が要るときは、7-Zip の順（kEmptyStream 0x0E、kEmptyFile 0x0F、kAnti 0x10、kName 0x11、kCTime 0x12、kATime 0x13、kMTime 0x14、kStartPos 0x18、kWinAttributes 0x15）で、既にある property との相対位置に挿す。
  - kEmptyStream: stream の無い file があるときだけ。kEmptyFile と kAnti: kEmptyStream を書くときで、元にその property があったか、立つ bit があるとき（GK は全部 0 の kEmptyFile を書く）。
  - kName: external = 0、各名前の UTF-16LE と 00 00。
  - 時刻・属性・StartPos: 定義されている file があるときだけ。全部定義なら allDefined = 1、そうでなければ bit の列。external = 0。
  - **整列**: 元の `filePropertyOrder` に kDummy（0x19）があれば、7-Zip の `SkipToAligned` の規則で kDummy を置く（kName の値を 16、時刻と StartPos を 8、属性を 4 に、header の先頭から揃える。`SP/p45/sz.py` の `W.skip_to_aligned` と同じ式）。無ければ置かない。
- 性質（試験で固定する）: 元の書庫の snapshot を変えずに直列化すると、元の平文の header と byte 一致する（GK 製と 7zz 製と libarchive 製の全 fixture。0 件の書庫は上の規則で `01 05 00 00 00` になるので除く）。
- V0 で、直列化した平文の header の長さが `ReadLimits().maxMetadataSize`（既定 16 MiB。KaitoKit ReadLimits.swift:98。next header と展開した header の両方に掛かる）を越えたら、書く前に `RewriterError.unrepresentable(entry: "", reason: "7z の header が 16 MiB を越えます")` を投げる（KaitoKit でも KF の検証でも開けない出力を作らない。GK の不具合ではないので `outputVerificationFailed` にしない）。

**符号化の方針**（元の形と `options.encryptsSevenZipHeaders` から決める。`options.encryptsSevenZipHeaders` は password が要る。WriterOptions.swift:113-115）。「元の header」の分類は snapshot の `header` による: `.plain` と、AES も圧縮も無い（Copy だけの）`.encoded` は「平文」、`isCompressed` だけは「圧縮」、`isEncrypted` だけは「AES だけ」、両方は「AES + 圧縮」:

| 元の header | encryptsSevenZipHeaders | 出力 |
|---|---|---|
| 平文 | false | 平文（kHeader をそのまま次の header にする） |
| 平文 | true | AES だけの EncodedHeader（GK の writer と同じ形、SevenZipRecords.swift:107-121） |
| 圧縮（AES 無し） | false | LZMA2 の EncodedHeader |
| 圧縮（AES 無し） | true | AES + LZMA2 |
| AES だけ | true | AES だけ |
| AES だけ | false | 平文 |
| AES + 圧縮 | true | AES + LZMA2 |
| AES + 圧縮 | false | LZMA2 |

- 元が「AES だけ」か「AES + 圧縮」で encryptsSevenZipHeaders が false の行は、暗号化の予約（§G6）がある commit でだけ使う。予約の無い commit で当たれば、commit の最初（何も書く前。追加を書いた後なら cleanup）に `WriterError.invalidOption("encryptsSevenZipHeaders")` を投げる。KF はパスワードの操作以外では session の `encryptsSevenZipHeaders`（`hasEncryptedHeaders`、ArchiveSession.swift:746-757）を渡すが、これは password 以外のエラーで false を返すので、名前を黙って平文で書き出さないための安全網。平文 → AES の向き（予約の無い header の暗号化）は許す。
- LZMA2 の header: 平文の header を 1 MiB の片に切り、`LZMA2ChunkPipeline`（chunkSize 1 MiB、`resolvedCompressionThreads`）で符号化し、`SevenZipFolderEncoder` の規則で一つの LZMA2 stream にする（5.7 MB で約 0.2 s、+7 %）。folder は `[LZMA2]` か `[AES, LZMA2]`、unpackSizes は `[平文長]` か `[LZMA2 の長さ, 平文長]`、folder CRC は平文の CRC-32（定義する）。SubStreamsInfo は書かない（GK の :107-121 と試作と同じ）。
- EncodedHeader の StreamsInfo: `kEncodedHeader` → PackInfo（packPos = header の pack の位置 − 32、1 本、kSize）→ UnpackInfo（folder 1 つ、folder CRC）→ kEnd。header の pack は最後の main pack の直後に置き、次の header はその直後。
- 開始 header: version は `00 04`（7-Zip の更新と GK の writer と同じ。元が 0.3 の libarchive 製でも 0.4 にする）、nextHeaderOffset・Size・CRC、その 20 byte の CRC（SevenZipRecords.swift:29-38 と同じ式）。`SplicedArchiveOutput` の `finalPatch` で最後に書く（§G8）。

#### G8 commit の実行

segment の実行・ftruncate・fsync・finalPatch・V5・一時ファイル・cleanup は `SplicedArchiveOutput` が行う（ORDER45 §1.1、P2 §G8 の意味のまま）。7z が決めるのは、作り直す folder の一時ファイルへの符号化、`SplicedCommitPlan`（segment の列・header・開始 header）、V0・V1・V3・V3a だけ。

1. `perform` の中で state を committing にする。checkUnchanged → 追加の writer があれば `endSevenZipEntries` → header の暗号化を外す行に予約無しで当たれば `invalidOption` → 暗号化の予約があれば G6 の確認 → 計画（G3。作り直す folder の長さはまだ決まっていない）→ 取消しの検査 → `meter = CommitProgressMeter(total: G3-5 の作業量, progress:)` → `meter.start()`。
2. 作り直す folder を §G5 の一時ファイルへ符号化する（入力の byte で `meter.advance`）。sequential mode の最初の add で同じ入力を符号化済みなら使い直す。
3. 最終計画: 一時ファイルの長さで各 folder の出力位置を決め、平文の header を直列化し（G7）、V0 を行い、方針どおり符号化して header の pack と next header の byte（`terminal`）を作り、開始 header（`finalPatch`）を作る。ここまで output の segment は一つも書いていない（V0 の 16 MiB の上限で止めても、書いたのは sequential mode の最初の add の prefix と追加の pack だけで、cleanup で消える）。
4. `SplicedCommitPlan` を作り、`output.commit(plan, meter: meter, verify: V1–V3a)` を呼ぶ:
   - `prefix`（出力の順）:
     - `[0, 32)`: 32 byte の 0 の `literal`（完成前の出力をどの reader も開けない形にする。SevenZipWriter と同じ規律。clone mode でも書く）。
     - `.carry(k)`: snapshot（sequential mode では原本）の元の pack の範囲の `source`。出力位置が元と同じなら、clone mode では部品が書かない。
     - `.convert(k, …)`: `generated`（G6 の byte。長さは事前に決まる）。
     - `.reencode(k, …)`: `generated`（一時ファイルから写す。長さは 2 で確定している）。
   - `appended`: 追加の folder の `[P_add, appendedEnd)`。最終計画の位置と同じなら部品は書かない（add の時に書いてある）。違えば部品が §G4 の再配置を行う。
   - `terminal`: header の pack と next header。
   - `finalLength`: next header の終わり（元の header・余分な byte・詰めた後ろの残りを落とす）。
   - `finalPatch`: `(0, 開始 header)`（version `00 04`、nextHeaderOffset・Size・CRC、その 20 byte の CRC）。
   - `formatVerificationUnits`: V1 の H + V3 の unpack size + V3a の pack の byte。
5. 変えない commit（戦略 `.unchanged`）の plan は、`prefix = [source(0 ..< 原本の長さ)]`、`appended = nil`、`terminal` は空、`finalPatch = nil`。clone mode では何も書かず、sequential mode では全体を写す（部品の規則）。
6. 部品の中の順: 再配置（要るとき）→ segment → terminal → `ftruncate(finalLength)` → fsync → `finalPatch` → fsync → V5（= 本書の V2）→ verify（V1・V3・V3a）→ close。自己照合の失敗は `UpdaterRouteError.outputVerificationFailed(reason:)` で、部品が output と一時ファイルを消す。
7. `meter.finish()` → checkUnchanged → snapshot と一時ファイルを消す → `lastCommitStrategy`（`SplicedCommitStrategy` の `.sequential` / `.relocatedAppend` を優先し、それ以外は G3-4）と `lastCommitStatistics` を記録 → committed。
8. checkUnchanged の時点: open、output の作成の前後、commit の開始、fsync の後。

**書く量**（clone mode）:

| 操作 | 書く量 |
|---|---|
| 改名、stream の無い entry の削除 | header（と header の pack）+ 64 B（先頭の 0 と開始 header） |
| 末尾の folder の削除 | 同上（切り詰め） |
| 追加だけ | 追加の pack（add の時に一度）+ header + 64 B |
| 途中の folder の削除 | 後ろの pack 全部 + header + 64 B |
| solid の一部削除 | 作り直した folder（一時ファイルと出力に一度ずつ）+ 後ろの pack + header + 64 B |
| solid の一部削除と追加（再配置） | 上 + 追加の pack の往復（一時ファイルへ書き、output へ写す） |
| 暗号化の変更 | 全 pack（掛け直し）+ header + 64 B |
| 変えない commit | 0（clone） |

sequential mode では、常に output 全体を一度ずつ書く（再圧縮はしない。作り直しでは一時ファイルの分、再配置では追加の pack の往復が加わる）。

#### G9 自己照合（書いた量に比例。commit の中、fsync の後）

- **V0 帳簿**（I/O なし、計画の後と header の直列化の前）: 出力の pack が 32 から隙間なく並び、`mainPackEnd` で終わる。運ぶ folder の記述（coder・props・bind・packed input・unpack size・CRC・substream）が元と同じで、pack の大きさも同じ。file と substream と folder の対応の数が合う。追加の folder の数と writer の record が合う。平文の header の長さが上限以下（§G7。越えれば `unrepresentable`）。
- **V1 構造**: output をパスで開き直さず、`SplicedArchiveOutput` が保持する output の記述子を dup した読取専用の `ZipUpdateSource(duplicating:)` で、`ArchiveReader.open(source:sourceURL: output, options:)`（G1-6 と同じ options、password は `options.password`、`recordsSevenZipEditLayout = true`）として解析する。KaitoKit の snapshot が計画の model と一致すること: folder（coder の methodID・入出力数・isComplex・props、bind、packedInputs、unpackSizes、CRC）、pack の範囲と digest の有無、substream、file（生の名前・時刻・属性・フラグ・StartPos）、header の形（平文 / encoded、isEncrypted・isCompressed が方針どおり）、`baseOffset == 0`、`packPosition == 0`、`unrepresentedReason == nil`、version。開始 header と次の header の CRC は KaitoKit の open が照合する。**KaitoKit の解析は GK の直列化から独立しているので、直列化の誤りをここで捕まえる。** 費用は header の解析 1 回（10 万件で約 0.2 s）。
- **V2 動かした運ぶ pack**: `SplicedArchiveOutput` の V5 そのもの（書いた source segment ごとに、output の範囲と snapshot（sequential mode では原本）の同じ範囲を 4 MiB ずつ pread し memcmp。書かなかった（clone の）範囲は読まない。読む量は書いた量の 2 倍まで）。7z の側で二重に実装しない。
- **V3 符号化した folder**: 追加の folder と作り直した folder について、V1 の reader で、その folder の substream を持つ entry を substream の順に `stream(entry)` で最後まで読む（KaitoKit が LZMA2 を復号し、各 substream の CRC を照合する。AES は `options.password`）。読む量はそれらの folder の unpack size。
- **V3a 変換した folder**: 目標が AES なら V1 の reader の `sevenZipDecryptedPackedStream(folder:packedInput: 0)`（KaitoKit が `options.password` から独立に鍵を導く）、目標が平文なら output の pack の範囲を直接読み、CRC-32 と長さが G6 で記録した平文の値と一致すること。次の coder 以降は変えていないので、平文の一致で復号の同一を示す。
- 失敗の reason は照合の名前と folder / file の index（password を含めない）。V2（部品の V5）と V3a の平文の pack の直接の読み取りは `SplicedArchiveOutput.verificationReadObserver` に報告する。V1・V3・V3a の KaitoKit を通す読み取りは、`ZipUpdateSource.readObserver` の、dup した記述子の報告で分けて見る。どちらも copy engine の観測には数えない。

#### G10 進捗・取消し・後始末

- 進捗は `ArchiveUpdater.CommitProgress`（`CommitProgressMeter`）。total は G3-5 の作業量（上界）で、計画の後に確定し以後変えない。4 MiB 以上増えたときと最後に通知し、単調で、completed は total を越えず、`finish()` で最後に completed == total（`total == 0` の変えない commit もある）。progress の throw は取消しと同じ（failed、後始末、原本は無傷）。
- 取消し: copy engine の片ごと、pipeline の待ち（OrderedChunkPipeline の take）、`generated` の closure の片ごと、作り直しの一時ファイルへの符号化の片ごと、folder ごと、V3 の entry ごと、G6 の確認の中、再配置の往復の片ごと。どこで止まっても output・snapshot・一時ファイルは残らない。

#### G11 SPI と試験の hook

- `@_spi(Testing)`: `CommitStrategy`、`lastCommitStrategy`、`lastCommitStatistics`（戦略、書いた運ぶ pack の byte、追加の pack の byte、変換した pack の byte、作り直した folder の数と入力・出力の byte、平文の header と格納した header の byte、照合で読んだ byte、段ごとの時間: plan・reencodeScratch（一時ファイルへの符号化）・packs・header・selfCheck）、`testingDisablesClone`。
- internal（`@testable` で使う）: `SevenZipUpdater.testingFault: TaskLocal<Fault?>`（`flipMovedPackByte`・`flipAppendedPackByte`・`flipReencodedPackByte`・`flipConvertedPackByte`・`corruptSerializedName`・`dropLastPackFromModel`。fsync の前に output か model を壊し、V0–V3a のどれかが捕まえることを確かめる）、`SevenZipUpdater.testingLayoutMismatch: TaskLocal<Bool>`（S6 の照合を壊す）、`SplicedArchiveOutput.verificationReadObserver`（共有）、`SevenZipAESEncryptor.testingIV`、P1-G の `ArchiveSourceSnapshot.testingCloneError`（clone の errno の注入）。
- 変更できる global 状態は TaskLocal だけ。

#### G12 ArchiveRewriter との違い（出力の形）

| 性質 | ArchiveRewriter（fallback と従来の設定） | SevenZipUpdater |
|---|---|---|
| 運ぶ folder | 全部復号し、1 file = 1 folder の LZMA2 に作り直す（solid・BCJ・BCJ2・PPMd が消える） | byte のまま（coder・props・IV・CRC も） |
| solid の一部削除 | 全体の作り直しの一部 | その folder だけを一つの solid な LZMA2 folder に作り直し、同じ位置に置く |
| header | 平文か AES だけ | 元の形に合わせる（§G7 の表） |
| 名前 | NFC、directory は末尾 `/` | 運ぶ file は生の UTF-16LE のまま（改名と追加は writer の規則） |
| 時刻・属性 | mtime を秒へ、ctime / atime は消える、属性は mode から作り直す | 生の値のまま（追加は writer の規則） |
| anti | 実体の空の項目になる | そのまま |
| stream の無い entry の順 | 生存 entry の順 | 元の位置のまま（7zz は先頭へ寄せる） |
| 部分的な暗号化 | options.password で全部を暗号化し直す | folder ごとにそのまま運ぶ。追加・作り直しは §G5・§G4 の規則 |
| 追加の位置 | 設定どおり | 常に末尾 |
| SFX の prefix・末尾の余分な byte | 捨てる | SFX は requiresRewrite、余分な byte は捨てる |
| 0 件の出力 | `01 00`（bsdtar が拒否） | `01 05 00 00 00`（7zz・bsdtar・KaitoKit が受理） |
| 開始 header の version | `00 04` | `00 04` |

### CONSTRAINTS

- 出力の byte: `ArchiveWriter.create` の 7z は P5-G の直前の commit と一致する（平文は byte、AES は `testingIV` を注入して byte。0 件の `01 00` も変えない）。`ArchiveUpdater`・`ArchiveRewriter`・`TarUpdater`・`CompressedTarUpdater`・`LHAUpdater` は変えない。
- `SplicedArchiveOutput.swift` と `ZipUpdateLayout.swift` を変えない（ORDER45 §1.1 と P4-G-b のもの）。変える必要が出たら止めて報告する。P2・P3・P4 の試験と `SplicedArchiveOutputTests` を変えずに通す。
- 原本を書かない（O_RDONLY 以外で開かない。rename・chmod・chflags・置換をしない）。読む inode と書く inode は常に別。その場で byte をずらさない（読むのは snapshot か原本、書くのは output）。
- 読み取り: copy のために読むのは書く運ぶ pack の範囲と、作り直しの一時ファイルだけ。作り直しのために復号するのは一部を失う solid folder だけ。変換のために読むのは変換する folder の pack と、G6 の確認（folder ごとに先頭 64 KiB までの復号）だけ。照合の読み取りは G9 の範囲だけ。追加の byte は、再配置のとき以外は読まない。
- 検査を弱めない: KaitoKit の open、`validateRepresentability` の全件、checkUnchanged、V0–V3a を残す。KF の公開前の検証（P0）は別に残る。
- 新しい public は §0.2 のものだけ、`@_spi(Testing)` は G11 のものだけ。`UpdaterError`・`RewriterError`・`WriterError`・`UpdaterRouteError` に case を足さない。
- KaitoKit の SPI を使うファイルだけ `@_spi(SevenZipEditLayout) internal import KaitoKit`（通らなければそのファイルだけ `@_spi(SevenZipEditLayout) import KaitoKit` にして報告）。GK の公開 API に KaitoKit の SPI の型を出さない。

1. 単一ファイルの 7z の即時編集・保存時モードの保存・パスワードの設定 / 変更 / 削除を `SevenZipUpdater` で行う（`.update(.sevenZip)`）。rewriter へ戻る場合は、同じ publish の中で mutate の前に切り替える（P2-A と同じ形）。

### DESIGN

#### A1 mode・経路・評価

1. capability は構造だけで決まる: 単一の 7z は `.update(.sevenZip)`。表現可能性の門番は今と同じなので、編集できる書庫の範囲は変わらない。
2. 経路は publish のたびに決める: `let mode = base.resolved(with: options)`（P2-A）。`.beginning` → `.rewrite(.sevenZip)`。
3. 経路の一覧:

| 状況 | 経路 |
|---|---|
| 解決が `.rewrite(.sevenZip)`（追加位置が従来） | `rewriteBranch(format: .sevenZip)`（今日の rewriter） |
| `.update(.sevenZip)` で `SevenZipUpdater.open` が `requiresRewrite`（S0–S6） | 同じ publish の中で mutate の前に `rewriteBranch(format: .sevenZip)`（作業ファイルは作られていない） |
| `.update(.sevenZip)` | updater（改名・追加・削除・solid の一部の作り直し） |
| パスワードの操作で `sevenZipAssessment?.canReencrypt != true` | 最初から `.rewrite(.sevenZip)`（今日と同じ） |
| パスワードの操作で `.update(.sevenZip)` | updater の `reencryptExistingEntries` |
| GK の `outputVerificationFailed` | 公開しない（`ArchivePublicationError.verificationFailed`）。自動で書き直しへ回さない |
| GK の `UpdaterError.sourceChanged` | そのまま失敗（原本は未変更） |
| 分割セット | `.rewrite(.sevenZip)` のまま |

4. `sevenZipAssessment` は注意書きとパスワードの操作の経路だけに使う。通常の編集の経路は open の判定で決まる（`assess` と open は同じ関数で判定するので、書庫が変わらない限り一致する）。

#### A2 publish の `.update(.sevenZip)` の枝

ORDER45 §3.2 の形（P2-A §A3、P4-A §A2 と同じ）。`requiresRewrite` を捕まえるのは open だけ。

```swift
case .update(.sevenZip):
    outputFormat = .sevenZip
    work = directory.appendingPathComponent("archive." + ArchiveCreationPlan.filenameExtension(for: .sevenZip))  // "archive.7z"
    try willOpenUpdater?()                       // この枝で一度だけ
    var updater: SevenZipUpdater?
    do {
        updater = try ArchiveStageDiagnostics.measure(.updaterOpen) {
            try SevenZipUpdater.open(url: archive, password: password, output: work, options: options)
        }
    } catch UpdaterRouteError.requiresRewrite(let reason) {
        didFallBackToRewriteForTesting?(reason)    // DEBUG（P2-A）
    }
    if let updater {
        publishedMode = mode
        try ArchiveStageDiagnostics.measure(deferredPlan == nil ? .mutate : .replay) { try mutate(updater) }
        try ArchiveImportPlan.checkCancellation(progress)
        progress.totalUnitCount += 1000       // 1000 単位を足すのはここだけ（呼出側は足さない）
        #if DEBUG
        try willCommitUpdaterForTesting.get()?()
        #endif
        do {
            try ArchiveStageDiagnostics.measure(.commit) { try updater.commit(progress: /* P1b の CommitProgress → Progress の写し */) }
        } catch UpdaterRouteError.outputVerificationFailed(_) { throw ArchivePublicationError.verificationFailed }
        try preserveAttributes(from: archive, to: work, includingCreationDate: true)
    } else {
        publishedMode = .rewrite(.sevenZip)
        try rewriteBranch(format: .sevenZip)     // willOpenUpdater を呼ばない（ORDER45 §1.2）。lstat(work) が ENOENT であることを確かめてから
    }
```

- `password` は publish の引数（session の password。入力の復号用）、`options` は出力用（`options(for:)` と `ArchiveEncryptionSettings.applying`）。
- 進捗の写しは P1b・P2-A と同じ（`total == 0` を完了として 1000 単位を満たす）。7z では `publish(…, commitProgress:)` に値を渡さない（渡されても 7z の枝では使わない。二重に数えないため）。
- 7z の publish は `sessionReader`（P3-A）を渡さない（nil）。session の reader の `reopen()` を呼ばない（P4-A の LHA と同じ）。
- 公開前の検証は今のまま（`ArchiveVerifiedFileSource` → `ArchiveReader.open(source:sourceURL:options: .kaitoFinderVerification(password: options.password))` → `expectedOutput.resolving(publishedMode).validate(verified, format: .sevenZip)`）。検証 reader は option を継ぐので snapshot を持ち、P1-A の採用の後の `capability_probe` で `assess` が使える。
- エラーの写しは P2-A と同じ。`outputVerificationFailed` は `verificationFailed`（`UpdaterError.invalidArchive` にしない。S5 の診断に updater の自己照合の case があれば、P2-A・P4-A と同じものを使う）。`reencryptionFailed` は P1b の文言。KaitoError はそのまま。
- 作業ディレクトリ、原本の同一性（`ArchiveSetIdentity`）、公開の境界、undo の退避は今のまま。`didCommitForTesting` の時点の作業ディレクトリは `["archive.7z"]` だけ（fallback でも同じ）。

#### A3 パスワードの操作

- `updatePassword`（ArchiveSession.swift:678-708）の 7z:
  ```swift
  let options = output.applying(to: writerOptions(.sevenZip), format: .sevenZip)
  var mode = capabilities.mode!.resolved(with: options)          // .update(.sevenZip) か .rewrite(.sevenZip)
  if case .update = mode, capabilities.sevenZipAssessment?.canReencrypt != true { mode = .rewrite(.sevenZip) }
  // publish(archive:, mode:, options:, password: password, progress:,           // commitProgress は渡さない
  //         expectedOutput: .init(projected: reader.entries, mode: mode, sevenZipEncryption: options.password != nil)) {
  //     editor in try (editor as? any ArchiveReencrypting)?.reencryptExistingEntries(currentPassword: password) }
  ```
  - 進捗は `.update` でも `.rewrite` でも今日の `totalUnitCount = 1`。`.update` の枝が updater を開けたときに 1000 を足し、fallback の rewriter の枝は今日どおり entry の数を足す（どちらでも最後に completed == total）。
  - mutate の閉包は、editor が `ArchiveReencrypting` でなくても失敗しない（open の `requiresRewrite` で rewriter へ戻った場合。rewriter が options で全体を暗号化し直す。今日と同じ）。ZIP の閉包は P1b のまま（`ArchiveUpdater` でなければ `staleSelection`）で、形式ごとに分ける。
  - 公開後の password と `encryptsSevenZipHeaders` の採用、再読込は今のまま（:702-707）。
- `savePending`（:538-585）で `outputEncryption` があり 7z のとき: 今の `mode = .rewrite(format)`（:550-555）をやめ、`mode = capabilities.mode!.resolved(with: output)`、`canReencrypt` が true でなければ `.rewrite(.sevenZip)`。replay は削除・改名の後、追加の前に `reencryptExistingEntries(currentPassword: password)` を呼ぶ（§SCOPE の `ArchiveSaveReplayPlan`）。`expectedOutput` に `sevenZipEncryption` を渡す。進捗に 1000 を足さず、`commitProgress` も渡さない（`.update` の枝が足す）。
- `savePendingSplit` は変えない（分割は `.rewrite`）。ZIP のパスワードの操作は P1b のまま（mutate の型の判定だけを `ArchiveReencrypting` に広げる。進捗の足し方も P1b のまま）。

#### A4 期待する出力（ArchiveOutputProjection）

- `.update(.sevenZip)`（SevenZipUpdater の意味）:
  - 生存 entry を元の順に並べ、名前だけを改名後にする。種類と size は元の entry のまま（root を除かない、symlink と directory の size を変えない）。7z に hard link は無い。
  - 追加は今日と同じ期待（種類だけ）で、生存 entry の後ろに呼出し順（即時は `plan.items` の順、保存時は `plan.projected` の追加 → 作成フォルダの順）。
  - `validate` は P2-A の `.update` と同じく並び順も照合する。
- `sevenZipEncryption: Bool?`（非 nil のときだけ、multiset / 並び順の照合とは別に）: 出力の各 entry について、stream を持つ entry（`formatSpecific["emptyStream"] == "false"`）の `isEncrypted` が値と等しく、stream の無い entry は `isEncrypted == false`。渡すのは 7z のパスワードの操作と、`outputEncryption` を含む 7z の保存（`.rewrite` へ戻った場合も。rewriter も stream を持つ全 entry を暗号化するので同じ期待になる）。
- `.rewrite(.sevenZip)` と `.inPlace` は今のまま。

#### A5 注意書きと文言

- `editNotice(options:onSave:)`（P3-A）に次を足す（resolved = `mode?.resolved(with: options)`）:
  - resolved が `.rewrite(.sevenZip)`: 既存の「編集する / 保存するとアーカイブ全体を再圧縮します」（P3-A の規則のまま）。
  - resolved が `.update(.sevenZip)` で `sevenZipAssessment == nil` か `updatable == false`: 同じ既存のキー（open で書き直しに戻るため）。
  - resolved が `.update(.sevenZip)` で `hasSolidFolders`: 新しいキー「ソリッドブロック内の項目を削除すると、そのブロックを再圧縮します」（即時と保存時で同じ。en: "Deleting an item inside a solid block recompresses that block."）。
  - それ以外は nil。
- 新しいキーは 26 言語すべて `translated`。既存の「再圧縮します」のキーの各言語の語彙に揃え、「ソリッドブロック」は各言語の 7-Zip の用語（en: solid block）にする。既存のキーの訳は変えない。
- 新しい文言は S25 の前に利用者の了承を得る。了承が無い場合: 新しいキーを作らず、`hasSolidFolders` の規則を除く（solid の書庫では注意書きを出さない）。AC-A8 は対象外になる。
- P3-A の `editNotice` の圧縮 tar の規則は、三形式（`.tarGzip`・`.tarBzip2`・`.tarXZ`）に限られている（ORDER45 §1.3、または P4-A）。限られていなければ S25 の着手の門で止まる（`.update(.sevenZip)` が「`compressedTarAssessment == nil`」の規則に当たるため）。

#### A6 分割・APFS 以外・格納順・名前・暗号化の見え方

- 分割 7z（`.7z.001` …）: `.rewrite(.sevenZip)` のまま。設定は rewriter に効く（追加は末尾）。
- APFS 以外（HFS+ / exFAT / SMB）: SevenZipUpdater の sequential mode（出力全体を一度書く。再圧縮しない）。undo は今日どおり APFS だけ。sequential mode の output は O_EXCL の新しいファイルなので、原本の xattr（Finder のタグなど）は運ばない。mode と作成日は `preserveAttributes`、quarantine は今の `additionalQuarantine` の規則による（今日の rewriter と同じ。clone mode では clone が xattr を運ぶ）。`fclonefileat` が ENOTSUP / EXDEV 以外の errno を返す volume では、編集が `WriterError.io` で失敗する（P1-G D7 の決定のまま）。
- 格納順の列: 既定（末尾）では、既存の項目の相対順が変わらず、追加は最後に来る。stream の無い項目の位置も変わらない（7zz で更新すると先頭へ寄る）。
- 名前: 運ぶ項目の名前の byte（NFD など）が変わらない（今日の rewriter は NFC にし、directory に `/` を足していた）。
- 部分的に暗号化された 7z: 既存の項目の暗号化の状態を保つ（今日は全体を暗号化し直していた）。追加した項目は今日と同じく session の password で暗号化する。release notes に書く。

#### A7 診断と P0b

- `.update(.sevenZip)` の即時編集・保存・パスワードの操作は stage `.updaterOpen`・`.mutate` / `.replay`・`.commit` を出し、`.rewriterOpen` は出さない。fallback では `.updaterOpen` の後に `.rewriterOpen`。
- `PerformanceProbeTests` / `ArchivePerformanceProbe` は、7z の updater の commit の後に `@_spi(Testing) import GyoshukuKit` で `SevenZipUpdater.lastCommitStatistics` を読み、`PROBE-7Z` 行に出す（戦略、書いた pack の byte、作り直し、変換、header の byte、段の時間）。TSV の既存の列の意味は変えない。
- `testArchivePasswordEditsWhenEnabled`: `KAITOFINDER_PROBE_ENCRYPTION` に `7z` を受け付け、GK で作る 7z の AES の fixture（entries は平文の header、payload は暗号化した header）で、設定・変更・削除と保存時の変更を測る（§SCOPE）。
- 基準: B-P5（S21 の三つ組）にはこの 7z のパスワードの probe が無い。パスワードの操作の基準は、同じ S25 の build で `KAITOFINDER_PROBE_ADDITION_PLACEMENT=beginning`（`.rewrite(.sevenZip)`、今日と同じ全体の再圧縮）の同じ probe で採る。従来の設定の 7z の即時編集・保存の行も、この knob で測る。
- direct の 7z は `SevenZipUpdater.open(url:password:output:options:)` を `.updaterOpen` で測る。

### ACCEPTANCE CRITERIA

- **AC-A1 `SevenZipUpdateRoutingTests`**: 単一の `.7z`（大文字の拡張子と内容で判定するものを含む）で capability が `.update(.sevenZip)`、`sevenZipAssessment` が期待どおり（GK 製・7zz の solid・BCJ2・archiveProperties・packPos = 16 の fixture）。分割セットは `.rewrite(.sevenZip)`。読み取り専用の判定は今日と同じ（`:`・`\` を含む名前など）。`resolved(with:)` と注意書き（即時と保存時）の表を、追加位置 × 評価（updatable・solid・canReencrypt）で確かめる。
- **AC-A2 `SevenZipUpdateEditTests`**（GK 製・7zz 製・libarchive 製 `lib.7z` の fixture、平文と AES）: 削除（先頭・末尾・solid の一部）・改名（同長・異長・フォルダ）・追加・新規フォルダ・置換・移動がそれぞれ成功し、`lastCommitStrategy` が期待どおり。`didCommitForTesting` の時点の作業ディレクトリが `["archive.7z"]` だけ。原本は rename まで不変。公開後の書庫で、触らない folder の pack の byte が原本と同一。P1-A の採用が起き、entries が `ArchiveReader.open(url:)` と一致。DragInTests と同じ属性（mode・quarantine・xattr・作成日時）が保たれる。全件削除の後の追加が成功し、capability が読み取り専用にならない。
- **AC-A3 `SevenZipUpdateDeferredSaveTests`**: 5 変更の保存と改名だけの保存が updater の 1 回の commit になり、保存後の格納順が予約中の表示の順（削除分を詰めたもの）と一致する。`addDirectory(_:modificationDate:ownerIDs:)` で予約日時の directory が書かれる。`outputEncryption` と追加を含む保存（GK 製の非 solid の書庫）で、`lastCommitStrategy` が `.relocatedAppend` でない（暗号化の予約が追加より先）。ZIP の同じ保存の出力が、P1b の順（追加の後の予約）のときと同じ（`ArchiveUpdater` の順序非依存を確かめる）。

## リスクと未決（オーケストレータが受け入れ時に見る点）

1. **直列化の誤りの影響範囲**: header の誤りは書庫の全 file を読めなくする。担保は、(a) 元の header との byte 一致の試験（GK 製・7zz 製の全 fixture）、(b) V1（KaitoKit の独立した解析と計画の構造の照合）、(c) 差分の試験、(d) 7zz・bsdtar・KaitoKit の互換の試験、(e) KF の公開前の検証 open と並び順の照合。公開前に失敗すれば原本は無傷。
2. **7z の AES に認証が無い**: 誤った currentPassword での掛け直しは、無意味な平文を正しく包み直してしまい、V3a（変換の前後の平文の比較）も通る。7-Zip は、暗号化済みの書庫へ別の password で追加すると、同じ props の形で folder ごとに password の違う書庫を作る（実測 `mix.7z`。旧版の「7-Zip は作らない」は誤り）。GK は変換する AES の folder ごとに先頭 64 KiB まで復号して確かめ（G6）、KF は編集前に全暗号化 entry を復号する（`verifyBeforeEditing`）。GK 単体で残る穴は AES + Copy（`-mx0 -p`）の 64 KiB を越える entry だけで、design.md に書く。
3. **大きな solid block の削除**: 7zz の既定の書庫（書庫全体が一つの solid folder）から 1 件を消すと、その folder 全体を復号・再圧縮する。費用は今日の全体の書き直しと同程度（P0b の本文 7z ≈ 11 s。旧版の「約 20 s」は根拠が無い）で、AC-G15 と受入計測で実測を報告する。出力は solid のまま（今日は非 solid になり大きくなる）。新しい注意書き（§A5）で知らせる。文言は利用者に確かめる。
4. **header の形の選択**: 元が圧縮なら LZMA2（1 MiB の片、並列）で書く。7-Zip は LZMA（030101）で書くが、GK は raw LZMA を作れない（Apple の API は xz の LZMA2 だけ）。LZMA2 の header は 7zz 26.03・bsdtar 3.7.4・KaitoKit で確かめた（`SP/p5spec/hdr_lzma2.py`、本レビューで再確認）。Archive Utility での読み取りは確かめていない（bsdtar で近似するが、同じ実装だとは確かめていない）。古い 7-Zip（9.20 より前）は LZMA2 を読めないが、GK が書く file の folder も LZMA2 なので今日と同じ前提。
5. **session の reader の再利用**: updater は snapshot を KaitoKit で解析し直す（10 万件で約 0.2 s）。安全のため（pack の digest が無い 7z では、open の後の同じ inode の書き換えを捕まえる手段が clone しかない）P2 の TarUpdater と同じ形にした。V1 と KF の検証 open で、さらに 2 回の解析がある。合わせて見込みに入れてあり、超過したら後続の課題（V1 の reader を KF へ渡す、など）にする。
6. **`hasEncryptedHeaders` の再解析**（ArchiveSession.swift:746-757、password のある 7z の再読込ごと）と `verifyBeforeEditing` の全復号は残る。前者は updater が header の形を知っているので省けるが、本仕様の範囲外。
7. **新しい public protocol**: `ArchiveReencrypting` を足し、P1b の `ArchiveUpdater` を適合させる（メソッドは既存。挙動は変えない）。KF の replay と `updatePassword` が形式に依らず書ける。
8. **SFX・分割**: SFX の 7z は rewriter のまま（stub は今日どおり落ちる）。KF は rewriter の出力（stub の無い 7z）を `.exe` の名前で公開するので、SFX として動かなくなる。今日と同じで P4 の LHA とも同じ決定だが、「SFX は読み取り専用にする」選択肢を利用者に諮る（本仕様では変えない）。分割 7z は P12。
9. **P4 との名前と部品**: `UpdaterRouteError` と `ZipUpdateSource(duplicating:)` は P4-G-b のもの（P4 §0.2）。`SplicedArchiveOutput` は ORDER45 §1.1 で P2-G が作る部品で、P5-G は変えない。S24 の着手の門で、`generated`・`finalPatch`・`makeScratch`・`CommitProgressMeter` があることを確かめる。P3-A の圧縮 tar の枝の条件と `editNotice` の規則は、ORDER45 §1.3 か P4-A で三形式に限られている（S25 の門）。
10. **未検証の項目**（design.md に書く）: anti の item を持つ実際の書庫（Step 0 で組むものだけ）、4 GiB を越える entry（AC-G17 は Copy の疎な folder だけ）、kStartPos を持つ実際の書庫、SFX の stub の保持、BCJ2 の暗号化の変換、古い 7-Zip と Archive Utility での LZMA2 の header。
11. **0 件の書庫**: updater は `01 05 00 00 00` を書く（3 つの reader が受理）。残る非互換は二つで、本仕様では直さない: `ArchiveWriter.create` と rewriter の 0 件の出力 `01 00` は bsdtar が拒否する（AC-G2 の byte 一致の約束のため変えない）、7zz の全件削除の出力（32 byte）は KaitoKit が拒否する（`SevenZipReader.swift:298-300`）。後続の課題として記す。
12. **header の暗号化を外す安全網**: KF の `hasEncryptedHeaders` が誤って false を返すと、今日の rewriter は名前を平文で書き出す。updater は予約の無い commit で AES の header を平文にしないので、編集が `invalidOption` で失敗する（公開しない）。この失敗が起きたら、KF の検出を直す（`SevenZipAssessment` に header の暗号化の有無を足して session の値を決める、など。リスク 6 の再解析の省略と一緒に扱う）。
13. **canReencrypt の保守性**: `canReencrypt` は、変換の要らない folder（目標と同じ状態の平文の BCJ2 など）にも変換の形を求める。安全側なので本仕様では変えない。パスワードの削除で平文の BCJ2 folder があるだけで全体の書き直しになる。
14. **作り直しの一時ファイル**: 方針 7（作業ファイル 1 つへ直接書く）の例外で、作り直した folder の圧縮後の byte だけが対象になる（ORDER45 §7-1）。7zz の既定の書庫の 1 件削除で、書く量が作り直した folder の分だけ増える。AC-G15 と受入計測で時間を分けて報告する。
15. **advisor**: 反証レビューは advisor が使えず、二人目の目を通していない。P4 との調停（ORDER45）は advisor に諮った。受け入れの時の advisor の相談は CLAUDE.md の規則どおりに行う。
