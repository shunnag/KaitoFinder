### 0.3 用語

- **session**: 一つの呼出しが報告する `ArchiveUpdater.CommitProgress` の列。
  - P6 で新設する session（add・finishAdditions・rewriter の commit）は `CommitProgressMeter` を使い、次を満たす:
    - total は最初の (0, total) で確定する。
    - completed は単調で、total を越えない。
    - 成功したら、最後に (total, total) を一度通知する（total == 0 もある）。
    - callback は呼出しの thread で同期的に呼び、保持しない。
    - throw は取消しと同じ扱い（同じ error で失敗し、editor は failed になり、自分の作った出力・一時ファイルだけを消す）。
    - 通知は ⌈total / 4 MiB⌉ + 2 回以下。
  - 既存の updater の commit の session は ORDER23 §1 の契約で、最後の total が変わりうる（§0.2）。KF はどちらにも通知ごとの比で対応する。
- **追加元の byte**: `add(contentsOf:)` が読む、ディスクの通常ファイルの内容の byte。header・名前・symlink の target は数えない。
- **圧縮の待ち**: add が受け取ったが、まだ出力へ書いていない入力（並列の圧縮器の in-flight と組立中の buffer）。

### 0.4 決めたこと（と採らなかった案）

1. **値の型は `ArchiveUpdater.CommitProgress` を使い回す**。
2. **追加の session は呼出しごと**。
   - total は、その呼出しが読む通常ファイルの byte の和。通常ファイルは writer の lstat の `st_size`。directory の URL は、progress を渡したときだけ、再帰と同じ列挙で事前に lstat する。
   - completed は、writer へ渡した byte（読取側で数える）。
   - 採らない案: 書いた byte で数える案、差分だけを渡す案（理由は草案のまま）。
3. **圧縮の待ちは `finishAdditions(progress:)` の session で報告する**。
   - P1–P5 の `commit(progress:)` の契約は変えない。
   - 待ちの上界: tar.xz は (threads + 1) × 16 MiB、**7z は threads × 16 MiB**（SevenZipWriter.swift:56-74 は、組み立ててから、枠を待つ submit へ渡す）。
   - text では数秒になる（16 MiB の片で約 6.7 s）。
4. **rewriter の `.end` は add で読まない**。add の session は (0, 0) を二度通知し、読取は `commit(progress:didCarry:)` の session に入る。
5. **KF は byte の意味を解釈しない**。通知ごとの比を、KF が決めた予算へ写す。total が一定だとは仮定しない。
6. **`commit(progress:)` を `ArchiveEditing` の要件にしない**（理由は草案のまま）。
7. **新しい UI 文言は無い**。
8. **「移動」は、書庫の中の移動と、その commit が record を動かす byte を指す**。既存の `commit(progress:)` を KF が常に写すことで扱う（今日は暗号化の変更のときだけ写している: ArchiveSession.swift:554-556、:695-697）。
9. **progress は出力を変えない観測値なので、既定の実装は捨ててよい**（ownerIDs とは違う）。
   - 既定の実装は (0, 0) を通知し、ownerIDs が nil なら `add(contentsOf:as:)`、あれば `add(contentsOf:as:ownerIDs:)` を呼び、(0, 0) を通知する。
   - P2-A §A5 の「nil なら 2 引数」の振り分けと同じ。試験用の editor（`RecordingEditor.plainFileCalls`）の意味を保つ。

### DESIGN

#### G1 追加の session（`addDisk`）

- `add(contentsOf:as:ownerIDs:expected:progress:)` は、最上位の lstat と照合（:314-322。`expected` を含む）の後で `CommitProgressMeter(total: T, progress:)` を作り、`start()` する。
  - 通常ファイル: T = `st_size`
  - symlink: T = 0
  - directory: T = §G2 の和（progress が nil なら走査しない）
- 通常ファイルの `read` の包み（:374）で、受け取った chunk の byte だけ `advance` する。
  - EOF の確認の `read(1)` は、空なら 0 を足す。
  - directory の再帰では、子孫の読取も同じ meter に足す（子孫で meter を作らない）。
- 成功したら、読後の fstat の照合（:376-384）の後で `finish()` する。失敗したら `finish()` しない。
  - LHA の symlink は今日どおり `unsupportedFileType` になり、(T, T) は通知しない。
- progress が nil なら、meter も `read` の包みも作らない。
- 数える点は「writer へ渡した」時点（ZIP の deflate、圧縮 tar、7z、LHA では圧縮の完了前に (T, T) になる）。doc comment に書く。
- `add(data:)`・`addDirectory` 系には progress を足さない。

#### G2 directory の事前の走査

- progress を渡した `add(contentsOf:)` の URL が directory のときだけ行う。
- 再帰（:327-340）と同じ列挙（`contentsOfDirectory`、名前の昇順、symlink を辿らない）で子孫を lstat し、`S_IFREG` の `st_size` の和を T にする。open はしない。
- 走査の後に変わった子孫の安全性は、今日の再帰の検査が守る。T との差は meter が clamp し、`finish()` が揃える。
- 試験用の注入: `@TaskLocal static var testingAfterPreWalk`（呼出側の thread で読む）。

#### G3 追加の終わり（`finishAdditions`）と待ちの上界

- **`ArchiveWriter.finishAdditions(progress:)`**:
  1. state が writing でなければ `WriterError.invalidState`。追加を閉じる。
     - 閉じたかどうかの検査は `perform` の do/catch の**外**（:293 の state の guard と同じ位置）で行い、誤用で instance を failed にしない。
     - 以後の `add`・`add(data:)`・`addDirectory`・internal の `addEntry` は invalidState。`finish()`・`finish(existingCount:…)`・`endTarMembers()` などはできる。
     - internal の `addEntry` の閉じた状態の検査は、S31 の名前の検査の関数（と `existingPathCheck`）を呼ぶ前に置く（閉じた後の誤った追加で、ZIP の updater の走査や表の構築を起こさない）。
       関数が無ければ（S31 が入っていなければ）、addEntry の名前の検査（:402-415）をこの形の internal の関数に切り出してから使う（挙動は変えない。P7-G も同じ関数を使う）。
     - rewriter との関係: `ArchiveRewriter.finishAdditions` は `ArchiveWriter.finishAdditions` を呼ばない。writer の追加を閉じるのは `ArchiveRewriter.commit` の中だけで、carry と記録した追加の後、`writer.finish()` の直前に行う（§G4）。
  2. P = 待ちの入力 byte（ZIP: zip pipeline の in-flight の重み。tar 系: 圧縮器の組立中 + in-flight。7z・LHA: pipeline の in-flight。非圧縮の tar と、格納だけの ZIP: 0）。`CommitProgressMeter(total: P)` を `start()` する。
  3. drain する。item を書き出すたびに、その重みだけ `advance` する。tar 系は、組立中の入力を `submit(final: false)` してから drain する。これは `beginEndOfArchive`（TarCompressor.swift:38-43）が `cutBeforeInput` で作る区切りと同じ位置。
  4. `finish()`
- **byte の不変**:
  - tar 系: `finish` の `beginEndOfArchive(bufferedCount:)` は、組立中が 0 なら区切りを作らない。したがって block の並びと辞書（GzipCompressor.swift:82-95）は同じ。
  - ZIP・7z・LHA: 待ちの item を順に書き出すだけ。
  - AC-G4 で示す。
- **`maximumPendingInputBytes(for:)`**（efdb651 の構造での値。S18・S24 の後の実装で変わったら合わせ、上界であることを試験で示す）:
  - zip: threads × `DeflateBlock.size`（枠を待ってから組み立てる。ArchiveWriter.swift:486）
  - tar: 0
  - tar.gz: (threads + 1) × `DeflateBlock.size`
  - tar.bz2: (threads + 1) × `ParallelBzip2Compressor.chunkSize(level: bzip2Level)`
  - tar.xz: (threads + 1) × `ParallelXZCompressor.defaultBlockSize`
  - 7z: threads × `LZMA2ChunkPipeline.chunkSize`
  - lha: S18 の in-flight の上限（threads × 1 MiB を想定。threads == 1 は 0）

#### G4 rewriter

- `readsAdditionsDuringCommit` = `options.additionPlacement == .end`
- **add**:
  - `.beginning`: writer へ渡す（§G1 の session）。
  - `.end`: P2 G2.1 の記録（:228-230）だけを行い、(0, 0) を二度通知する。
- **`finishAdditions`**: 追加を閉じ、(0, 0) を二度通知する。
  - `.beginning` で先に drain すると、追加と carry の間に tar の区切りが増えるため。
- **`commit(progress:didCarry:)`**（`commit(didCarry:)` は `commit(progress: nil, didCarry:)` へ渡す）:
  - total は、`checkUnchanged`・`preparedWriter()`・生存 entry の決定の後、最初の carry の前に確定する。
  - total = **C** + **A** + **D**:
    - **C** = 運びの loop（:327-344）が entry の stream と退避ファイルから読む byte:
      - 生存する通常ファイルは `uncompressedSize`。
      - hard link を実体化する entry は参照先の大きさ。
      - tar の hard link、directory、`linkPath` の symlink は 0。
      - 退避（`buffer` :450-466）する参照先は、その読取の分も足す。
      - `uncompressedSize == nil` の entry は 0 とし、読取を数えない。
    - **A** = `.end` の記録:
      - 通常ファイルは `DiskSignature` の size。
      - `add(data:)` は `data.count`。
      - directory の URL は §G2 の和（commit の最初に走査する）。
      - `addDirectory` 系は 0。
      - `.beginning` は 0。
    - **D** = min(C + A + 待ちの入力 byte（commit の開始時）, `maximumPendingInputBytes(for: format)`)
  - carry・記録した追加・退避の読取の包みで `advance` する。
  - carry と追加の後、`writer.finish()` の前に、writer の internal の追加の終わりを行い、書き出した重みを `advance` する。
  - `writer.finish()` の後、置換（:364-373）の前に `finish()` する。
  - `didCarry` は今日と同じ回数・引数で呼ぶ。出力の byte は `commit(didCarry:)` と同じ。

#### G5 updater

- **`ArchiveUpdater`（ZIP）**:
  - `add(…, progress:)` は、`preparedWriter()` の後で writer の §G1 へ渡す（S31 の `existingPathCheck` の設定は `preparedWriter()` のまま）。
  - `finishAdditions` は、writer があれば writer の §G3、無ければ (0, 0) を二度。
  - 追加を閉じる。以後の add は `UpdaterError.invalidState` で、`perform`（:437-444）の外で判定して failed にしない。
  - commit の `drainAppendedRecords()` は、待ちが 0 ならすぐ返る。
- **`TarUpdater`・`CompressedTarUpdater`**: add は、追記用の writer（付随の保存領域）の §G1。`finishAdditions` は (0, 0) を二度通知して閉じる。
- **`LHAUpdater`・`SevenZipUpdater`**: add は `beginAppend` の writer の §G1。`finishAdditions` はその writer の §G3（終端は書かない）。
- どの updater も、`commit(progress:)` の total の式・通知・`lastCommitStrategy` を変えない。`readsAdditionsDuringCommit` は全て false。

#### G6 取消しと失敗

- session の callback の throw と `Task` の取消しは、今日の add・commit の失敗と同じ経路（各 `perform` と cleanup）を通り、error を包まずに返す。
- どの callback も、その呼出しの公開の境界（output == nil の置換）より前に呼ぶ。

#### G7 試験用の乱数の注入（新しい仕組みを足さない）

- ZipCrypto の header の 11 byte（efdb651 ArchiveWriter.swift:548）: 既存の `ArchiveUpdater.testingRandomBytes`（ArchiveUpdater.swift:29。
  ZipReencryption.swift:317 が同じ 11 byte に使っている）を読む: `try ArchiveUpdater.testingRandomBytes?(11) ?? EncryptionPrimitives.random(count: 11)`。
- 7z AES の IV（efdb651 EncryptionPrimitives.swift:170）: S24（P5-G）が足す `SevenZipAESEncryptor.testingIV` を使う。S24 の commit に無いときだけ、
  P5-G の定義（internal の `@TaskLocal static var testingIV: (@Sendable () -> Data)?`、nil なら今の `random(count: 16)`）のとおりに足す。

### ACCEPTANCE CRITERIA

- **AC-G1 追加の session**:
  - 対象: `ArchiveWriter`（7 形式）、`ArchiveUpdater`、`TarUpdater`、`CompressedTarUpdater`（3 codec）、`LHAUpdater`、`SevenZipUpdater`、`ArchiveRewriter`（`.beginning`）。

    - 最初の通知は (0, T)。completed は単調で T を越えない。最後の通知は (T, T) で一度だけ。

- **AC-G2 directory**:
  - 3 階層・17 ファイル（0 byte と 5 MiB を含む）の directory を足すと、T = 通常ファイルの byte の和。

- **AC-G3 rewriter**:
  - `.end`: add の session は (0, 0) の二回。commit の total = C + A + D（試験が式で計算する。D は min(C + A, W)）。通知は単調で、最後は (total, total)。`didCarry` の回数と引数は `commit(didCarry:)` と同じ。

- **AC-G4 追加の終わり**:
  - `ArchiveWriter` の 7 形式 × threads 1・8 で、finish の前に `finishAdditions` を呼んだ出力と呼ばない出力が `cmp` で一致する。

#### A2 台帳 `ArchiveWriteProgress`

`nonisolated final class`（Sendable。状態は `Mutex`）。一つの書込み操作に一つ。

```swift
struct Plan: Sendable {
    var counted: Int            // 削除・改名・新規フォルダ・パスワードの操作など、1 単位ずつの呼出し
    var additions: [UInt64]     // 追加の項目ごとの byteCount（directory・symlink・空ファイルは 0）
    var itemCount: Int          // 「n / N 項目」の N（§A5）
    var carriedBytes: UInt64    // 書き直しで運ぶ生存 entry の uncompressedSize の和（nil は 0）
    var changesExisting: Bool   // 削除・改名・暗号化の変更がある
    var countsCarriedItems = false  // 既存の書庫からの新規作成だけ true（§A5）
}
enum Branch: Sendable {
    case writer(GyoshukuKit.ArchiveFormat)
    case updater(GyoshukuKit.ArchiveFormat, processesAdditionsAtCommit: Bool)
    case rewriter(GyoshukuKit.ArchiveFormat, readsAdditionsDuringCommit: Bool)
}
enum Slot: Sendable, Hashable { case addition(Int), finishAdditions, commit }
init(progress: Progress, plan: Plan)       // completed = 0、仮の total（counted + 追加の項目数 + 1）、項目数の key を 0 / N に置く
func begin(_ branch: Branch, archiveBytes: UInt64, options: WriterOptions)   // completed が 0 のときだけ
func addition(_ index: Int) -> (ArchiveUpdater.CommitProgress) throws -> Void
func didFinishAddition(_ index: Int)       // 項目の残りを満たし、項目数を 1 進める
func didCount(_ n: Int = 1)
func didCarry(_ done: Int, _ total: Int)   // countsCarriedItems のときだけ項目数を進める
var finishAdditions: (ArchiveUpdater.CommitProgress) throws -> Void { get }
var commit: (ArchiveUpdater.CommitProgress) throws -> Void { get }
func credit(_ slot: Slot, completed: UInt64, total: UInt64) throws   // 上の closure の本体。試験はこれを直接呼ぶ
func didPublish()                          // 残りを全て満たす（completed = total、項目数 = N）。throw しない
func reset()                               // completed と項目数を 0 に戻し、begin をもう一度許す
```

- **写し方**（全ての slot で同じ）:
  - 予算 U の slot に (c, t) が来たら、`units = t == 0 ? U : min(U, U × c / t)`（`Double` で計算し、`Int64` へ切り捨て）、`next = max(credited, units)`。
  - total が通知ごとに変わってもよい（§0.2）。c > t も `min` で止める。
  - slot に入ると、前の slot の残りを満たす（順序の保証）。
- **取消し**: `credit` は最初に `ArchiveImportPlan.checkCancellation(progress)` を行う。`didFinishAddition`・`didCount`・`didCarry`・`didPublish` は throw しない。
- **lock**: 差分は `Mutex` の中で決める。`Progress` の更新と `didCreditForTesting` は lock の外で呼ぶ（KVO の observer や試験の hook が再入しても deadlock しない）。
- **Progress の更新の回数**:
  - 増分が 0 なら `Progress` を触らない。
  - 項目ごとの `Progress` の更新は、`completedUnitCount` と `fileCompletedCountKey` を各 1 回まで。
  - AC-A10 を満たさなければ間引く: slot の終わり、増分が total の 1/1000 以上、前回から 50 ms のどれかに当たったときだけ更新する（credit の回数は hook に全部渡す）。
- **DEBUG**: `static let didCreditForTesting = TaskLocal<(@Sendable (Slot, Int64, Int64) -> Void)?>(wrappedValue: nil)`（credit の後の slot・completed・total）。
- `completedUnitCount ≤ totalUnitCount` を常に保つ（DEBUG で assert）。

#### A3 予算（`begin` が決める。単位は byte に揃える）

- S = 原本の大きさ（`publish` の `ArchiveSetIdentity.capture(url:)` の volume の size の和）
- W = `options.maximumPendingInputBytes(for: 出力の形式)`（options は S27（P9）の `compressionThreads` を含む session の options）
- ΣA = 追加の byteCount の和

| slot | 予算 |
|---|---|
| 削除・改名・フォルダ・パスワードの操作 | 1 単位ずつ（`counted`） |
| 追加の項目 i（add で読む editor） | max(1, byteCount_i) |
| 追加の項目 i（`readsAdditionsDuringCommit == true`） | 1 |
| finishAdditions | `.writer(f)`・`.updater(.zip / .lha / .sevenZip)` で ΣA > 0 なら max(1, min(ΣA, W))。それ以外は 0（slot を作らない） |
| commit: `.updater(.zip)`・`.updater(.tar)`・`.updater(.sevenZip)` | max(1000, changesExisting ? S : 0) |
| commit: `.updater(.tarGzip / .tarBzip2 / .tarXZ / .lha)` | max(1000, ΣA + (changesExisting ? S : 0)) |
| commit: `.rewriter(f, r)` | max(1000, carriedBytes + (r ? ΣA : 0) + min(carriedBytes + ΣA, W)) |
| 検証と公開 | 1 |

- 予算は比の重みにすぎない（受入は単調性と粒度で見る）。`processesAdditionsAtCommit` は KF の枝が決める。
- `.writer(f)` には commit の slot が無い。

## リスクと未決（P6）

1. **予算の比**（§A3）: 形式ごとの commit の重みは推定で、追加の後に棒が前へ跳ぶことがある。`max_gap_ms` が目立つ行があれば、その行の式だけを直す。圧縮 tar の `.update` で、書庫のほぼ全体を作り直す編集は、commit の予算が過小になる（比の写しなので、棒は止まらない）。
2. **読取で数える**（§0.4-2）: 追加の slot は圧縮より先に満ちる。LZMA2 の 16 MiB の片は finishAdditions の slot で跳ぶ（7z と tar.xz の text で最大約 6.7 s の間隔）。片を小さくするのは P14 の範囲。
3. **非 clone の volume**（§0.7）: 最初の add の先頭の写しと、7z の `.reencode` は報告しない。
4. **P9（S27。P6 より前に入る）**: `maximumPendingInputBytes(for:)` は `resolvedCompressionThreads` を通るので、設定の並列数がそのまま上界に効く。KF の予算の W も同じ options から求める。
5. **P12（S29・S30。P6 より前に入る）**: P6-A は分割の生産と publisher の進捗を変えない（replay の ledger は nil）。P12 の `ArchiveVolumeInput.copy` と `VolumeSetPublisher` の形はそのまま読む。
6. **公開前の検証の尾**: `.rewrite` の tar.xz・tar.bz2・7z では、`verification_open` が書庫全体を展開するので、棒が最後の 1 単位の手前で止まる。`tail_ms` で計測し、1 s を越える行は、KaitoKit の open に進捗を足す後続の課題として報告する。

  2. `O_NOFOLLOW` の open と fstat の照合（:355-369）
  3. tar の hard link の検出（:370-371）
  4. 名前の正規化と衝突検査（:402-415。S31 の後は internal の関数一つと、ZIP の updater の `existingPathCheck`）
  5. 読取（256 KiB ごと）、EOF の確認、CRC
  6. 読後の fstat の照合（:376-384）、close
  7. hard link の記憶（:385-389）
- worker で動くのは deflate だけ（`OrderedChunkPipeline`、:64-66、:479-506）。
- **ZIP の出力**は、entry ごとに header の write、data の write、seek、確定した header の write、seek を行う（:508-539、:460-476）。格納・directory・空ファイル・ZipCrypto の前では pipeline を drain する（:433-435）。
- deflate は block ごとに `deflateInit2_` と `deflateEnd` を行う（DeflateBlock.swift:14-20）。
- **KF は writer の再帰を使わず、項目ごとに `add` を呼ぶ**（ArchiveImportTransaction.swift:502-518、ArchiveCreationTransaction.swift:186-199、replay）。エラーは、その項目の path を付けて包む。

### 0.3 決めたこと（と採らなかった案）

1. **項目ごとの `add` は今日のまま同期**。先読みは新しい一括の入口だけに入れる。
2. **一括の入口は配列**（`[ArchiveAddition]`）。
3. **エラーを包む型を一つ足す**（`ArchiveAdditionError`）。`CancellationError` と、呼出側の callback が投げた error は包まない。
4. **進捗と項目の通知は一つの callback**（`ArchiveAdditionEvent`）。
5. **読取の検査は今日と同じ鎖を worker で行う**。
6. **worker に渡すのは、閾値以下の通常ファイルだけ**。
   - 閾値は、ZIP の deflate の entry では **writer の `deflateBlockSize`**（既定は 1 MiB、試験では 64 KiB）、それ以外では 1 MiB。
   - これを越えるファイルは、今日の呼出側の経路（P6 の session 付き）。
7. **directory の URL の項目は、その項目だけ今日の再帰で追加する**。
8. **出力の byte は、同じ項目を同じ順に項目ごとの API で足したものと一致する**。
9. **失敗の帰属は、最小の index の失敗**。呼出側の段で失敗したら、窓を drain してから、より小さい index の結果を先に確かめる。
10. **名前の検査は一か所に書く**。一括の呼出側の段は、S31（P1d-G）が切り出した addEntry の名前の検査の internal の関数を、項目ごとの経路と同じ順に呼ぶ（ZIP の updater の `existingPathCheck` の走査と budget を含む）。

### DESIGN

#### G1 API（public）

```swift
public struct ArchiveAddition: Sendable {
    public enum Source: Sendable {
        /// ディスクの項目。add(contentsOf:as:ownerIDs:progress:) と同じ（symlink は辿らない。directory は再帰）。
        case contents(of: URL)
        /// 明示的な空 directory（mode 0755）。addDirectory(_:modificationDate:ownerIDs:) と同じ。
        case directory(modificationDate: Date?)
    }
    public var path: String
    public var source: Source
    public var ownerIDs: ArchiveOwnerIDs?
    public init(path: String, source: Source, ownerIDs: ArchiveOwnerIDs? = nil)
}

public enum ArchiveAdditionEvent: Sendable, Equatable {
    /// additions[index] の最初の syscall（lstat）の前。
    case willStart(index: Int)
    /// additions[index] の追加元の byte の session（P6 §0.3。directory・symlink・空ファイルは (0, 0) を二度）。
    case progress(index: Int, ArchiveUpdater.CommitProgress)
    /// additions[index] を受け取った（項目ごとの add が戻る時点に当たる。圧縮の完了とは限らない）。
    case didFinish(index: Int)
}

/// 一括の追加で、ある項目の処理が失敗した。
public struct ArchiveAdditionError: Error, Sendable {
    public let index: Int
    public let path: String
    public let sourceURL: URL?       // 失敗した追加元（directory の再帰では子孫）。.directory は nil
    public let underlying: any Error // CancellationError と events の throw は包まない
}

public protocol ArchiveEditing: AnyObject {
    /// additions を順に追加する。出力は、同じ順に add(contentsOf:as:ownerIDs:progress:) と
    /// addDirectory(_:modificationDate:ownerIDs:) を呼んだものと byte で一致する。
    /// events は呼出しの thread で同期的に呼ぶ。throw は取消しと同じ（包まずに返し、editor は failed）。
    /// 失敗した項目があれば、最小の index の ArchiveAdditionError を投げ、editor は failed になる。
    func add(_ additions: [ArchiveAddition], events: ((ArchiveAdditionEvent) throws -> Void)?) throws
}
extension ArchiveEditing {
    public func add(_ additions: [ArchiveAddition], events: ((ArchiveAdditionEvent) throws -> Void)?) throws
}
extension ArchiveWriter {
    /// ArchiveWriter では、ownerIDs と modificationDate を受ける公開の入口はこれだけ（項目ごとの API では internal）。
    public func add(_ additions: [ArchiveAddition], events: ((ArchiveAdditionEvent) throws -> Void)?) throws
}
```

- **既定の実装**: 各 index で `willStart` → 次のどちらか → `didFinish`。
  - `.directory` は `addDirectory(path, modificationDate:, ownerIDs:)`（その既定の実装が nil/nil を 1 引数へ振り分ける）。
  - `.contents` は `add(contentsOf:as:ownerIDs:progress:)`（progress を `.progress(index:, _)` へ写す）。
  - `CancellationError` と events の throw 以外の error は `ArchiveAdditionError` で包む。
- **events の順序の約束**:
  - `willStart(i)` は、項目 i のどの syscall よりも前。`willStart(i)` が throw すれば、項目 i のファイルは開かれない。
  - `progress(i, …)` は `willStart(i)` と `didFinish(i)` の間。異なる項目の progress は混ざらず、index の昇順。
  - `didFinish(i)` は index の昇順。`willStart(j)`（j > i）が `didFinish(i)` より前に来ることがあり、その幅は窓の大きさ以下。
  - 失敗で終わる場合、失敗した index より前の項目の `didFinish` は全て通知済み。
- 先読みした項目の session は、呼出側が結果を受け取った時点で (0, T) と (T, T) を続けて通知する。

#### G2 呼出側の段（index の昇順）

各項目 i について:

1. `willStart(i)`。`Task.checkCancellation()`。追加を閉じた状態（P6 §G3）なら invalidState。
2. `.directory`: 今日と同じ entry を、出力の順の列へ入れる（drain しない）。
3. `.contents(of: url)`: URL の file system 表現を一度だけ作り、lstat と出力の同一性を照合する（`expected` があれば照合）。
   - `S_IFDIR`: 窓を drain してから、今日の再帰（`addDisk`）で足す。
   - `S_IFLNK`: 今日と同じく、呼出側で readlink する。
   - `S_IFREG` で閾値（§0.3-6）を越える、または ZIP の ZipCrypto: 窓を drain してから、今日の呼出側の経路。
   - `S_IFREG` で閾値以下:
     - 名前の正規化と衝突検査: S31 の internal の名前の検査の関数を呼ぶ（:402-415 の集合の更新と、ZIP の updater の
       `existingPathCheck` の呼出しを含む）。項目ごとの経路と同じ順・同じ回数で呼ぶので、S31 の走査の回数と budget の越え方も同じになる。
     - tar の hard link の判定と、lstat の値からの記憶（:370-371、:385-389）。
     - ZIP の圧縮方式の決定（:599-605）。
     - `FileJob(index, path: [CChar], expected: lstat の値, method, level, hooks)` を窓へ入れる。`hooks` はここで capture した試験用の TaskLocal の値。
   - それ以外の種類: `unsupportedFileType`。
4. 窓が満ちていれば、最も古い結果を受け取って出力する（§G4）。
5. 呼出側の段で失敗したら、窓の結果を index の順に受け取り、より小さい index の失敗があればそれを投げる。無ければ自分の失敗を投げる。

- **「窓の drain」**: 先読みの結果を順に writer へ渡し終えることだけを指す。tar 系の圧縮器の組立中の buffer と pipeline（TarCompressor.swift:26-67）には触れない（触れると tar の区切りが増え、byte が変わる）。ZIP では、窓と zip pipeline は同じなので、今日の drain（:433-435）と同じ。
- 名前の検査と衝突の予約は、一括では open の前に行う（項目ごとの経路では open の後）。失敗が二つ重なる項目では、報告する原因が変わりうる。doc comment と CHANGELOG に書く。

#### G3 worker の仕事（`FileJob`）

1. `open(path, O_RDONLY | O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC)`
2. fstat が expected と一致すること（dev・ino・mode・size・mtime の秒とナノ秒）。違えば `sourceChanged(追加元の path)`。
3. size ちょうどを読む。短い読取は続け、0 が来たら `sourceChanged`。`read(1)` が空であること。
4. 読後の fstat の照合と close（`defer` で必ず閉じる）。
5. CRC-32（ZIP・7z）と LHA の CRC16 は、今日と同じ値になるなら worker で計算してよい。
6. ZIP の deflate の entry は、`DeflateBlock(input:, dictionary: Data(), final: true)` を worker で符号化する（size ≤ `deflateBlockSize` なので、今日の単一 block と同じ入力）。格納と AES の entry は符号化しない。
7. 結果は `Result<Prefetched, Error>`。失敗は index と追加元の URL を持つ。
8. **窓と並列数**:
   - ZIP は zip pipeline に file の仕事を足す。他の形式は、先読み専用の `OrderedChunkPipeline`。
   - in-flight の件数は `resolvedCompressionThreads` 以下（OrderedChunkPipeline.swift:94-103 と同じ枠）。
   - open から close まで（1–4）だけを、幅 `prefetchConcurrency = min(resolvedCompressionThreads, Step 0-P7 の最良の本数)` の limiter で囲む。
   - 同時に開く記述子は `prefetchConcurrency` 以下。
9. **GCD の worker では TaskLocal が見えず、`Task.isCancelled` も常に false**:
   - 試験の hook は、手順 3（`FileJob`）で capture した値を使う。
   - 取消しは pipeline の放棄で伝え、未着手の仕事は開かずに捨てる（`State.encode` の `shouldRun`）。
10. **失敗・取消し・events の throw で戻る前**に `abandonAndWait()` で、着手済みの仕事が close し終わるのを待つ（最大で `prefetchConcurrency` × 閾値の読取）。記述子を呼出しの外へ残さない。

#### G4 出力（呼出側、index の昇順）

- **ZIP**:
  - 先読みした entry は、確定した CRC と大きさの local header と data を、`Data` にまとめて一度に書く。
  - AES は呼出側で、`zipSalt()` を index の順に取って暗号化する（圧縮後の大きさ + 28 が先に分かる）。
  - 格納・directory・空ファイル・symlink も順序の列の要素として書き、pipeline を drain しない。
- **ZIP の項目ごとの経路**（:508-539）でも、最初の block が最後の block である entry は、確定値の header と data を一度に書く（byte は同じ）。
- **tar 系・7z・LHA**: 先読みした `Data` を返す読取の closure を writer に渡す（header・pax・hard link・詰め物・片の分け方は今日と同じ）。
- `didFinish(i)` は、その項目の出力（ZIP は書込み、他は writer への引渡し）の後。
- **worker の仕事の失敗の帰属**:
  - ZIP の deflate の失敗は、その block の item の index。
  - tar 系の圧縮器と出力の失敗は、そのとき writer へ渡していた項目の index。

#### G5 updater と rewriter

- `ArchiveUpdater`・`TarUpdater`・`CompressedTarUpdater`・`LHAUpdater`・`SevenZipUpdater`: 今日の add と同じ準備（`preparedWriter()` と名前の同期。ZIP では S31 の `existingPathCheck` の設定を含む）の後、writer の一括へ渡す。
- `ArchiveRewriter`:
  - `.beginning`: writer の一括へ渡す。
  - `.end`: 各項目を P2 G2.1 のとおり記録する（記録時の検査は逐次）。events は `willStart`・(0, 0)・(0, 0)・`didFinish`。commit の中で、記録した追加を writer の一括（internal。項目ごとに `expected` を渡す）で追加し、読んだ byte を P6 §G4 の meter へ足す。
- `finishAdditions` との関係は、項目ごとの経路と同じ。

#### G6 z_stream の再利用

- `DeflateBlock.encode` は、worker の thread ごとに一つの `z_stream` を `deflateReset` で使い回してよい（同じ level・windowBits・memLevel・strategy）。
- 辞書付きの block は、毎回 `deflateSetDictionary` を行う。
- thread-local の保持は pthread の key の destructor で `deflateEnd` する（Swift 6 では `nonisolated(unsafe)` の key）。

### CONSTRAINTS

- **出力の byte**: 一括 = 項目ごとの API の同じ列。対象は 7 形式 × threads 1・4・8、password なし・ZIP AES・ZipCrypto・7z AES（固定の salt と、P6 §G7 の乱数の注入）。
  - 既存の `ParallelDeflateBzip2WriterTests`・`ParallelLZMA2WriterTests`・`TarChunkLayoutTests` が変更なしで通る。
- **TOCTOU**: 検査の鎖（§G3 の 1–4、呼出側の lstat・出力の同一性・`expected`）を弱めない。先読みの内容は、検査の後にだけ出力へ渡す。
- **名前の検査**: S31 の関数だけで行い、写しを作らない（grep で示す）。`LiveNameCheckTests` が変更なしで通る。
- **記述子**: 同時に開く数は `prefetchConcurrency` 以下。呼出しが戻った時点で、開いた記述子は残っていない。
- **メモリ**: 先読みの内容 ≤ threads × 1 MiB + 今日の圧縮の窓。`peak_rss_mib` ≤ 基準 + 32 MiB。
- **API**: 項目ごとの `add` の意味・同期性・エラーを変えない。`WriterError` に case を足さない。公開 API の追加は §G1 だけ。
- events の throw、取消し、失敗は、P6 §G6 と同じ経路で後始末する。
- 作業ツリーの外を変えない。commit しない。

### ACCEPTANCE CRITERIA

- **AC-G1 byte の一致**（`BatchAdditionEquivalenceTests`）:
  - 項目の構成（1 回の出力は約 15 MB）:
    - 0 B・1 B・4 KiB の小さなファイル 580 件
    - 64 KiB − 1、64 KiB、64 KiB + 1（deflateBlockSize 64 KiB の試験用）
    - 1 MiB ちょうど ×2、1 MiB + 1 ×2、3 MiB ×2
    - `.png`（格納）×2
    - symlink ×3（LHA は除く）
    - 明示の日付の directory ×3
    - tar では、同じ inode の二つの名前 ×2
    - 日付は `touch -t` で固定し、atime ≥ mtime にする
  - 対象:
    - `ArchiveWriter` の 7 形式 × threads 1・4・8（ZIP は password なし・AES・ZipCrypto、7z は password なし・AES）。deflateBlockSize は既定と 64 KiB の両方。一括と項目ごとの API の出力が `cmp` で一致する。
    - `ArchiveUpdater`（ZIP の追記）、`TarUpdater`、`CompressedTarUpdater`（3 codec）、`LHAUpdater`、`SevenZipUpdater`、`ArchiveRewriter`（`.end`・`.beginning`）の commit の出力も一致する。
    - `ArchiveUpdater`（ZIP の追記、2,048 件以上の書庫か `testingNameCheckMinimumEntries = 0`）で、`testingNameCheckBudget` が 0・既定（4）・`Int.max` のそれぞれについて、一回の一括で 10 件を追加した結果（受理・例外・出力 byte）と `nameCheckScanCount` が、同じ値の項目ごとの API と一致する（一括の途中で S31 の budget を越える場合を含む）。
    - LHA に symlink を渡すと、項目ごとの API と同じく `unsupportedFileType` になる（`ArchiveAdditionError` で包む）。
- **AC-G2 検査**（`BatchAdditionSafetyTests`。注入 `testingBeforeWorkerOpen`・`testingDuringWorkerRead` は `FileJob` に capture して渡す）:
  - lstat の後・open の前に項目を symlink に差し替えると、`ArchiveAdditionError(index: その項目, underlying: WriterError.io(operation: "open source", code: ELOOP))`。
  - 同じ大きさの別のファイルに差し替えると `sourceChanged`。
  - 読取中に伸ばす・縮めると `sourceChanged`。どの場合も、その項目の内容は出力へ書かれず、updater では何も公開されない。
  - 出力ファイル自身を追加元にすると、`invalidPath("source contains output archive")` を包む。

## リスクと未決（P7）

1. **open の並列の伸び**: warm の採り直しは 4 本で 0.35 倍、8 本で 0.46 倍。Step 0-P7 の門を満たさなければ、P7 の利得は出力の一度書きと URL の変換の削減だけになり、AC-G7 の zip の閾値を満たさない。その場合は Step 0-P7 で止めて報告する。
2. **名前の検査の順序**: 失敗が二つ重なる項目では、報告する原因が変わる。instance はどちらでも failed。
3. **hard link の記憶の時期**: lstat の時点で記憶する。参照先の読取が後で失敗すれば一括全体が失敗するので、矛盾は残らない。
4. **directory の URL**: 逐次の再帰に落ちる。`recursive` は速くならない（KF は通らない）。
5. **rewriter の `.end`**: 記録時の検査（`DiskSignature.capture` の open と fstat）は逐次のまま。5 万件で約 0.9 s。
6. **閾値と corpus**: 絶対値の閾値は ORDER-P6-P13 §3.7-0 の corpus（平均 2.1 KB、三階層）に対するもの。make-corpora.sh の small（平坦で、平均 2.5 KB）では、一つの directory の列挙が重くなるので比較に使わない。
7. **GCD の thread**: limiter で待つ worker は threads 本以下。圧縮の pipeline と合わせて最大 2 × threads 本が動く。コアの少ない機械では、`prefetchConcurrency` を下げてよい（Step 0-P7 の門の値が上限）。
8. **ZIP の updater の名前の検査**: 一括でも S31 の走査は項目ごとに一回で、budget（4）を越えると全件の表を作る。5 万件の取込みでは最初の 4 件の後に表を一度作るので、S31 の前と同じ費用が一回だけ残る（AC-A5 の zip の閾値はこれを含む）。
