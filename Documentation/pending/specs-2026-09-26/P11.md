### 0.4 What the profile rules in and out

- **In, dominant:** sequence execution, 59–81% of decode on every large stream. The reference decodes r0text end to
  end in 268 ms (≤ 7.9 ns per sequence); Kaito spends 12.9 ns per sequence in the loop alone.
- **In, dominant for per-entry frames:** Huffman table construction. The pair table costs ≈7.8 µs per new table
  (388 ms / 50,000; 23.4 ms / 2,961): 47% of the small-zstd.zip decode and 28% of headers-zstd.zip.
- **In, secondary:** Huffman decode at 0.8–1.0 GB/s, and FSE table construction (6% of text, 8% of small-zstd.zip,
  12% of headers-zstd.zip).
- **Small:** block read, `Array` copy, compaction and caller copy total 19 ms of 442 on text (4.4%), and 10.7 ms of
  820 on small-zstd.zip (1.3%). They are bundled into the buffer work; no gain is claimed for them.
- **Out:** XXH64 (23.5 GB/s; only a raw-pointer overload); overlapping staging on a thread; prefetch for long windows;
  raw blocks (no-regression check only).
- **Per-frame allocation is a cost centre for the ZIP targets.** Allocating and zeroing two 128 KiB buffers per frame
  (what a buffer sized by `maximumBlockSize` would do for these frames) measured +22–38 ms per 50,000 frames in a
  hot-cache C loop (`$SCR/p11review/alloc.c`: 3.4–8.7 ms for today's one storage malloc, 25.9–41.6 ms with the two
  zeroed buffers, 4.9–6.1 ms when sized by need). Scratch must be sized by need (D0).

## OBJECTIVE

Make the Swift zstd decoder about 1.5× faster on large streams and about 2× faster on archives with many small
frames, with byte-identical output and every existing check, limit and error kept. Against a retained pre-change
binary:

- 256 MiB `text.tar.zst` open: ≤ 0.70× before (≈465 → ≤ 325 ms).
- 50,000-frame method-93 ZIP extract: ≤ 0.55× before, which brings it to or below the Deflate ZIP of the same files.

Three ordered stages, sized by measured share: 1. sequence loop and sequence tables (59–81%), 2. Huffman (10–60%),
3. the remaining copies (1–2%).

## DESIGN

Names are indicative; behaviour and invariants are binding. Every unchecked access carries a short Japanese comment
stating its invariant (M10 practice).

### D0. Scratch sizing and initialization (applies to D1, D2, D8, D9)

- All scratch belongs to one `ZstdFrameDecoder` (one frame), is allocated lazily on first need, and is freed in
  `deinit`. No static or global pool, and no sharing between decoder instances.
- Buffers are **sized by need**: capacity starts at `max(4 KiB, first request)` and doubles up to the kind's maximum
  (`header.maximumBlockSize` for the block and literal buffers). Never allocate `maximumBlockSize` up front: every
  frame of both ZIP corpora declares a 128 KiB block limit but carries a ≈1.2 KB block (§0.1).
- **Do not zero whole buffers.** Zero the front pad once at allocation, and after every fill zero (or, for RLE,
  fill) exactly the back pad that follows the valid bytes (≤ 32 bytes). With this rule every byte a fast path can read
  is initialized: valid data, earlier data of the same buffer, or a pad that was just written.
- Expose `internal var allocatedScratchBytes: Int` (sum of scratch capacities) for tests. `allocatedWindowBytes` and
  `allocatedBufferBytes` keep their meaning.

### Stage 1: padded buffers, compact sequence tables, a tight sequence loop

**D1. Reusable, padded block buffer.**

- Layout `[F | cap | B]`, F ≥ 8, B ≥ 32, `cap` per D0 (≤ `maximumBlockSize`).
- A compressed block is read into `[F, F + size)` by a new `ZstdInput.read(_ count: Int, into: UnsafeMutableRawPointer)`
  with the policy of `read(_:)` (ZstdBitReader.swift:181-203): consume the 4 KiB read-ahead first; if at least 4 KiB is
  still needed, read directly into the destination; otherwise refill the read-ahead (4 KiB or the remaining input) and
  copy. The direct read loops over short reads exactly as `readByteRange` does (ByteSource.swift:398-425): each
  `read(into:at:)` must return `1…remaining`, else `KaitoError.truncated`. `count > remaining` throws `truncated` before
  any read. After the read, zero `[F + size, F + size + B)`. Existing coverage of short reads:
  `testByteSourceRangeShortReadsAndTerminalError` (ZstdTests.swift:657-696, `ShortSource` returns ≤ 7 bytes per read,
  including a 128 KiB raw block); it stays unchanged.
- Keep `read(_:) -> [UInt8]` (tests).
- `ZstdByteReader` and `ZstdForwardBits` may become views (base pointer + range) over this buffer; tests that build a
  reader from `[UInt8]` go through a helper that copies into a padded buffer and keeps it alive.

**D2. Reusable literal buffer.** Capacity ≥ regenerated size + 32 (D0).

- Huffman literals are decoded into it (Stage 1: today's decoder behind an `into:` entry point).
- RLE literals: fill `size + 32` bytes with the RLE byte.
- **Raw literals are not copied**: the sequence loop reads them in place from the block buffer (today :167 copies).
  The bytes after them are block bytes or the zeroed back pad.
- The sequence loop receives `(base: UnsafeRawPointer, count: Int)`; every source has ≥ 32 initialized bytes after
  `count`.

**D3. Output slack.** One named constant `outputSlack` (≥ 32) replaces the literal 16 at :89, :90, :94, :96, :114.
Slack is write-only: it is never counted in `historyCount`, hashed, returned, or read. Proof to write next to
`copyMatch`: every match chunk reads only bytes below the current write position (D6), and literal copies read only
from D1/D2 buffers. So storage is **not** zeroed (zeroing 128 KiB of storage per ZIP frame would repeat the §0.4 cost).

**D4. Compact sequence tables.**

- Cell of 8 bytes: `struct SequenceCell { var base: UInt32; var nextBaseline: UInt16; var stateBits: UInt8; var extraBits: UInt8 }`
  (largest base 2^31 for offset code 31; baselines < 512).
- Split `ZstdFSE.read` (ZstdFSE.swift:59-96) into (1) parse the normalized distribution into a fixed scratch array
  (≤ 53 entries), keeping the reader-advance at :94, and (2) build straight into the frame's per-kind cells
  (capacity LL 512, OF 256, ML 512): spread pass, then state pass, in today's order, with no intermediate
  `[Int]`/`[Cell]`.
- Keep every check of ZstdFSE.swift:18-23, :41, :51 and of `read` (:62, :66-68, :78-80, :87-89).
- Predefined tables are `private static let` **arrays** of `SequenceCell` (Sendable values). Mode 0 copies the
  predefined cells (≤ 64) into the kind's cells. No static raw pointers and no `nonisolated(unsafe)`.
- Mode 1 builds one cell (log 0) after the `symbol < bases.count` check (:206); mode 3 reuses the kind's cells, and
  "repeat without table" still throws (:210) — track per kind whether the frame has a table yet. A table build that
  throws leaves the decoder terminal, so partial overwrite is harmless.
- Keep `ZstdFSE` and its API for Huffman weights (ZstdHuffman.swift:75) and for tests.

**D5. Padded backward bit reader** (sequence stream now; Huffman streams in Stage 2).

- State: a 64-bit container loaded from the eight bytes `[p-7, p]` (little-endian), `consumed` (0…63) bits already
  taken from the top, and the byte position `p`.
- Read n bits (0…31): `(container &<< consumed) &>> 1 &>> (63 - n)`, then `consumed += n`.
- Refill: `p -= consumed >> 3; consumed &= 7; container = load(p - 7)`.
- **Bounds theorem** (write it next to the code): the stream occupies `[s, e)` inside the block buffer, so
  `s ≥ base + F ≥ base + 8`. A valid stream never makes `p < s - 1`, so every load `[p-7, p]` lies in
  `[s-8, e) ⊂ [base, base + F + cap + B)`. A refill that would make `p < s - 1` is malformed; choose and document one
  response: throw there through a cold helper (one predictable branch per refill), or clamp `p` to `s - 1` **and** set
  a sticky overflow flag checked with the exact end check. Either way no load can leave the allocation.
- Initial state: the stream must be non-empty and its last byte non-zero (ZstdBitReader.swift:13-15). `p = e - 1`,
  `consumed = lastByte.leadingZeroBitCount + 1`. `remaining = (p + 1 - s) * 8 - consumed`, computed only outside hot
  loops.
- Initial states are read with unchecked reads of `accuracyLog` bits (always < table size); a short stream is caught
  by the end check.
- Per-sequence order (RFC 8878): refill; OF extra; if `ofBits > 24` refill again; ML extra; LL extra; refill; LL, ML,
  OF state bits — **except after the last sequence, which reads no state bits** (today :327). Bounds: OF ≤ 31, ML ≤ 16,
  LL ≤ 16 extra bits; states ≤ 9 + 9 + 8; after a refill ≥ 57 bits are in the container, and `consumed` ≤ 63 at every
  read.
- End: after the last sequence `remaining == 0` and the overflow flag is clear (today :339).
- Keep `ZstdBitReader` (:4-74) for Huffman weights (ZstdHuffman.swift:76-94) and its test
  (ZstdDifferentialTests.swift:130-156, which asserts zero padding via `peekPadded(11) == 0`).

**D6. Sequence loop.** Rewrite `executeSequences` (:267-349) and `copyMatch` (:351-376).

- Hoist every invariant into locals before the loop (cell pointers, `windowSize`, `historyCount`,
  `maximumBlockSize`, repeat offsets, output and literal pointers). No class stored property is read, written or
  passed `inout` inside the loop (dynamic exclusivity checks).
- Widen `UInt32` bases to `Int` before adding extra bits. Lengths ≤ 131,074 (ML code 52), offsets < 2^32; wrapping
  arithmetic only where these bounds make overflow impossible.
- `resolveOffset` (:378-398) becomes non-throwing with identical repeat-offset semantics. Case 4 with `repeats.0 == 1`
  yields offset 0, which the offset check rejects with "zstd match exceeds history" (today "zstd repeat offset is
  zero"; no test in KaitoKit, GyoshukuKit or KaitoFinder matches that string). The `default` case is unreachable
  (value ≥ 1).
- **Per-sequence checks, all kept, all before any copy**, fusable into one unlikely branch:
  1. `literalLength ≤ literalsRemaining` (:301)
  2. `literalLength + matchLength ≤ maximumBlockSize - outputCount` (:302)
  3. `offset > 0 && offset ≤ windowSize && offset ≤ historyCount + outputCount + literalLength` (:322)
  The out-of-line cold helper re-evaluates them in this order and throws today's message for the first that fails
  ("zstd sequence lengths" for 1–2, "zstd match exceeds history" for 3; ZstdTests.swift:341, :374).
- **Literal copy:** always copy 16 bytes (SIMD16 or two 8-byte moves); if `literalLength > 16`, continue in 16-byte
  chunks (32-byte chunks allowed if ≤ `outputSlack` and ≤ source pad); a plain `copyMemory` above a measured threshold
  is allowed (source and destination never overlap). Writes stay in `[o, o + roundUp(LL, W))`, before the slack end;
  reads stay in the source plus its ≥ 32 initialized bytes; garbage past `o + LL` is overwritten by the match copy or
  the tail literals.
- **Match copy:**
  - offset ≥ 16: 16-byte chunks; chunk k reads `[o - off + 16k, +16)`, all below `o + 16k`, i.e. history or this
    match's earlier chunks.
  - 8 ≤ offset < 16: 8-byte chunks, same argument.
  - offset < 8 (≤ 0.9%): first 8 bytes one at a time from `o - off`, then 8-byte chunks from distance
    `d = off × ceil(8 / off)` (8…14), a multiple of the period.
  - A bulk `memmove`/`copyMemory` is allowed only when `offset ≥ matchLength` (non-overlapping) and the length is
    above a measured threshold. Overlapping matches never use it (a memmove of an overlapping LZ copy is wrong).
  - No `initialize(from:count:)` / memmove calls remain on the ≤ 16-byte paths (:314-316, :372).
- Tail literals (:342-347): copy exactly `tail` bytes after the guard at :339.
- A block returns only after every check, including the exact end check; `writePosition`/`historyCount` advance only
  after that. Any throw leaves the decoder terminal (ZstdDecompressor.swift:65-67).

**D7. Stage-1 plumbing.**

- `compressedBlock` (:217-265) reads from the block buffer and passes raw pointers instead of the five nested
  `withUnsafe…` closures (:248-263).
- Stage 1 removes the per-block allocations at :132 (compressed block input) and :166-167 (literals) and decodes
  Huffman output into the literal buffer instead of ZstdHuffman.swift:114. Raw/RLE blocks (:130-131) and :264 are
  Stage 3.
- Literals-only blocks (sequence count 0, :225-229) copy the literals into storage as today.

**D-T. Test tuning (no global state).** An internal `struct ZstdTuning: Sendable` (pair-table threshold, Huffman fast
loop on/off, match path: default / 8-byte chunks for all offsets ≥ 8 / byte-then-period for all offsets) with a
`static let default`. It is passed through internal initializer parameters of `ZstdDecompressor` and
`ZstdFrameDecoder` (default `.default`). No mutable static, no environment variable, nothing public.

### Stage 2: Huffman

**D8. Cheap table construction with reused storage.**

- Single-symbol table (≤ 2^11 cells, 2 bytes each) built by rank: count symbols per weight, compute rank starts, fill
  each symbol's range; no `filter`/`enumerated`/`append`/allocation (today :31-46).
- Storage belongs to the frame decoder; treeless sections (type 3) reuse it (:176-177).
- Keep every weight check (:19-36, :46, and the weight-count checks of `read`, :66-72, :93).
- Weights: `ZstdHuffman.read` may decode the FSE weight description through the D4 scratch builder (≤ 64 cells) and
  the checked `ZstdBitReader`, instead of allocating `ZstdFSE` arrays per table; `ZstdFSE` stays for tests.
  Measure first: the non-pair part of table cost is 108 ms (small-zstd.zip) and 24 ms (headers-zstd.zip).

**D9. Build the pair table only when it pays.**

- The 4,096-entry pair table (:49-59; 4 bytes per entry) is allocated and built lazily, at the first decode for which
  `(symbols already decoded with the current table) + (this section's count) ≥ T`. Below T, decode with the
  single-symbol table.
- **A new table (literals type 2) invalidates the pair table and resets the counter**; a treeless section keeps both.
- Calibrate T by a sweep (V8): T ∈ {0, 2 Ki, 4 Ki, 8 Ki, 16 Ki, 32 Ki, ∞} on text, r0text, text1, headers.tar.zst,
  small-zstd.zip, headers-zstd.zip; choose the lowest total and record the sweep. Sizing facts: a pair build ≈7.8 µs;
  new tables carry 1.5–1.8 K literal bytes in the ZIPs and 2.5–24 K in the section that carries them in the tars
  (§0.3).
- Output is identical whichever table is used.

**D10. Huffman fast loop.**

- For 4 streams (and 1), compute K from both limits: remaining bits of every stream,
  `K ≤ ⌊bits_i / (L × maxBitsPerLookup)⌋` (pairBits for pairs, maximumBits for singles), and output room,
  `K ≤ ⌊(segmentEnd_i − p_i) / (L × bytesPerLookup)⌋`.
- K iterations without per-lookup checks; each refills every stream once (D5 reader), then L lookups per stream:
  L = 4 for pairs (≤ 12 bits, 48 ≤ 57), L = 5 for singles (≤ 11 bits, 55 ≤ 57). Indices masked to the table width.
- A pair lookup writes 2 bytes even for one symbol: K guarantees `p_i + 2L ≤ segmentEnd_i`.
- Tails use today's checked logic (`finishStream`, :160-175) on the **same** padded reader, driven by its
  `remaining`, with the per-stream exact end check (:174); pairs only while `end − position ≥ 2` and
  `remaining ≥ pairBits`, and only if the pair table is built.
- Every stream non-empty with a non-zero last byte; keep the jump-table and segment checks (:101-112).
- After decoding `count` bytes, zero `[count, count + 32)` (D0).
- Keep `decode(from:count:fourStreams:) -> [UInt8]` as a thin wrapper (ZstdTests.swift:461).

### Stage 3: zero-copy block output

**D11. Zero-copy block output.**

- `nextBlock` returns an `UnsafeRawBufferPointer` view of the block's bytes in storage instead of `[UInt8]`
  (:126-154, :264).
- Raw blocks are read straight into storage (`prepareBlock` + `ZstdInput.read(_:into:)`); RLE blocks are filled in
  storage. This replaces `storeBlock` and the arrays at :130-131 and :149.
- **Order for raw and RLE blocks (size known from the header):** first check `produced + size` against the content
  size ("zstd frame output exceeds content size", :136-138), then `prepareBlock`. ZstdTests.swift:303-311 asserts
  `allocatedBufferBytes == 0` after that error and stays unchanged.
- A block producing 0 bytes never calls `prepareBlock` (today's `!bytes.isEmpty`, :118); an RLE block of size 0
  still consumes its byte. D1/D2 scratch is allocated only when a compressed block arrives.
  `testHugeWindowsAllocateOnlyProducedBytes` (ZstdTests.swift:236-277) stays unchanged.
- The raw-block read pattern keeps `testListingReadVolumeAndDirectBlockReads` (ZstdTests.swift:602-626: at most
  ⌈encoded / 64 KiB⌉ source reads and exactly `encoded.count` bytes read) and
  `testInputDirectReadThresholdAndSkipBoundaries` (:628-655).
- XXH64 is updated from the view (new `update(_ bytes: UnsafeRawBufferPointer)`, same stripe/tail logic,
  ZstdXXH64.swift:35-54).
- `ZstdDecompressor` keeps `(view, offset)` instead of `pending: [UInt8]` (:9-10, :29-38, :59-63).
- **Lifetime:** the view is valid until the next `nextBlock` call or the frame decoder's release. `ZstdDecompressor`
  calls `nextBlock` only after the view is consumed and sets `frame = nil` only then (today :29-40). The last block's
  content-size and checksum checks (:140-146) run before its view is returned.
- Tests that call `nextBlock` (ZstdTests.swift:222, :248, :267, :307, :320, :323) compare `Array(view)`.

**D12. Optional, only if it measures ≥ 1%.** Read the next block header together with the current block body to
avoid the 4 KiB read per block (ZstdBitReader.swift:162-167). Keep both read-pattern tests above, or change them
deliberately and explain it in the record.
