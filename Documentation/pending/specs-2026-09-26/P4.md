## この版での調停（2026-09-25）

反証レビュー反映版（指摘 F1–F17 を反映済み）を、P5 と共通の設計（`specs/final-p2p3/ORDER-P2-P3.md` の §1–§2。以下「ORDER23」）と `specs/final-p45/ORDER-P4-P5.md`（以下「ORDER45」）に合わせて、次のとおり改めた。

1. **出力の部品**: 旧 §0.4 の案を、ORDER45 §1.1 の最終の形にした（`SplicedCommitPlan`、`CommitProgressMeter`、`makeScratch`、`generated`、`finalPatch`）。部品は P2-G（S11）が作り、LHAUpdater は `source` と `literal` だけを使う。形を変える必要が出たら、止めて報告する。
2. **照合の読み取りの観測**: `SplicedArchiveOutput.verificationReadObserver` 一つにした。V2 の単位は V2 が読む byte（output と source の header。2 × header 長）にし、AC-Gb7 の等式が観測と一致するようにした。
3. **`ZipUpdateSource(duplicating:)`**（internal）を P4-G-b で作る。LHA の V3(b) と、P5 の V1・V3・V3a が共有する。
4. **KF の枝**: `rewriteBranch(format:)` は `willOpenUpdater` を呼ばない（ORDER45 §1.2 で P2-A を改める）。`callsWillOpenUpdater:` の引数は作らない。圧縮 tar の条件を三形式にする修正と probe の knob は、ORDER45 §1.3 で P3-A に入れる。入っていなければ P4-A が入れる。
5. **段と版**: B-P4 の KaitoKit は S14（S17 で 0.12.0 の tag を付けた commit）。S22 は KaitoKit 0.13.0 → GyoshukuKit 0.9.0 に決め、P5 の KaitoKit 部分をまとめない（P5 は S26）。
6. **行番号の基準**: KaitoKit は 24311ac。LHA の parser のファイルは ba42ed8 と同一。
7. **受入計測**: PROBE-TSV の `format/fixture/mode/operation/stage` の名前で書いた（fixture は `entries` / `payload`）。

@_spi(LHARawLayout)
public struct LHAMemberLayout: Sendable, Equatable {
    /// [headerOffset, dataOffset)。level 1 は拡張 header の列を含む。
    public let headerRange: Range<UInt64>

    public let dataRange: Range<UInt64>
    public let headerLevel: UInt8           // 0...3

    public let osID: UInt8?                 // level 0 で OS byte が無ければ nil
    public let crc16: UInt16                // header の data CRC16 欄
    /// ArchiveReader.entries の index。公開しない member は nil（LHAHeaderParser.swift:1093-1099）。
    public let entryIndex: Int?
}

@_spi(LHARawLayout)
public enum LHAArchiveTerminator: Sendable, Equatable {
    case zeroByte(offset: UInt64)                   // LHAHeaderParser.swift:176-179
    case emptyNameDirectoryMember(Range<UInt64>)    // :237-240。範囲はその member 全体。後ろは読まない
    case endOfFile                                  // :281-285。LArc か anonymous の後で EOF
}

@_spi(LHARawLayout)
public enum LHATrailingBytes: Sendable, Equatable {
    case none                       // 終端が zeroByte で、その後ろに byte が無い

    case nonZero(count: UInt64)     // 0 以外を含む
    case unchecked(count: UInt64)   // 65,536 byte を越えるので読んでいない

}

@_spi(LHARawLayout)

    public let archiveLength: UInt64
    /// 最初の member の header の offset（SFX の prefix 長。通常は 0）。member が無ければ終端の offset。
    public let firstHeaderOffset: UInt64

    public let endOfMembersOffset: UInt64

    public func member(at position: Int) throws -> LHAMemberLayout

// UpdaterRouteError.swift（TarUpdater.swift から移す）
/// updater の経路の error。TarUpdater・CompressedTarUpdater・LHAUpdater・SevenZipUpdater（P5）が共有する。
public enum UpdaterRouteError: Error, Sendable, Equatable {
    /// この書庫またはこの設定は updater で編集しない。ArchiveRewriter で書き直すこと。
    /// open からだけ投げる。原本・output・一時ファイルには何も残っていない。
    case requiresRewrite(reason: String)
    /// commit の中の読み戻しで、出力が計画と一致しなかった（GyoshukuKit の不具合）。書庫の性質ではない。
    case outputVerificationFailed(reason: String)

public typealias TarUpdaterError = UpdaterRouteError

// LHAUpdater.swift（public import KaitoKit。SPI はこのファイルで import しない）
/// LHA の追加・削除・改名。運ぶ member の byte は変えない。追加は末尾。thread-safe ではない。
/// 原本は読むだけで、output を新しく作る。output の mode・xattr・作成日の復元と公開（rename）は呼出側。
/// open のエラー: WriterError（options・output の検査・原本の flags・clone）、KaitoError（KaitoKit の解析）、
/// UpdaterError.invalidArchive（LHA でない）、RewriterError.unrepresentable（門番）、UpdaterRouteError.requiresRewrite。
public final class LHAUpdater: ArchiveEditing {
    public static func open(url: URL, output: URL, options: WriterOptions = WriterOptions()) throws -> LHAUpdater
    /// 構造から open が requiresRewrite を投げると分かる場合の理由。nil は「open の walk（R8）以外では updater で編集できる」。
    /// reader を変えず、終端の後ろを最大 64 KiB 読む。R0・R7・R8 は判定しない。
    public static func rewriteReason(reader: ArchiveReader) -> String?

### DESIGN

**K1 記録**:
- `headerOffset` は、各 parser の引数の `offset`（または上の導出）。
- `osID` は、level 0 では CRC の後の byte（:336-337）、level 1/2/3 では base header の値。
- `dataRange` は record の `dataOffset ..< dataOffset + compressedSize`。`headerRange` は `headerOffset ..< dataOffset`。
- level 1 の `dataOffset` は拡張 header の列の後（:478）なので、どの level でも `headerRange.upperBound == dataRange.lowerBound` が成り立つ。
- OS-9 の `K` の level 2 は、実際の header 長（宣言長 + 2、:575-590）を使う。

**K2 終端**: `parse` の loop（:172-273）を抜けた理由で決める。
- 0 byte（:176-179）→ `.zeroByte(offset)`。
- 空名の `-lhd-`（:237-240）→ `.emptyNameDirectoryMember(offset ..< parsed.nextOffset)`。
- :281-285 の EOF の受理 → `.endOfFile`。
- `recoverDamagedArchives` の読み手は記録を作らない（SPI は nil を返す）。

**K3 公開しない member**:
- `publish` の `continue`（:1093-1099）で捨てる record を、書庫の順での位置と一緒に `unpublishedMembers` に残す（通常は空）。
- SPI の `member(at:)` は、公開する record（entry k）と公開しない record を、書庫の順に合わせて返す。公開しない member の `entryIndex` は nil。
- 記憶の使用量は、公開する entry あたり +16 B 以内。公開しない member は、その数に比例するだけ。

**K4 `lhaRawLayout()`**:
- 次のどれかなら nil を返す。
  - `reader as? LHAReader` が nil。
  - `options.recoverDamagedArchives`。
  - `volumeSet != nil`、または `source is ConcatenatedByteSource`。
- 終端が `.zeroByte(offset)` のとき、`offset + 1 ..< source.length` を分類する。
  - 長さ 0 なら `.none`。
  - 65,536 以下なら、一度に読んで `.zeros` か `.nonZero` にする。
  - 越えれば読まずに `.unchecked`。
  - 他の終わり方では `.notApplicable`。
- 読み取りの失敗は `KaitoError` として投げる。
- `endOfMembersOffset` は、最後の member の `dataRange.upperBound`（member が無ければ `firstHeaderOffset`）。`.zeroByte` の offset と一致する。
- `firstHeaderOffset` は `startOffset`（ArchiveReader.swift の LHA 分岐の SFX 候補の offset）。
- 返す値は reader から独立した Sendable の値で、内部の record の配列を共有する（`member(at:)` で必要な所だけ作る）。

### DESIGN

**Ga1 member ごと**（1 MiB 以下、`threads > 1`。LHAWriter.swift:22-51 の置き換え）:
- 入力を読む前に `pipeline.waitForCapacity(emit:)` を呼ぶ（ZIP の ArchiveWriter.swift:454 と同じ）。同時に抱える入力を、threads 個に抑えるため。
- 入力の読み取りと CRC16（:31-43）は、今日どおり呼出側の thread で行う。
  - 読み取りの失敗と `sourceChanged` は add の中で出る。
  - add が戻る時点で、入力の file handle は読み終わっている。
- `OrderedChunkPipeline<Data, Data?, Pending>(threads:)`。worker は注入された `encoder(input)` を行い、縮めばその byte を、縮まなければ nil を返す。
- `Pending`（呼出側だけが扱う tag）は、`LHARecords.Entry`、CRC16、`-lh0-` のときに書く入力（`Data`）、directory かどうか、を持つ。
- emit（呼出側、投入の順）は、今日の :45-49 と同じ規則で method を決め、header と payload を書く。directory は `submit(nil, tag:)` で順番だけを取る。
- 先に `drain` する時点: 1 MiB を越える member の前、`finish()`、`endMembers()`。
- `abort()` は、pipeline を `abandon()` してから、今日の :117-129 を行う。
- 記憶: 同時の入力は threads 個まで。thread ごとに、入力 1 MiB + 出力と、`LH5Encoder` の表（約 1.1 MiB）。

**Ga2 1 MiB を越える member**（`addStreamed`、:53-107、`threads > 1`）:
- 読み取り・raw の出力への書き込み・CRC16 は、今日どおり呼出側で順に行う。
- 各区切りの入力（直前までの 8 KiB の履歴 + 1 MiB）は、今日の :67-80 と同じ規則で作り、`OrderedChunkPipeline<Piece, PieceOutput, Void>` に投げる。
- worker は、新しい `Bits` に `LH5Encoder.write(input, startingAt: prefix, to: &bits)` を行い、完成した byte と、残りの bit（値と bit 数）を返す。
- emit（呼出側、順番どおり）:
  1. 走っている `Bits` にその出力を継ぎ、完成した byte を spool へ書く。bit 位置が 0 でなければ、各 byte を shift する。
  2. 今日の :87 と同じく、`compressing = spool.size < size` を区切りごとに評価する。false になった時点で pipeline を `abandon()` し、以後の区切りは投げない（raw の書き込みは続ける）。
- 出力が byte 一致する理由:
  - `write` の呼出しは毎回新しい表から始め（LH5Encoder.swift:32-35）、呼出しの終わりで block を閉じる（:93）。呼出しをまたぐのは bit 位置だけなので、区切りごとの bit 列の連結は、今日の一本の `Bits` と同じになる。
  - 早めの打ち切りも、同じ区切りの後で同じ判定になる。無駄になる符号化は、threads 個の区切りまで。
- 最後に、今日の :90-105 と同じ規則で、縮めば spool を写し、header を直す。
- `Bits` に足すもの（internal）: 残りの bit を読む accessor と、別の `Bits` の出力（完成した byte + 残りの bit）を継ぐ `mutating` の操作。`encode` / `write` / `finish` / `takeCompleteBytes` の意味は変えない。
- 記憶: threads × (1 MiB + 8 KiB + 出力)。

**Ga3 失敗と取消し**:
- 符号化の失敗（取消しを含む）は、後の add / drain / finish / endMembers で出る。ZIP / 圧縮 tar / 7z と同じ扱いで、doc comment に書く。
- worker は GCD の thread で動くので、TaskLocal は届かない。失敗の注入は、`encoder` 引数で行う。
- どこで失敗しても、`ArchiveWriter.perform` の今日の経路（ArchiveWriter.swift:262-278）で `abort` し、出力を消す。

**Ga4 `endMembers()`**:
- 追記用。`drain` した後、終端・同期・close を行わずに `finished = true` にし、`output.offset()` を返す。
- `ArchiveWriter.endLHAMembers()` はこれを呼び、state を finished にする。
- `memberRecords` は、emit の時点の値を記録する: header の絶対 offset、header 長、data 長、method、KaitoKit の `canonicalRawName` と同じ規則で作った名前の byte（0xFF を `/` にした directory + filename）。

| L1 | `firstHeaderOffset != 0`（SFX） | SPI | stub の扱いは決めていない（今日の rewriter は落とす） |
| L2 | `terminator` が `.zeroByte` でない（空名の `-lhd-` で終わる、EOF で終わる） | SPI | 空名の `-lhd-` の後ろの byte と、終端の無い書庫への追記の意味を決めていない |
| L3 | `trailingBytes` が `.nonZero` か `.unchecked` | SPI | KaitoKit が本物の member の手前で止まっている可能性がある（tl-S11）。rewriter も後ろを落とす |
| L4 | `unpublishedMemberCount > 0` | SPI | 公開しない member を運ぶかどうかを決めていない（今日の rewriter は落とす） |
| L5 | level 3 の member がある | SPI | GK の walk と header の出し直しは level 0/1/2 だけ |
| L6 | `entry.isIncomplete` がある | KaitoKit の公開値 | 安全網。GK は recovery で開かないので、KF からは到達しない（KF の試験は作らない） |
| L7 | `kind == .directory` の entry で、`method != "-lhd-"`、`dataRange.count > 0`、`uncompressedSize != 0` のどれか | KaitoKit の公開値 + SPI | KaitoKit の directory は、`-lhd-` だけでなく attribute 0x10 や名前の末尾の `/` でも決まる（LHAHeaderParser.swift:1084-1085）。data の大きさの検査は `-lhd-` にしか無い（:1394-1402）。改名で `-lhd-` に出し直すと data が落ち、`.update` の projection のサイズの照合が正しい編集を拒否する |
| L8 | method が `-lh7-` で、OS ID が 0x20（LHArk）の member がある | SPI | KaitoKit は OS ID で LHArk の文法を選ぶ（LHAReader.swift:122-132）。改名で OS `U` に出し直すと、中身が化ける。V1 と KF の検証は payload を復号しないので、捕まえられない |
| L9 | `dataRange.count > UInt32.max` の member がある | SPI | level 2 の出し直しでは圧縮後のサイズを 32 bit で書く。門番は元のサイズしか見ない（ArchiveRewriter.swift:192-198）ので、改名が `sizeOverflow` になる（操作ごとの拒否を作らない） |

- `UpdaterError.invalidArchive`、KaitoError、`RewriterError.unrepresentable` は、rewriter へ戻す理由ではない。今日どおり、読み取り専用か失敗になる。
- `rewriteReason(reader:)`:
  - 同じ SPI と公開値だけで、R10・L1–L9 を判定する（`LHALayout` の同じ関数）。
  - SPI が nil か throw なら、理由を返す（注意書きを出す側に倒す）。
  - R0・R7・R8 は判定しない。設定と名前は KF が別に解決し、R8 は walk でしか分からない（ORDER23 §7-7 と同じ扱い）。
  - 費用は、O(member 数) の型付きの走査と、終端の後ろの最大 64 KiB の読み取り。

#### Gb4 LHALayout: 独立した walk と照合

- 目的: SPI の境界を、KaitoKit の parser とは独立に確かめる（P2 §G4、P3-G D2-1-7 と同じ考え方）。walk の入力は、`ByteSource`（snapshot）と長さだけ。
- 読み方:
  - offset 0 から、4 KiB の窓で header を読む。次の header が窓の中ならそこから、外ならその offset から読む。
  - header が窓に収まらないときは、その header の全体を読む。level 0/1 は base の長さ、level 1 は拡張 header の列の各 record、level 2 は全長（最大 65,535 B）。header CRC は全体に対して確かめる。
  - payload は読まない。
  - 取消しは 1,024 member ごと。
- header の解釈（KaitoKit と同じ規則。違えば R8）:
  - 先頭の byte が 0 なら終端。残りが 21 byte 未満なら R8（KaitoKit は truncated を投げる）。
  - level 0:
    - 長さ = byte[0] + 2（24 以上）。8 bit の和（byte[1] = byte[2..<長さ] の和）。byte[20] == 0。method の形（LHAHeaderParser.swift:1278-1290）。
    - 名前が header に収まる（`22 + 名前長 ≤ 長さ − 2`）。
    - data 長 = byte[7..<11]。
  - level 1:
    - base の長さ = byte[0] + 2（27 以上）。8 bit の和。byte[20] == 1。`22 + 名前長 ≤ base − 5`。
    - 拡張 header の列は、base の最後の 2 byte の長さから辿る。各 record は type・data・次の長さで、長さは 3 以上。列の合計は skip size 以下。
    - data 長は、0x42 があればその値、無ければ skip size − 列の合計。header 長 = base + 列の合計。
    - 0x00 があれば、base と拡張 header の列の全体を繋いだ byte で、その欄を 0 にした CRC16 を確かめる（LHAHeaderParser.swift:773-829、:1259-1276）。
  - level 2:
    - 全長 = LE16 byte[0..<2]（26 以上）。byte[20] == 2。
    - 拡張 header の列は byte[24..<26] から、全長の中で辿る。列の後の詰め物は許す。
    - 0x00 があれば、その欄を 0 にした header 全体の CRC16 を確かめる。
    - data 長は、0x42 があればその値、無ければ byte[7..<11]。
    - `K` の宣言長の不足（:575-590）は解釈しない（R8）。
  - level 3 は L5（SPI で先に判定している）。
  - 名前の byte は、KaitoKit の `canonicalRawName`（:1292-1311）と同じ規則で作る。
    - 元になる名前: level 0 は base の名前、level 1 は 0x01（空でなければ）か base の名前、level 2 は 0x01。directory は 0x02。
    - filename は NUL の前だけを使う。directory が NUL を含めば R8。
    - 0xFF を `/` にする。directory が空でなく、名前も空でなく、directory が `/` で終わらなければ `/` を挟む。
- 照合（member k ↔ SPI の `member(at: k)` ↔ `reader.entries[k]`。L4 により全 member が公開されている）。次のどれかが違えば R8。
  - 件数。
  - 各 member の `headerRange`・`dataRange`・`headerLevel`・`method`・`osID`・`crc16`、`entryIndex == k`。
  - 名前の byte が `entries[k].rawName.bytes` と等しいこと。
  - walk の終端の offset、`terminator` の `.zeroByte(offset)`、`endOfMembersOffset` の三つが等しいこと。
- 記憶: walk は何も保持しない。計画は、照合の後に SPI の `member(at:)` を使う。
- 試験用に、internal の `LHALayout.testingKaitoKitMismatch: TaskLocal<Bool>` を置く。

#### Gb5 予約と改名した member の header

- 予約は P2 §G5 と同じ（`names` から `EditPathReservations`、`survives`、root の扱い、重複の remove、削除済みの改名は `invalidEntryIndex`、追加した名前の同期）。
- **運ぶかどうかは `!removed.contains(i)` で決める**。root（`names[i] == ""`、名前が `.` の directory）も運ぶ。
- `rename(entryAt:to:)`:
  - `ArchiveWriter.normalizedPath(path, directory:, format: .lha)` で正規化する（`:` と `\` の禁止、NFC）。
  - 正規化した名前が `names[i]` と同じなら、byte を変えない（予約だけ）。
  - 違えば、**このときに**新しい header を作って保持する（改名 1 件あたり 100 B 前後。フォルダの改名で全 member が変わっても、100k で 10 MB 程度）。
    - file の header:

      ```swift
      LHARecords.Entry(name: 新しい名前, mode: ArchiveRewriter.mode(for: entry),
                       size: entry.uncompressedSize ?? 0, date: entry.modificationDate ?? Date())
          .header(method: member.method, packedSize: UInt32(member.dataRange.count), crc: member.crc16)
      ```

      - L9 により、`dataRange.count` は UInt32 に収まる。
      - CP932 で表せない名前は `WriterError.invalidPath`、64 KiB を越える header は `sizeOverflow` になる（LHARecords.swift:11-30、:59）。どちらも新しい名前という入力の誤りで、今日の rewriter と同じ種類の失敗になる。updater は failed になる。
    - directory の header: `LHAWriter` の directory と同じ（`-lhd-`、packed 0、CRC 0）。L7 により、updater に来る directory は `-lhd-` で data が 0 byte なので、落ちる byte は無い。
    - header 長の下位 byte の規則（LHARecords.swift:53-58）は、`LHARecords` がそのまま適用する。このため、名前の長さが同じでも header 長が 1 byte 変わることがある。
- **改名した member が失うもの**（design.md と CHANGELOG に書く）。今日の rewriter が全 member に行っていることを、改名した member にだけ行う形になる。
  - level は 2 になり、OS id は `U`、base の attribute は 0x20 になる。
  - 拡張 header は 0x00・0x01・0x02・0x50・0x54 だけになる。0x3F（comment）、0x40（DOS 属性）、0x41（Windows の時刻）、0x42（64 bit のサイズ）、0x46（code page）、0x51（uid/gid）、0x52・0x53（名前）、未知の拡張は落ちる。
  - 時刻は、KaitoKit の `modificationDate` の Unix 秒（切り捨て）になる。
    - level 0/1 の DOS 時刻は、KaitoKit が `TimeZone.current` で解いた値（LHAHeaderParser.swift:1415-1456）になる。
    - 0x41 の秒未満は落ちる。
    - 日付が無ければ `Date()`。
  - permission は `ArchiveRewriter.mode(for:)` になる。OS が `U` の member だけ元の値で、他は 0644 / 0755。
  - 変わらないもの: method、payload の byte、data CRC16、元のサイズ、KaitoKit で読んだ内容。OS に依る解き方の member は L8 で来ない。MacLHA の `m` は、門番を通った時点で envelope を持たない。
- 改名しない member は、level 0/1/2・OS id・拡張 header・名前の byte・時刻の表現のすべてが byte のまま。

#### Gb6 LHAEditPlan（純関数）

- 入力: SPI の member の表（件数 n、各 `headerRange`・`dataRange`）、`removed`、`renamed`（index → header の byte）、追加 block の長さ A（あれば）。
- 出力: segment の列（`SplicedSegment` の `source` / `literal`）、生存 member の終わり M'、各 member の出力 offset、変えた member の一覧、V2 の境界の一覧と header 長の和。
- member ごとの出力:

  | member | 出力 |
  |---|---|
  | 削除 | なし |
  | 変えない | `source(headerRange.lowerBound ..< dataRange.upperBound)` |
  | 改名（file） | `literal(新しい header)` + `source(dataRange)` |
  | 改名（directory） | `literal(新しい header)` |

- source 側が厳密に連続し、出力側も連続する segment だけを併合する。segment の数は、変更の数に比例する。
- 追加 block は M' に置く。
- **終端**:
  - 変えた commit（削除・改名・追加のどれかがある）では、`terminal = [0]`、`finalLength = M' + A + 1`。
  - 変えない commit（正規化後に同じ名前への改名だけを含む）では、output を原本と同じ byte にする。prefix は原本の全体の `source` 一つで、terminal は空。clone mode は clone のまま、sequential mode は全体の copy（部品の「変えない plan」）。
  - 全件を削除した場合は、L1 により `firstHeaderOffset` が 0 なので、出力は 1 byte の `[0]` になる。
- **header の長さが同じ改名**: 前の member で位置の差が生じていなければ、新しい header は元と同じ位置に来る。特別な枝は作らない（P2 §G6.4）。
  - GK 製の level 2 の member で新しい header の長さが元と同じなら、clone mode では header だけを書く。
  - level 0/1 の member の改名は、ほぼ常に長さが変わり、後ろをずらす。

#### Gb7 追加

- P2 §G7 と同じ。最初の add で、その時点の予約で計画し、`P_add = M'` として `SplicedArchiveOutput.beginAppend(at: P_add, prefix:)` を呼ぶ（sequential mode では P_add までを先に書く）。
  - writer は、返る FileHandle（dup 済み）の上に作る。

    ```swift
    ArchiveWriter(output: handle, url: output, identity:, format: .lha, options:,
                  lhaWriter: LHAWriter(output: handle, url: output, identity:, threads: options.resolvedCompressionThreads))
    ```

  - `prepareAppend(at: P_add, existingPaths:)` で、位置と名前の集合を合わせる。`recordsMembers = true`。
- 以後の add はこの writer へ渡す。
  - `add(contentsOf:as:ownerIDs:)` は、ownerIDs が nil 以外なら、何もせずに `WriterError.unsupportedOption("ownerIDs")` を投げる。引数の誤りなので、updater は failed にしない。
  - `addDirectory(_:modificationDate:ownerIDs:)` は、日付を ArchiveWriter の internal の `addDirectory(_:modificationDate:ownerIDs: nil)`（P2-G）へ渡す。
- commit では `endLHAMembers()` で `appendedEnd` を得る。pipeline に残る member は、ここで書かれる。
- writer が失敗したとき:
  - `LHAWriter.abort()` は output を 0 に切り詰め、同一性が一致すれば unlink する（LHAWriter.swift:117-129）。clone mode ではこれで clone も消える。
  - add の名前の衝突（`duplicatePath` など）でも同じになる（`ArchiveWriter.perform`）。
  - それで構わないのは、updater が failed になり、cleanup で snapshot も消すため。このことを comment に書く。
- `addStreamed` は、共有の file offset で seek と truncate をする。updater と `SplicedArchiveOutput` は pread / pwrite だけを使うので、offset の共有は問題にならない（P2 §G7 と同じ）。
- 再配置（「追加の後に予約」で M' が `P_add` と違う場合）は、`SplicedArchiveOutput.commit` が一時ファイルで行う（strategy `relocatedAppend`）。

#### Gb8 commit

- 次の順に進める:
  1. checkUnchanged → `endLHAMembers` → 最終計画（`SplicedCommitPlan`）→ 取消しの検査。
  2. `meter = CommitProgressMeter(total: output.units(for: plan), progress: progress)` → `meter.start()`。
  3. `output.commit(plan, meter: meter, verify: V1–V4)`。中身は作成・再配置・segment・終端・`ftruncate`・fsync・V5・形式の照合・close（ORDER45 §1.1）。
  4. `meter.finish()` → snapshot の削除 → `lastCommitStrategy`（`SplicedCommitStrategy` を写す）→ committed。
- 進捗は共通の契約どおり。
  - total = `units(for:)` = 書く byte（segment、終端、再配置の往復）+ V5 の読み取り + `formatVerificationUnits`。計画の後に確定し、変えない（LHA では正確で、`finish()` は差を足さない）。
  - V2 は、境界ごとに、読んだ byte（2 × その header 長）だけ `advance` する。
  - V3 は、追加 member を一つ確かめるごとに、その header 長 + data 長だけ `advance` する。
  - V1・V4 の読み取り（書いた header の長さ + 1 byte 程度）は、total に含めない。
- 書く量（clone mode）:

  | 操作 | 書く量 |
  |---|---|
  | 末尾の削除 | 終端の 1 byte |
  | header の長さが同じ改名（level 2） | 新しい header + 終端 |
  | 追加 | 追加 block + 終端 |
  | 途中の削除、header の長さが違う改名（level 0/1 の改名を含む）、置換 | 最初の変更位置から後ろ全部 + 終端 |

  sequential mode では、output 全体を一度ずつ書く。

#### Gb9 照合（書いた量に比例。commit の中、fsync の後）

- output の記述子から読む。copy engine の観測には数えない。
- **V1 書いた header**: 改名した header が、計画の位置で計画の byte と一致する。さらに §Gb4 の walk の規則で level 2 として解け、次が成り立つ。
  - header CRC が合い、名前の byte が計画どおり。
  - file では、method・data 長・CRC16 が元の member と同じ。directory では `-lhd-`・data 長 0。
  - 先頭の byte が 0 でない。
- **V2 境界**: 出力の source segment が member の先頭で始まる所（書いた segment も clone の segment も）で、output の header の byte が、source の同じ member の header と一致する。読み取りは `verificationReadObserver` に報告する。
- **V3 追加 block**:
  - (a) `[P_add, appendedEnd)` を walk すると、`LHAWriter.memberRecords` と同じ offset・header 長・data 長・method・名前の byte が同じ順で出て、`appendedEnd` で終わる。
  - (b) `ZipUpdateSource(duplicating: output)` の上に、`[P_add, appendedEnd)` + `[0]` を独立した LHA として見せる `ByteSource` を作り、`ArchiveReader.open(source:options:)` で開く。options は §Gb3 の 6 と同じ。member を 1 つ以上含むので、内容で判定される。次を確かめる。
    - 件数・`rawName.bytes`・サイズ・method・`headerOffset` / `dataOffset`（view の座標）が、記録と一致する。
    - 各 member を `stream(entry)` で最後まで読み、KaitoKit の CRC16 の検査を通る。
  - 進捗は、固定の単位（§Gb8）で進める。KaitoKit が実際に読んだ量には依らない。
- **V4 終端**: output の長さが計画どおりで、最後の byte が 0。変えた commit では、その後ろに何も無い。
- **V5**: 書いた source segment ごとに、output と snapshot（sequential mode では原本）の同じ範囲を 4 MiB ずつ pread して memcmp する（`SplicedArchiveOutput` が行う）。
- 失敗は `UpdaterRouteError.outputVerificationFailed`（failed、cleanup、原本は無傷）。
- 公開前の KF の全体の header 解析と、`.update(.lha)` の projection の照合（P4-A）は、これとは別に残る。運んだ member の payload は、どこでも復号しない。byte のまま運び、V2・V5 と KF の header 解析で確かめる。OS に依る解き方の member は L8 で来ない。

#### Gb10 試験の hook

- `@_spi(Testing)`: `CommitStrategy`、`lastCommitStrategy`、`testingDisablesClone`（§0.2）。
- internal（GK の試験は `@testable import`）:
  - `LHAUpdater.testingFault: TaskLocal<Fault?>`。値は `flipWrittenByte(offset)`・`shiftSourceSegment`・`dropTerminator`・`corruptWrittenHeader`・`corruptAppendedPayload`。fsync の前に output を書き換え、V1–V5 のどれかが捕まえることを確かめる。呼出側の thread で読むので届く。
  - 照合の読み取りの観測は `SplicedArchiveOutput.verificationReadObserver`（V2・V5）。V3(b) の読み取りは `ZipUpdateSource.readObserver` の、dup した記述子の報告で分けて見る。
  - `LHALayout.testingKaitoKitMismatch`。
  - clone を ENOTSUP / EXDEV 以外で失敗させる注入。P1-G の `ArchiveSourceSnapshot.testingCloneError` を共有する。
  - 符号化の失敗は、P4-G-a の `encoder` 引数で注入する（TaskLocal は worker へ届かない）。
- 変更できる global の状態は、TaskLocal だけ。

#### Gb11 LHAUpdater と ArchiveRewriter（fallback と従来の設定）の違い

| 性質 | ArchiveRewriter | LHAUpdater |
|---|---|---|
| 運ぶ member | 復号して LH5 で符号化し直し、level 2・OS `U`・CP932 の名前にする。lh6/lh7 などは lh5 になる | byte 単位で同一（level、method、拡張 header、名前の byte） |
| 改名した member | 同上 | header だけを level 2 で出し直し、payload は byte のまま（§Gb5） |
| 追加 | 設定どおり（`.end` / `.beginning`） | 常に末尾 |
| 終端の後ろの byte | 落とす | 0 だけなら、変えた commit で落とす。0 以外は L3 で rewriter へ戻す |
| 1 回の編集の費用 | 全 member の復号と符号化（P4-G-a で並列） | 変更位置から後ろの copy と、追加の符号化・復号（V3） |

### CONSTRAINTS

- 出力の byte: `ArchiveUpdater`・`TarUpdater`・`CompressedTarUpdater`・`ArchiveRewriter`・`ArchiveWriter.create` は、S18 の後の出力と一致する。
- `SplicedArchiveOutput.swift` を変えない。
- LHAUpdater は原本を書かない（O_RDONLY 以外で開かない）。読む inode と書く inode は、常に別。
- 読み取り:
  - commit で source から読むのは、書く source segment の範囲だけ（clone mode では、位置の変わらない範囲を読まない）。
  - walk は header だけを読む。照合は、書いた量・追加した量・境界の数に比例する。
- 検査を弱めない。次を残す。
  - KaitoKit の open
  - `validateRepresentability` の全件
  - walk と SPI の照合
  - checkUnchanged
  - V1–V5
- 新しい public は §0.2 のものだけ、`@_spi(Testing)` は §Gb10 のものだけ。`UpdaterError` / `RewriterError` / `WriterError` に case を足さない。
- import の置き場所:
  - `@_spi(LHARawLayout) internal import KaitoKit` は、SPI を使う internal だけのファイル（`LHALayout.swift`、必要なら `LHAAppendedMemberCheck.swift`）に置く。
  - `LHAUpdater.swift` は `public import KaitoKit` にする（P1-G の `ZipCentralDirectory.swift:2` と `ArchiveUpdater.swift:3` の分け方と同じ）。

#### A2 publish の `.update(.lha)` の枝

ORDER45 §3.2 の形（P2-A §A3 と同じ）。`requiresRewrite` を捕まえるのは open だけ。

```swift
case .update(.lha):
    outputFormat = .lha
    work = directory.appendingPathComponent("archive." + ArchiveCreationPlan.filenameExtension(for: .lha))  // "archive.lzh"
    try willOpenUpdater?()                            // この枝で一度だけ
    var updater: LHAUpdater?
    do {
        updater = try ArchiveStageDiagnostics.measure(.updaterOpen) {
            try LHAUpdater.open(url: archive, output: work, options: options)
        }
    } catch UpdaterRouteError.requiresRewrite(let reason) {
        didFallBackToRewriteForTesting?(reason)   // P2-A の DEBUG hook
    }
    if let updater {
        publishedMode = mode
        try ArchiveStageDiagnostics.measure(deferredPlan == nil ? .mutate : .replay) { try mutate(updater) }
        try ArchiveImportPlan.checkCancellation(progress)
        progress.totalUnitCount += 1000               // 1000 単位を足すのはここだけ
        do {
            try ArchiveStageDiagnostics.measure(.commit) { try updater.commit(progress: /* P1b の写し */) }
        } catch UpdaterRouteError.outputVerificationFailed(_) { throw ArchivePublicationError.verificationFailed }
        try preserveAttributes(from: archive, to: work, includingCreationDate: true)
    } else {
        publishedMode = .rewrite(.lha)
        try rewriteBranch(format: .lha)               // willOpenUpdater を呼ばない（ORDER45 §1.2）。lstat(work) が ENOENT であることを確かめてから
    }
```

- 作業ファイルの名前は `archive.lzh`（ArchiveCreationPlan.swift:39-49）。全件を削除した 1 byte の出力も、この名前のヒントで検証の open が通る（FormatDetector.swift:334-339）。
  - 元の名前に `lha` / `lzh` の拡張子が無い書庫（内容で判定したもの）で全件を削除すると、公開後のファイルは名前で開き直せない。今日の rewriter も同じ 1 byte を書くので、今と同じ制限である。検証の文書に書く。
- 公開前の検証は、P0・P1-A の全体の open と、`expectedOutput.resolving(publishedMode).validate(verified, format: .lha)` のまま。
- error の写し:
  - `outputVerificationFailed` → `ArchivePublicationError.verificationFailed`（P2-A と同じ写し。S5 の診断に updater の自己照合の case があれば、それを使う）。
  - KaitoError、`UpdaterError.invalidArchive`、`WriterError`、`RewriterError.unrepresentable` はそのまま返す（P2-A §A3 と同じ）。
  - `UpdaterError.sourceChanged` はそのまま失敗。
- `didCommitForTesting` の時点の作業ディレクトリは `["archive.lzh"]` だけ（fallback でも同じ）。

#### A3 期待する出力（ArchiveOutputProjection）

- `.update(.lha)` は、P2-A §A4 の `.update` の意味をそのまま使う。
  - 生存 entry を元の順に並べ、名前だけを改名後にする。種類とサイズは元の entry のまま（root の directory を除かない、directory のサイズを 0 にしない）。
  - 追加は今日と同じ entry を、生存 entry の後ろに呼出し順に並べる。
  - 検証では、並び順・種類・既知のサイズを、一回の走査で照合する。
- hard link の規則は当たらない（LHA の entry に `.hardlink` は無い）。tar の追加の hard link の重複の規則（ArchiveOutputProjection.swift:71-78）も、tar だけのまま。
- 改名した LHA の directory は、GK が `-lhd-` で出し直す。KaitoKit の種類は `.directory` のまま。

#### A4 注意書き（P3-A §A7 に足す規則。ORDER45 §3.3 の表の LHA の行）

- 解決後が `.update(.lha)` で `lhaRewriteReason != nil` のとき、既存の 2 キーを出す。onSave なら「保存するとアーカイブ全体を再圧縮します」、そうでなければ「編集するとアーカイブ全体を再圧縮します」。
- 解決後が `.update(.lha)` で `lhaRewriteReason == nil` のときは nil。
- 解決後が `.rewrite(.lha)`（先頭の設定）のときは、P3-A の規則どおり既存のキー。
- `reloadAfterMutation` の capability の再検査でも、同じ inspect を使う。
  - 全件削除や追加で構造が変われば、注意書きも変わる。
  - R10 (b) の書庫は、最初の書き直しの後に全名前が CP932 になり、注意書きが消える。

#### A5 保存時モード

- P2-A の `replay(on:sourcePassword:progress:preservingOwnerIDs:)` がそのまま効く。LHA では `preservingOwnerIDs` は false で、directory とフォルダには `addDirectory(path, modificationDate: 予約日時, ownerIDs: nil)` が渡る。
- 予約の順（削除 → 改名 → 追加 → フォルダ）は、LHAUpdater の再配置を起こさない。
- 予約中の格納順の表示（ArchivePendingChanges.swift:79-88）と、保存後の並びが一致する（追加は末尾）。

#### A6 分割・APFS 以外・名前

- 分割 LHA（`.lzh.001` …）: `.rewrite(.lha)` のまま。`ArchiveSplitWorkProducer` に `.update` は来ない（P2-A）。
- APFS 以外: LHAUpdater の sequential mode。書く量は output 全体を一度で、今日の rewriter と同じだが、復号と再符号化は要らない。
- 名前:
  - 運ぶ member の名前の byte は変わらない。書庫全体の文字コードが CP932 と推定される書庫と、ASCII の名前だけの書庫が対象。
  - 表示名は KaitoKit の解読のまま。
  - 非 ASCII の名前を持ち `nameEncoding == nil` の書庫は、R10 (b) で rewriter へ戻る（名前は CP932 になる。今日と同じ）。

#### A7 診断と P0b

- `.update(.lha)` の即時編集と保存は、stage `.updaterOpen`・`.mutate` / `.replay`・`.commit` を出し、`.rewriterOpen` と `.workCopy` は出さない。fallback では、`.updaterOpen` の後に `.rewriterOpen` を出す。
- `KAITOFINDER_PROBE_ADDITION_PLACEMENT=beginning` の probe では、LHA は `.rewriterOpen` を出し、`.updaterOpen` を出さない。
- P0b の run に LHA の 500k（1 byte × 500,000）を足してよい。報告だけで、合格条件は無い。

### CONSTRAINTS

- `../GyoshukuKit` と `../KaitoKit` は編集しない。S20 の commit の後に始める。
- 検査を弱めない（P1-A・P2-A の CONSTRAINTS と同じ一覧）。
- 編集できる書庫の範囲と、読み取り専用の理由を変えない。
- 並行性: `LHAUpdater` を session の actor の外へ出さない。DEBUG の hook は `#if DEBUG` の TaskLocal。

- commit しない。

### ACCEPTANCE CRITERIA

- **AC-A1 経路**:
  - 単一の `.lzh` / `.lha`（大文字の拡張子と、内容で判定する拡張子の無い LHA を含む）で、capability が `.update(.lha)`。
    - GK 製・level 0/1/2 混在・ASCII の名前だけの書庫では、`lhaRewriteReason` が nil で、`editNotice` が nil。
    - 次の書庫では、`lhaRewriteReason` が非 nil で、`editNotice` が既存の再圧縮のキー（即時 / 保存時）: SFX、EUC-JP の名前、宣言の無い UTF-8 の非 ASCII 名、0x46 = 65001 の非 ASCII 名、tl-S5、tl-S11、level 3、anonymous、空名の `-lhd-` の終わり、data を持つ directory、LHArk。
  - 読み取り専用の判定は今日と同じ（MacBinary・`-pm2-`・symlink・CP932 で表せない名前・`:` を含む名前）。
  - `.lzh.001` は `.rewrite(.lha)`。
  - `.update(.lha)` の publish が、圧縮 tar の枝に入らない。session の reader の `reopen()` を呼ばない（`sessionReader` が nil）。`editNotice` の圧縮 tar の規則に当たらない。
- **AC-A2 即時編集（LHAUpdateEditTests）**: GK 製の書庫と level 0/1/2 混在の書庫（tl-S3b）で、削除・改名（header の長さが同じ・違う・フォルダ）・移動・追加・新規フォルダ・置換のそれぞれについて:
  - 成功し、`lastCommitStrategy` が期待どおり（`@_spi(Testing) import GyoshukuKit`）。
  - `didCommitForTesting` の時点の作業ディレクトリが `["archive.lzh"]` だけ。原本の inode・byte・mtime は、rename まで不変。
  - 公開後の書庫で、改名しない member の header と payload の byte が元と一致する（level 0 の lh6 の member を含む）。
  - P1-A の採用（`.adopted`）が起き、entries が `ArchiveReader.open(url:)` の結果と一致する。
  - DragInTests.swift:414-438 と同じ属性（mode・quarantine・xattr・作成日時）が保たれる。
  - 全件を削除した後の追加が、即時と保存時モードの両方で成功し、capability が読み取り専用にならない。
- **AC-A3 保存時モード（LHAUpdateDeferredSaveTests）**:
  - 五操作の保存と改名だけの保存が LHAUpdater で成功し、保存後の格納順が、予約中の表示の順と一致する。
  - 予約したフォルダの mtime が、予約日時になる。
- **AC-A4 fallback（LHAUpdateFallbackTests）**:
  - AC-A1 の非 nil の書庫で、即時の削除と保存時モードの保存が成功する。
    - tl-S11 について確かめるのは、経路の切り替わりと、KaitoKit から見た内容だけにする。
    - rewriter は、KaitoKit から見えない後ろの member を落とす（§リスク 3）。これを検証の文書に書く。
  - `didFallBackToRewriteForTesting` と `willOpenUpdater` が一度だけ呼ばれ、stage に `.updaterOpen` と `.rewriterOpen` が一度ずつ出る。
  - mutate は一度だけ（`progress.completedUnitCount` が二重に数えられない）。終わりに `progress.completedUnitCount == progress.totalUnitCount`。公開前の検証は、`.rewrite(.lha)` の期待で通る。
  - R10 (b) の書庫では、fallback の後の再検査で `lhaRewriteReason` が nil になり、二回目の編集は `.updaterOpen` だけで済む。
  - 設定を「先頭」にすると、`.updaterOpen` を出さずに rewriter を使い、追加が先頭になる。書庫を開いたまま設定を変えても、次の編集から効く。`willOpenUpdater` はこの経路でも一度だけ呼ばれる。
- **AC-A5 検証（LHAUpdateVerificationFailureTests）**:
  - `didCommitForTesting` で output の member を二つ入れ替えると、並び順の照合で `verificationFailed` になる。原本は不変で、capability は読み取り専用にならない。
  - publish の DEBUG hook で `UpdaterRouteError.outputVerificationFailed` を投げても、同じ結果になる。
- **AC-A6 名前**: 宣言の無い CP932 + 0x46 = 932 + ASCII の混在の書庫で、即時の追加（日本語の名前）と改名の後も、運んだ entry の表示名が変わらない。
- **AC-A7 APFS 以外（LHAUpdateNonAPFSTests）**:
  - `VolumePublishTestDisk("HFS+")` と `("ExFAT")` の上の LHA で、即時の削除・追加・同長改名と保存が成功する。

- **AC-A8 既存の試験**: SCOPE の 3 か所の期待を改め、従来の設定の試験を残す。変えた試験の一覧を報告する。`ArchiveRewriteTests.swift:486`（LHA の編集と undo）と `ArchiveImportCorrectionTests.swift` の LHA の試験を、変えずに通す。

## リスクと未決（オーケストレータが受け入れ時に見る点）

1. **walk と KaitoKit の一致**: 境界の正しさは、次の五つが担保する。KaitoKit が LHA の解釈を変えても、R8 で rewriter へ戻る（安全側）。主な担保は、AC-Gb9 の差分試験。
   - SPI（KaitoKit の parser の値）。
   - GK の独立した walk。
   - 両者と entries の照合（範囲・level・method・OS id・CRC16・名前の byte）。
   - V1–V5。
   - 公開前の KaitoKit の全体の解析と、並び順の照合。
2. **名前の文字コード**:
   - R10 (a): EUC-JP などと推定された書庫は、rewriter へ戻る（今日と同じく、全名前が CP932 になる）。
   - R10 (b): `nameEncoding == nil` で非 ASCII の名前を持つ書庫も、rewriter へ戻る。足した CP932 名だけが推定の入力になると化けるため（`SP/p4rev/enc/results.txt`: 珍しい漢字 2 字の名前 12 件中 9 件）。最初の書き直しの後は、updater になる。
   - ASCII の名前だけの書庫に、珍しい漢字の名前を足すと化ける。今日の rewriter でも同じ byte を書くので、既存の問題である。P4 では扱わず、`verificationFailed` で公開しない（原本は無傷）。
   - CP932 と推定された書庫でも、次のときは書庫全体の推定が変わりうる（`fromWindows` の多数決、LHAHeaderParser.swift:1023-1032）。そのときも、projection の名前の照合が `verificationFailed` にし、公開しない。
     - 削除で、CP932 だけの名前が無くなる。
     - GK の追加で、OS `U` の member が過半になる。
   - 根本の代案は、GK が追加・改名の header に 0x46 = 932 を宣言すること（KaitoKit は宣言付きの名前を推定に入れない、:1015-1022）。LHARecords の出力を変えるので、P4 では行わない。
3. **tl-S11（header 長の下位 byte が 0 の level 2）**:
   - KaitoKit と bsdtar はそこで止まり、Lhasa と 7zz は後ろの member を読む。
   - そういう書庫は L3 で rewriter へ戻り、今日と同じく後ろの member は黙って落ちる（AC-A4 で経路だけを確かめ、損失を文書に書く）。
   - KaitoKit の読み方を直すか、この形を読み取り専用にするかは、別の判断として利用者に諮る。P4-K は公開値を変えない。
4. **改名した member の正規化**: level 0/1 の member や、拡張 header の多い member を改名すると、その member だけが今日の rewriter と同じ形になる（§Gb5 の一覧）。design.md と release notes に書く。OS に依る解き方の member（LHArk）は L8 で rewriter へ戻る。
5. **SFX・公開しない member・後ろの byte**: どれも rewriter へ戻り、今日どおり落ちる。SFX は stub を落とした書庫を元の名前で公開するので、実行形式として動かなくなる（P5 の 7z と同じ）。stub を残して更新するか、SFX を読み取り専用にするかは、利用者に諮る（ORDER45 §8-3）。
6. **編集できる範囲を広げること**:
   - MacBinary の `m` member・symlink・`-pm2-` は、raw のまま運べば編集できる。ただし、R・L に当たって rewriter へ戻ると、保存で必ず失敗する（P0 の不具合の再来）。
   - 広げるには、「この書庫は updater でしか編集できない」ことを capability に持つ必要がある。そのうえで、設定が先頭のときや R・L に当たるときに読み取り専用として扱う KF の経路が要る。後続の課題。
7. **解析の二重**:
   - LHAUpdater も、KaitoKit の解析を一度行う（100k で約 0.4 s。500k は未計測）。
   - session の reader（P1-A で採用した検証 reader）を渡して省くのは、後続の課題。そのためには、記述子の同一性と SPI の結び付けが要る（P3-K の `ByteSourceFileIdentity` が土台）。
8. **共有の出力の部品**:
   - ORDER45 §1.1 の文を、S11（P2-G）の着手前に P2.md へ入れる。
   - 入れ損ねて P2-G が TarUpdater の中に部品を持った場合は、P2-G の Codex thread へ一つの修正として送る（P4-G-b で shipped の TarUpdater から切り出さない）。S20 の着手の門で確かめる。
   - P2・P3 の試験と `SplicedArchiveOutputTests` を変えずに通すことを、P4-G-b でも門にする（AC-Gb1）。
9. **並列化の記憶**:
   - member ごとの pipeline は threads × (2 MiB + 表 1.1 MiB)、区切りの pipeline は threads × (1 MiB + 8 KiB + 出力)。
   - AC-Ga4 の最大常駐メモリで確かめる。試作では測っていない。
10. **追加の照合の費用**: V3(b) は、追加 member を KaitoKit で直列に復号する。大きな追加（GB 級）では、commit の時間の大半になりうる。AC-Gb11 で時間を報告し、超過が問題になれば、方針 1 の範囲で member ごとの並列化を後続で検討する。
11. **KaitoKit の release**: P4-K は、KaitoKit 0.13.0 の SPI の追加だけ。P5 の KaitoKit 部分（0.14.0）とはまとめない（ORDER45 §5）。
