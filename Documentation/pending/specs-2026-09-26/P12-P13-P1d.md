# P12（KaitoFinder）: 分割巻の保存で重複する全体の読み取りを減らす

## OBJECTIVE

分割セットの保存（保存時モードの保存、即時モードの編集、分割出力の「別名で保存」）から、次の冗長な処理を除く。

- 新しいデータ N（= 作業ファイル W の長さ）を全部読む三つの処理
- 入力 M の SHA-256 の計算（`usesHashes` でないとき）

設計上必要な証明はすべて残す。

- 除く:
  - S4・S10 の reader の後の再ハッシュ（`VolumePublishTransaction.swift:293`。一回の保存で 2 回）。APFS で hazard が無いときだけ stamp の照合にする。
  - W の開き直し（`ArchiveSplitSave.swift:153-154`。tar.* では全体の展開）。
  - `prepare()` の W 全体の SHA-256（`ArchiveVolumeMetadata.swift:112`。値を比べる処理が無い）。
  - 連結コピーの入力側の SHA-256（`ArchiveSplitWorkProducer.swift:57,61,67`。比べるのは :68 の `usesHashes` のときだけ）。
- 残す:
  - S4 の byte の証明（:270）と reader の照合（:271-283）。
  - S10 の byte の証明（:270）と reader の照合。
  - 次の番号の名前が無いことの照合（hash の前と後。:254、:262、:294）。
  - reader の失敗時の全文 hash（:286）。
  - 即時モードで旧巻を削除する前の証明（:389-398）。
  - 回復（`VolumePublishRecovery`）のすべての証明。
  - FAT/exFAT・ネットワーク・file provider・HFS+ での全文の再ハッシュ。
- 全巻を書き直す公開はそのままにする。一部の巻だけを書き直す公開はしない。確認文「すべての巻を書き直して…」も変えない。

### 段 1（P12-1）

**D1 reader の後の再照合を stamp にする（APFS で hazard が無いときだけ）**

- `VolumeSetPublication.begin`（`VolumeSetPublisher.swift:82` の `volume` の後）で次を決め、`VolumeSetPublication` の stored property（`let`）として持ち、publish の transaction へ渡す。

  ```swift
  stampsProveContent = operations.allowsStampRecheck && volume.fileSystem == "apfs" && volume.hazard == nil
  ```

  - `VolumePublishOperations.allowsStampRecheck: Bool = true`。試験で同じ注入を全文 hash の経路と比べるための切り替え。hazard の注入は他の動作（`isNetworkVolume`、回復の索引）も変えるので使わない。
  - journal には書かない（schema を変えない）。`VolumePublishRecovery` では使わない（transaction の既定 `false`）。
  - HFS+（`hfs`）は mtime が秒単位なので対象外。FAT/exFAT（`needsOldHashes`、`VolumePublishFileSystem.swift:187`）、`non-local`、`file-provider` も対象外（hazard が nil でない）。
- `VolumePublishTransaction` に `var stampsProveContent = false` を足す。既定では今と同じ。
- `validateNew`（:268-295）の :293 を次にする。

  ```swift
  if validation != nil {
      if stampsProveContent { try recheckStamps(in: directory, inodes: inodes) }
      else { try validateHashes(in: directory, inodes: inodes) }   // 今と同じ
  }
  try directory.requireAbsent(record.nextName)                      // :294 を残す
  ```

- `recheckStamps`（新設。mutating）:
  1. `record.validate(stagingName:)` と `directory.verifyPath()`（`validateHashes` の :251-253 と同じ）。
  2. `directory.requireAbsent(record.nextName)`。
  3. `record.newVolumes` の全部について次がすべて成り立てば、巻ごとに `operations.didRecheckStamps(url)` を呼ぶ。
     - `directory.info(name)` が通常ファイル。
     - `st_size == volume.length`。
     - `newProof[name] == Stamp(info)`（dev・ino・size・mtime の秒と ns）。
     - `inodes == nil || inodes[name] == info.st_ino`。
  4. 一つでも違えば、その場で `try validateHashes(in: directory, inodes: inodes)` を呼んで返る（今の :293 と同じ全文の証明。内容が違えば `contentMismatch`、配置の inode が違えば `publishedVerificationPending`）。
  5. `directory.requireAbsent(record.nextName)`。
- 前提が成り立つ理由:
  - `newProof[name]` は、同じ `validateNew` の :270 が hash を読み終えた後の path の stat で記録している（:257-260）。hash の間の書き換えは `VolumePublishFS.hash` の前後の `sameFile`（:155-172）が捕まえる。
  - reader の間の書き込みは、APFS の ns 単位の mtime か inode の変化で捕まえる。xattr の書き込み（`writeNative`、Spotlight）は ctime だけを変え、stamp に入らない。
  - size と mtime（ns まで）を意図して戻す書き込みは捕まえない。`newMatches`（:169-176）と `oldProof`（:161-168）が既に置いている信頼と同じ（§リスクと未決 3）。
- :286 の catch の中の全文 hash は残す（reader の失敗を byte の破損と区別するための証明）。

# P13（KaitoFinder）: tar の `\` を含む名前の展開と、変換で受け取る名前の規則

## OBJECTIVE

- (a) **tar の `\`**:

## DESIGN

### (a) 名前の構文

**A-1 型**（`ExtractionPath.swift`。`import KaitoKit` と `import GyoshukuKit` を足し、型は修飾して書く）:

```swift
nonisolated enum ExtractionPath {
    enum NameSyntax: Sendable, Equatable {
        case portable   // 今の規則: / と \ で分け、先頭の drive 文字（英字 + :）を外す
        case posix      // / だけで分ける。\ と : はただの文字
        init(_ format: KaitoKit.ArchiveFormat) { self = format == .tar ? .posix : .portable }
        init(_ format: GyoshukuKit.ArchiveFormat) { self = format.allowsColonsAndBackslashes ? .posix : .portable }
    }
    static func components(_ name: String, syntax: NameSyntax) throws -> [String]
}
```

- `components` は既定の引数を持たない（一引数の旧い関数を残さない）。呼出し漏れは compiler が見つける。
- 処理の順（今の :5-19 を syntax で分ける）:
  1. NUL があれば拒否する（「パスにNULがあります。」）。
  2. 先頭の `/` の byte を落とす（design.md §9）。
  3. `portable` だけ: 先頭の drive 文字を外す（:9-11）。
  4. 分割する。`portable` は `/` と `\` で分け（:13）、`posix` は `/` だけで分ける。
  5. `..` の成分があれば拒否する（「パスに..成分があります。」、:15）。
  6. `posix` だけ: 各成分を `\` で分けた片（byte で比べる）に `..` があれば、同じ文言で拒否する。今の tar の `a\..\..\x` の拒否を保ち、`\` を区切りと解釈するかもしれない driver に `..` の一歩を渡さないため。
  7. `.` の成分を落とす。空なら拒否する（「パスに有効な名前がありません。」）。

- init に `nameSyntax: ExtractionPath.NameSyntax = .portable` を足す。既定を今の厳しい規則にするので、呼出し漏れは拒否になり、traversal にはならない。

  - 空・`.`・`..`・NUL・`/` の拒否と、NAME_MAX・PATH_MAX・`isInside` の照合（:55-58、:64-81）は変えない。

**A-4 traversal が起きないことの証明**（検証記録にこのまま書く）:

1. 展開のすべての書き込みは `ExtractionDestination` を通る。各成分は directory の記述子に相対な一回の系呼出しで開く（中間: `mkdirat` と `openat(…, O_DIRECTORY | O_NOFOLLOW)`、:112-115。葉: `openat(parent, leaf, O_CREAT | O_EXCL | O_NOFOLLOW)`、:158・:234。link: `symlinkat` :207、`linkat` :283）。
2. macOS の VFS は、名前の探索で `/`（0x2F）だけを区切りにする。`openat(dirfd, "a\\..\\x")` はその directory の直下の一つの名前だけを指す。成分が `/`・NUL・空・`.`・`..` を含まないことは `validate`（:59-61）が保証する（変えない）。
3. `\` を置けない、または特別に扱うファイルシステム（msdos・exfat・smbfs など）でも、A-1 の 6 と A-2 により `\` で分けた片に `..` は無い。`\` が区切りと解釈されても、出力 root の下の名前にしか届かない。実際の動作（拒否か置換か）は検証記録で確かめる（VERIFICATION の FAT/exFAT の手順）。
4. 解決後の実パスの照合（`isInside`、:64-81）と、symlink の target の検査（:192-205。target は `/` だけで分けて解決する）は変えない。
5. 以上により、`posix` で新たに許すのは「出力 root の中の一つの名前に `\` の byte が入ること」だけになる。

**A-5 NFC と重複**:

- 出力名を予約する鍵（`ExtractionService.swift:259`）は `components.joined("/")` の NFC のまま。
- `posix` では `a\b`（1 成分）と `a/b`（2 成分）は別の鍵になる（今は同じ鍵で、後の方が「重複する出力名です」で失敗する）。
- 正準等価な綴り（`é\x` と `e\u{301}\x`）は今と同じく、最初の一件が勝つ。大文字と小文字の違いだけの衝突は `O_EXCL` で防ぐ。

## リスクと未決

1. **cpio・ar・xar・ISO（Rock Ridge）の `\`**: どれも Unix 由来で `\` はただの文字。依頼は tar 系だけなので `.portable` のまま。そろえるなら `NameSyntax.init(_: KaitoKit.ArchiveFormat)` の一行と試験で済む。利用者に確かめる。
2. **`\` で分けた片に `..` がある名前の拒否**（A-1 の 6）: `x\..\y` のような正当な Unix の名前も拒否する。今も拒否しているので後退ではない。なお GK の tar の名前の規則は `x\..\y` を書ける（`ArchiveWriter.normalizedPath`、`/` だけで分ける）ので、KaitoFinder で改名して作った名前が展開では一件ずつの失敗になりうる。
3. **ZIP の不一致**: 一覧では一つの葉、展開では区切り、という既存の不一致は残る（依頼どおり）。
4. **展開先が FAT/exFAT/SMB**: `back\slash.txt` は今は `back/slash.txt` として書けている。P13 の後は driver の扱い（拒否か置換）になる。FAT/exFAT は VERIFICATION の手順で実測して検証記録に書き、release notes に書く。SMB は未検証として書く。展開先が apfs・hfs 以外のときだけ `.portable` に戻す案（今の成功の動作を保つ。file promise の名前は出力先より先に決まるので対象外）は、実測の結果を見て利用者に確かめる。
5. **UX**（任意）: (b) の拒否は、保存パネルを閉じて作成を始めた後に出る。パネルの確定時（`ArchiveSavePanel.panel(_:validate:)`）に選んだ形式で葉を検査すれば、既存の文言のままパネルを閉じずに示せる。本書には入れない。

1. アプリ（P1d-A）では、世代ごとに一つの名前表 `ArchiveNameIndex` を session が持つ。今の「改名用の索引」`EntryNode.renameOccupancy`（`EntryTree.swift:59-72`）と同じ条件で作る占有表。即時モードの計画・mutate の中の検査・改名欄の検査・保存時モードの install と保存が共有する。公開と照合が済んだ編集の後は、その変更だけを当てて次の世代の表にする（advance）。当てた結果は新しい reader の名前と位置ごとに照合して確かめ、一つでも違えば捨てる。
2. GK（P1d-G）では public API を変えない。ZIP の `ArchiveUpdater` の名前の衝突検査を、最初の数回だけ生存名の線形走査にし、回数が budget を越えたら今の全件の表を作る。走査の述語は今の二つの表の述語と同一にし、試験の神託で確かめる。
3. 保存時の保存の前の全件の表現可能性の検査を、予約の時と同じ差分の検査（`ArchiveReservationValidation.validate`、:59-84）に置き換える。**これは P1 の「保存時モードの全体検査は残して安くする」（計画の P1 の行）を改める判断**。オーケストレータ（必要なら利用者）の了承を得てから入れる。了承が無ければ A5 の「保存の前の検査」だけを外し、他は入れる。
4. cross-repo の接点は新しく作らない。P1d-G は GK の内部だけを変え、P1d-A は既存の GK の public API だけを使う。KF は GK の内部の挙動に依存しない。

### DESIGN

**G1 生存名 L**: open 時の `reader.entries` のうち `removed` に無いもの（名前は `renamed[index] ?? entry.name`、種類は `entry.kind == .directory`）と、`writer?.appendedPaths` を合わせたもの。今の `existingPaths + writer.appendedPaths`（:210-213、:217-218）と同じ集合。

**G2 意味の定義**（今のコードの動作をそのまま書き下したもの。実装はこれと同一でなければならない）:

- 共通: 等しさは Swift の String の `==`（正準等価）。`/` は合成に関わらない starter なので、名前全体の NFC は成分ごとの NFC の連結になり、成分ごとの正準等価と NFC の byte の一致は同値。
- `.reservations`（改名用。`EditPathReservations.swift:19-20,66-76`）:
  - `K(x)` = x の末尾の `/` を一つ除いたもの。`C(x)` = `K(x)` を `/` で分けた列（空の成分も残す）。
  - 候補 c（`normalizedPath` 済み、種類 d）、除く index e について:
    - ancestorFile: L\{e} のある file l について、`C(l)` が `C(c)` の真の接頭辞（長さ 1 以上）。
    - exact: L\{e} のある l について `C(l) == C(c)`。
    - subtree: L\{e} のある l について、`C(c)` が `C(l)` の真の接頭辞。
    - 順: ancestorFile → `invalidPath(c)`、exact → `duplicatePath(c)`、`!d && subtree` → `invalidPath(c)`。
- `.writer`（追加用。`ArchiveWriter.swift:198-212` と :402-415）:
  - L の各 l について、`k(l)` = 名前の末尾の `/` を一つ除いた生の文字列（空の成分や先頭の `/` をそのまま含む）。`P(l)` = `pathComponents(k(l))`（空の成分を除く）の接頭辞を `/` でつないだもの（長さ 1 から 成分数 − 1 まで）。
  - 候補 c（`normalizedPath` 済み。空の成分は無い）の `kc` = 末尾の `/` を除いたもの、`Q(c)` = `kc` の真の接頭辞を `/` でつないだもの。
    - exact: ある l について `k(l) == kc`。
    - subtree: ある l について `kc ∈ P(l)`。
    - ancestorFile: ある file l について `k(l) ∈ Q(c)`（l が空の成分を含めば一致しない）。
    - 順: exact → `duplicatePath(c)`、`!d && subtree` → `invalidPath(c)`、ancestorFile → `invalidPath(c)`。
  - 例: 既存 `a//b/c` に対して候補 file `a/b` は、`.writer` では `invalidPath`（`P = {a, a/b}`）、`.reservations` では受理（`C = [a, "", b, c]`）。単純な byte の接頭辞の比較では前者を見逃すので、空の成分・先頭の `/` を含む名前は遅い経路で扱う。

**G3 走査の実装**:

- 平らな snapshot: 最初の走査で、open 時の `reader.entries` の名前を index 順に一回だけ平らな buffer に写す（UTF-8、末尾の `/` を一つ除く、種類、「単純」の印）。「単純」= ASCII で、空の成分も先頭の `/` も無い。単純でない名前は、NFC の key（`.reservations` 用）と、空の成分を除いてつないだ NFC の key（`.writer` 用）をその時に求めて持つ（割当ては単純でない名前だけ）。snapshot は以後変えない。
- 生きている状態は snapshot に写さない:
  - `excluded: [Bool]`（open 時の件数の長さ）を `remove` と `rename` で O(1) で更新する（removed ∪ renamed のキー）。
  - 走査は snapshot の index のうち `excluded` でないものと、`renamed` の値の列と、`writer.appendedPaths` の列を対象にする（後の二つは少数なので String で比べてよい）。
- 候補が ASCII なら単純な名前とは byte で、`/` の境界での接頭辞として exact・subtree・ancestorFile を求める。候補が ASCII でなければ、候補の NFC と各名前の NFC の key で同じ比較をする（`U+212A` と `K`、`U+037E` と `;` も正しく扱う）。
- `budget = 4`: 一つの updater の中で走査を 4 回行った後の検査では、今の表を作ってそれを使う（改名は `reservations()`（:215-222）、追加は `writer.replaceExistingPaths(existingPaths)`（:369、:385））。

**A4 advance（公開と照合が済んだ後）**:

- `reloadAfterMutation` に `advancing change: ArchiveNameIndexChange?`（既定は nil）を足す。中身: `removed: [Int]`、`renamed: [Int: String]`（最終の名前。GK へ渡した正規化済みの byte）、`appended: [(name: String, isDirectory: Bool)]`（editor へ渡した順）、`mode: ArchiveCapabilities.Mode`。
- `mode` は、公開に成功した呼出しで実際に使った mode を渡す: S13 の `base.resolved(with: options)` の後の値で、`savePending`・`updatePassword` の `nonRelocatableEntry` による `.rewrite(.zip)` への切り替え（e49ecf5 の `ArchiveSession.swift:555-560`、:706-711）の後の値。分割の保存では `ArchiveSplitWorkProducer.Result.mode`（`recompressedZIP` なら `.rewrite(.zip)`）。
- 関数の最初で `let previousEntries = reader?.entries` を取っておく。
- 関数の最後（`invalidated = false` の前）で、次のすべてを満たすときだけ advance して保存する。一つでも欠ければ `nameIndexStorage` を空にし、次に使う時に作り直す。
  1. `change.mode` が `.inPlace` か `.update(_)`（`.rewrite(_)` は出力の順が保証されない）。
  2. 保存済みの表の世代が「新しい世代 − 1」（`reloadAfterMutation` は世代を 1 だけ進める。:781）で、形式が一致し、`entryCount == previousEntries.count`。
  3. 位置の照合（運んだ entry は byte の比較だけで、NFC も hash も使わない。500k 件で約 22 ms）:
     - 旧 entries を順にたどり、`removed` は飛ばす。
     - 改名していない entry: 新しい reader の対応する entry の名前の byte が `old[i].name` と等しく、kind も等しい。名前の復号が書庫全体の推定に左右されて変わった場合も、ここで捨てられる。
     - 改名した entry: `ArchiveEditPlan.key(new.name) == ArchiveEditPlan.key(renamed[i])` で、kind が等しい（key は末尾の `/` を除いて比べる）。
     - その後の末尾の entries が `appended` と順に一致する（key が等しく、directory か否かも一致する）。件数が一致する。
  4. 変わった entry（改名と追加）の名前が clean の述語を満たす。
  5. 変わった entry を一件ずつ `ArchiveRewriter.probe(entries: [entry.pendingCopy(index: 0)], format:)` に通す（`ArchiveReservationValidation.swift:80-83` と同じ検査）。通れば `representable` を旧値のまま運び、通らなければ `representable = false` にする（表は保つ）。
- occupancy は旧値を写し（COW。500k 件で約 2 ms）、改名前の key と削除した key を除き、改名後の key と追加の key を入れる（`name_index_advance` の span の中）。追加に hard link が現れたら `containsHardLinks = true`。
- 変更を渡す側: `edit`（`plan.removals` と `plan.renames`）、`append`（`plan.replacingEntries` を removed、`plan.items` を appended。`ArchiveImportTransaction.swift:498-516` の順）、`createFolder`（`plan.path` を directory として appended）、`updatePassword`（空の変更。実際の mode が `.inPlace` のときだけ）、`savePending`・`savePendingSplit`（A5 の最後の項）。それ以外の `reloadAfterMutation` の呼出し（Undo など）は nil を渡し、表を捨てる。
- 後段の約束: `ArchiveNameIndexChange` の `appended` は editor へ渡した順（即時は `plan.items` の順、保存は追加の後にフォルダ）。
  S39（P6-A）は台帳を足してもこの順と advance の条件を変えず、S41（P7-A）は一括の `[ArchiveAddition]` を同じ順に作る（ORDER-P6-P13 §2）。
- 正しさの論拠: 旧表は旧 reader の entries から作ったもの。3 により新 reader の entry の列は「旧の列から removed を除き、renamed を置き換え、末尾に appended を足したもの」と一致する。表は各 entry の key と directory か否かだけで決まり、4 により変わった entry も clean なので、advance した表は新 reader から作り直した表と等しい。P0 の公開前の照合はこの前に独立に済んでいる。

**A5 保存時モード: install と保存の前の検査**:

- `ArchivePendingEditor.install(base:generation:format:sessionID:checksCancellation:index:)`（`ArchivePendingChanges.swift:158-179`）に `index: ArchiveNameIndex?` を足す。
  - `index.generation == generation`、形式が一致、`entryCount == base.count`、`representable`、`!containsHardLinks` をすべて満たすときは、新設の `ArchiveReservationValidation(base:format:index:)`（occupancy を index から受け取るだけ。O(1)）を使い、`makeValidation` を呼ばない。
  - 満たさないときは今の `makeValidation` を呼ぶ。成功して occupancy がある場合は、その結果を `session.adoptNameIndex(…, representable: true)`（A2 の規則で保存）で渡す。そのために `ArchiveReservationValidation` の occupancy に internal の読み出しを足す。
  - document から install を呼ぶすべての所（:480、:921、:938、:1220、:1352、:1631、:1765）で `index: session.nameIndex(generation: <その世代>, format: session.reservationFormat)` を渡す。
- 保存の前の検査（`savePending` の `validateRepresentability(plan.projected, …)`、`savePendingSplit` の同じ呼出し）:
  - `nameIndex(generation: baseGeneration, format: outputFormat)` が `representable && !containsHardLinks` で、`outputFormat == reservationFormat` のときは、全件の検査の代わりに差分の検査を `representability_differential` の span の中で行う。
  - 差分の検査は新しい overload `ArchiveReservationValidation(base:format:index:).validate(pending, projected: plan.projected, position:)`。衝突があるときと正規化できない名前があるときは今の `validateFull` に落ちて同じ例外を投げる（:60-62、:75-77）。例外の順が全件の検査と同じになる理由: 基底の entry はすべて表現できる（帰納）ので、全件の検査で最初に失敗するのは変わった entry で、差分の検査は変わった entry を projected の順（生存の基底の index 順 → 追加 → folder）に調べる。衝突が一つでもあれば全件の検査に落ちる。
  - `position` は変わった index の位置を算術で求める（`ArchivePendingChanges.swift:68-90` の順。基底の index i の位置は i − （i より小さい削除の数）、追加と folder は基底の生存数からの offset）。`ArchivePendingProjection`（:124-129）の全件の辞書は作らない。
  - それ以外（index が無い、表現可能性が未証明、hard link がある、形式が違う）は今の全件の検査。
- 保存が成功したら、`reloadAfterMutation` に次の変更を渡して advance する: `removed = plan.edits.removals`、`renamed` = 各 index の最後の改名（`ArchiveSaveReplayPlan.swift:77-139` の `ordered` の最後。循環をほどく一時名の後の最終の名前）、`appended` = `plan.additions`（順）の後に `plan.folders`（順）（`replay` の :203-213 と同じ順）、`mode` = A4 の実際の mode。この後の install（`ArchiveDocument.swift:916-938` の経路）は A5 の近道を通る。

### CONSTRAINTS

- 検査の結果は今と同一に保つ（受理・拒否・例外の型・文言・対象の名前）。名前が clean でない基底、hard link のある基底（A5）、形式が違う保存では、今の全件の経路を通る。GK の独自の検査と P0 の公開前の照合はそのまま残る。

- 表は session・窓・editor で同じ値（COW）を共有し、永続の複製を増やさない。advance の間だけ旧表と新表の二つが並ぶ。
- 削除だけの編集で、表を新しく作らない。
- 決定 3（A5 の差分の検査）はオーケストレータの了承の後に入れる。了承が無ければ A5 の「保存の前の検査」だけを外す。
- GK・KK の public API だけを使う。新しい UI 文言は無い。Swift 6 で書き、`@unchecked Sendable` を新しく使わない。
